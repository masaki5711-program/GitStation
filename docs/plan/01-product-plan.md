## 1. 目的と方針

**目的**: 社内で完結する、GitHub / GitLab に相当する開発基盤を自作する。
既製品では実現できない 3 つの価値を持たせる。

| # | 差別化の軸 | 内容 |
|---|---|---|
| 1 | **ローカル LLM による検証** | マージとパイプラインを、社外にデータを出さないローカル LLM で検証する（§6） |
| 2 | **kanflow との双方向連携** | 要件（PBI・受入基準）とコード・パイプライン・デプロイを相互に結びつける（`02`） |
| 3 | **Git を知らない人への開放** | 設備仕様書などの文書を、Git を意識させずに版管理する（文書ポータル） |
| 4 | **仕様駆動による AI 開発の加速** | 仕様 → PBI → 実装 → 検証 → デプロイを、要件の ID で 1 本につなぎ、AI が根拠付きの文脈で実装・検証できるようにする（`03`）。**製品の根幹の目的** |

**設計方針**

1. **コアは小さく、拡張点は明示的に。** 機能を足すときに既存のコアを書き換えずに
   済むよう、拡張点（§5）を最初から設ける。
2. **Claude が保守する。** すべての失敗は登録済みのエラーコードを持ち、ログと
   Runbook だけで原因にたどり着ける（CLAUDE.md §3）。
3. **決定的な処理が主、LLM は補助。** マージ可否の最終判断は、テスト・権限・
   人間の承認という決定的な仕組みで行う。LLM は根拠付きの指摘を出す側に置く。
4. **完全オンプレミス。** 実行時に外部サービスへ依存しない（LLM も社内 GPU で動かす）。

### 3.10 エッジの配布と更新（工場の IoT 基盤）

GitStation は工場の IoT を支える基盤として、大量のエッジコンピュータのプログラムを統合管理する（2026-10-28 のユーザーの要望）。
§3.4 の SSH でサーバーに押し込む方式は数台〜数十台のアプリサーバー向けで、数百〜数千台のエッジには使わない。

| 機能 | 優先度 | M | 備考 |
|---|---|---|---|
| エッジのエージェント（`forge-edge-agent`。エッジから HTTPS で取りに来る pull 型） | Must | M4E | エッジは外から接続を受けない。工場の NAT・ファイアウォールの内側でも動き、回線が切れても続きから再開する |
| 機器の登録と識別（機器ごとの証明書による相互 TLS、登録用の一回限りのトークン） | Must | M4E | 機器は `authorize()` の主体（機器）になり、権限マトリクスに行を持つ。自分に割り当てられたリリースしか読めない |
| 機器の台帳（工場・ライン・設備・機種・OS のグループとラベル）と状態（現在の版、最後の接続、健全性） | Must | M4E | 設備の仕様書（範囲 D）と結びつける |
| リリース（CI が作る不変の成果物。署名付き、内容のハッシュで識別） | Must | M4E | エッジは署名を確かめてから入れる。改ざんされた成果物は入れない |
| 望ましい状態の宣言（このグループにはこの版）と段階的な展開（カナリア → 割合 → 全台） | Must | M4E | 失敗の割合がしきい値を超えたら自動で止める |
| 更新してよい時間帯（保守の時間帯。ラインの稼働中は更新しない） | Must | M4E | 稼働中の設備を止めない |
| 更新後の健全性の確認と自動のロールバック（前の版を残す、A/B の切り替え） | Must | M4E | 更新に失敗した機器は自分で前の版に戻る |
| 本番への展開は人の承認（§3.4 の承認付きデプロイと同じ仕組み） | Must | M4E | CLAUDE.md §3-7 |
| 工場ごとの中継（キャッシュ）と差分の配布 | Should | M4E | 帯域を節約し、数千台が同時に本体から取りに来ないようにする |
| オフラインの更新（USB などで持ち込む署名付きのパッケージ） | Could | M8 | 外とつながらないネットワークの設備向け |
| 機器のログ・指標の収集 | Won't | — | 製造データの収集は別の基盤の役割。forge は更新の結果と健全性だけを持つ |

**M1 から守る設計の制約**（エッジの機能を後から無理なく足すため）:

- 機器の定期的な接続（心拍）は `events` / `audit_log` に入れない。台帳の行を上書きし、記録するのは状態の変化（版の変更、失敗、ロールバック、承認）だけにする。数千台が数分ごとに接続しても Outbox と監査ログがあふれないようにする。
- 主体の種類に「機器」を足せるようにしておく（ADR-0010 の `Principal` と権限マトリクス）。
- エラーコードの領域に `EDGE` を足す（登録の前に、エージェントモデル側で `validate-error-registry.js` の `AREAS` と `forge-error-contract.md` に加える）。
- ジョブキュー（手順 C6）に機器ごとのジョブを積まない（数千件にしない）。展開の進み具合は、望ましい状態と機器からの報告で決める。

### 3.11 クライアント CLI `gstn`（AI と開発者が GitStation を操作する）

**2026-10-30 追加（ユーザーの要望）**: 開発は Claude Code で行う。Claude が GitHub の `gh` と同じように、
GitStation のさまざまな操作をコマンドで行えるようにする。今 GitLab で使っている `glab` の置き換えでもある（`06` §2）。
**AI が扱いやすいことを最優先の設計目標にする。**

- 名前は **`gstn`**（`gs` は Ghostscript、`gst` は zsh の `git status` の別名と重なるため）。
- 開発者の PC で動く **クライアント**。サーバーの `forge` バイナリ（`forge admin` は運用者がサーバーで使う管理用）とは別。
  REST API v1 だけを呼び、DB やサーバー内部には触れない。Windows / Linux の単一の実行ファイル。外部のサービスに依存しない。
- 同じクライアントのライブラリの上に、MCP サーバー（`06` §4.5）も載せる。CLI と MCP は同じ API の 2 つの入り口。

**AI が扱いやすくするための約束（すべてのコマンドに適用）**

| # | 約束 | 内容 |
|---|---|---|
| C-1 | 網羅 | **Web UI と API でできることは、原則すべて `gstn` でもできる**。REST のルートの登録簿と `gstn` のコマンドの対応をテストで検査し、対応のないルートはゲートで止める（権限マトリクスと同じ考え方） |
| C-2 | 機械が読める出力 | すべてのコマンドに `--json`（API v1 と同じ形・版の規則）。`--fields` で項目を絞る。既定は人が読む表 |
| C-3 | 決まった失敗の形 | 終了コードを固定する（0 成功 / 2 使い方の誤り / 3 認証・権限 / 4 見つからない / 5 衝突 / 6 一時的な失敗で再試行してよい / 1 その他）。失敗時は stderr に `{error_code, user_message, request_id, retryable}` を JSON で出す。AI はエラーコードから catalog と runbook を引ける |
| C-4 | 対話しない | 端末でないときは決して入力を待たない。確認が要る操作は `--yes` で通す。変更する操作には `--dry-run` |
| C-5 | 自分で説明する | `gstn help --json`（全コマンド・引数・例・必要なスコープ）と `gstn schema <コマンド>`。AI が手探りせずに使い方を知れる。OpenAPI と同じ登録簿から生成する |
| C-6 | 汎用の口 | `gstn api <METHOD> <path>`（`gh api` 相当、`--paginate`）。専用のコマンドがまだない操作もすぐ使える |
| C-7 | 待てる | 時間のかかる操作（パイプライン、チェック、マージ）に `--wait --timeout`。`gstn run watch` でログを追う |
| C-8 | git との橋渡し | `gstn auth git-credential`（git の資格情報ヘルパー）で、素の `git clone/push` もトークンで動く。`gstn repo clone` |
| C-9 | 安全 | AI は `is_agent` のトークン（ADR-0019）を使う。ADR-0017 のとおり、エージェントは push と MR の作成はできるが、**MR の承認・保護ブランチへのマージ・本番のデプロイの承認はできない**（サーバーの `authorize()` が拒否し、`gstn` は理由とエラーコードを返す）。トークンは表示もログ出力もしない |
| C-10 | 文脈 | `gstn context PBI-123`（`03` §6 の文脈 API）で、PBI・受入基準・関連する仕様とコードの位置をまとめて受け取る |

**段階（API ができた順にコマンドを足す）**

| M | コマンド |
|---|---|
| M1 | `auth`（`login --with-token`、`status`、`logout`、`git-credential`）、`repo`（create / list / view / clone / rename / transfer / delete）、`group`・`project`（create / list / member）、`protected-ref`、`api`、`help --json`、`schema` |
| M2 | `browse`（ファイル・コミット・差分・blame）、`token`（自分のトークンの一覧・作成・失効。ログインの API ができてから）、`user` |
| M3 | `mr`（create / list / view / diff / comment / review / merge `--wait` / checks、`status --json` = マージできない理由の一覧、`conflicts` = 他の MR との衝突の予測）、`checks`（外部ツールからの登録・更新）、`pbi`（kanflow の PBI の表示と紐付け）、`context`、`spec`（lint / trace）、`conflicts`（衝突の予測）、`risk check`（push の前の手元の差分）・`mr risk`（`04` M-6 の危険の検査）、`webhook`、MCP サーバー |
| M4 | `mr checks --wait`（失敗の診断 = エラーコードと既知の修正を返す）、`mr autofix`（サーバーのローカル AI の自動修正の起動・状況・履歴）、`mr queue`（マージキューへの投入・状態・`pause`）、`project settings merge.auto`（`04` M-5 の自動マージの方式）、`pipeline`・`run`（list / view / logs `--follow` / rerun / cancel）、`ci`（lint / plan、`04` P-3）、`deploy`（一覧・状態・ロールバックの要求） |
| M5 | `ops`（運用 API / MCP と同じ読み取り: ログ、メトリクス、ジョブ、エラーの集約）、AI レビューの結果 |

**修正の 2 つの流れ**: 開発者の PC の Claude が `gstn mr status` / `checks --wait` で失敗を読み、自分で直して push する流れと、
サーバーのローカル AI が直す流れ（ADR-0017 の自動修正）の両方を使える。同じ MR を同時に直さないよう、MR ごとに「いま直している主体」を
1 つだけ持ち（Claude の作業中はサーバーの自動修正が待つ）、`gstn mr status` に表示する。マージの自動化は `04` M-5。

### 4.2 コアの仕組み（すべての機能が乗る土台）

| 仕組み | 内容 | 段階 |

```
forge-db       sqlx、マイグレーション、リポジトリ層、Outbox、ジョブキュー
forge-auth     認証プロバイダ、認可（権限マトリクスの単一定義）、トークン、監査
forge-git      git の実行、Smart HTTP、ref 操作、マージの実行、保守
forge-review   MR、レビュー、承認、マージ条件の評価
forge-checks   Checks API（チェックの登録・更新・マージ条件との結合）
forge-ci       パイプライン定義の解析、スケジューリング、Runner API
forge-deploy   環境、デプロイ先、承認、ロールバック
forge-llm      LLM ゲートウェイ（プロバイダ、キュー、プロンプトの版管理、評価記録）
forge-integ    外部連携（作業項目プロバイダ、kanflow アダプタ、Webhook 配信）
forge-notify   通知（アプリ内、メール）
forge-docs     文書ポータル（M7）
forge-web      axum のルーター、REST API、OpenAPI、ミドルウェア
forge-cli      `forge` バイナリ
forge-runner   Runner バイナリ（M4）
forge-client   クライアント: 型付きの API クライアント（ライブラリ）と `gstn` バイナリ、MCP サーバー（§3.11）
```

`forge-client` は REST API v1 だけを呼ぶ。依存してよいのは `forge-core` と `forge-errors` だけ（API の型と、エラーコードの
表示文言）。`forge-web` やサーバー側のクレートには依存しない。

依存の向き: `forge-web / forge-cli → 機能クレート（review, ci, llm, integ …）→
forge-auth / forge-git / forge-db → forge-core → forge-errors`。機能クレート同士は
直接依存せず、イベントか `forge-core` の trait を介して連携する。
**CLAUDE.md §3-9 の依存の向きはこの構成に合わせて更新する**（エージェントモデル側の変更として先に行う）。

### 4.4 データベース

- 本番は PostgreSQL。**開発環境も PostgreSQL（コンテナ）にすることを提案する**
  （§11-5）。理由: ジョブキューの `SKIP LOCKED` や JSONB は SQLite にない。
  2 種類の SQL を保守すると、テストの抜けと Claude の調査負担が倍になる。
- マイグレーションは追記のみ（CLAUDE.md §3-6、`migration-immutability` フック）。

## 5. 拡張性の設計

機能を追加するときに、コアを書き換えずに済む「差し込み口」を以下に限定して設ける。

| # | 拡張点 | 形 | 最初の実装 | 将来の実装 |
|---|---|---|---|---|
| 1 | **ドメインイベント** | Outbox の購読者 | Webhook、通知 | LLM 検証、kanflow 連携、検索索引 |
| 2 | **Checks API** | コミットに対するチェックの結果（状態、結論、要約、行単位の注釈） | CI のパイプライン | LLM レビュー、kanflow の作業項目チェック、外部の静的解析 |
| 3 | **REST API v1 + OpenAPI** | バージョン付き。破壊的な変更は v2 で行う | 全機能 | クライアント SDK の生成 |
| 4 | **認証プロバイダ** | `trait AuthProvider` | ローカル | LDAP、OIDC |
| 5 | **作業項目プロバイダ** | `trait WorkItemProvider`（`02` §4） | kanflow | forge 内の Issue、その他のツール |
| 6 | **LLM プロバイダ** | `trait LlmProvider` | Ollama API | OpenAI 互換 API（vLLM、llama.cpp server） |
| 7 | **CI 実行方式** | `trait Executor` | Docker / Podman | シェル、VM |
| 8 | **デプロイ先** | `trait DeployTarget` | SSH | コンテナ基盤、エッジのフリート（pull 型のエージェント、§3.10） |
| 9 | **ストレージ** | `trait BlobStore` | ファイルシステム | S3 互換（オンプレミス） |
| 10 | **機能フラグ** | インスタンス単位・プロジェクト単位 | 新機能の段階的な公開 | |

**Checks API を中心に置く理由**: 「マージしてよいか」を決める材料（テスト、LLM の
指摘、kanflow の作業項目の状態、承認）を、すべて同じ形の「チェック」として扱える。
保護ブランチのルールは「どのチェックが必須か」を名前で指定するだけになり、
新しい検証を足してもマージ条件の評価ロジックは変わらない。

## 6. ローカル LLM による検証

### 6.1 基本方針

| 原則 | 内容 |
|---|---|
| **計算はコード、判断の補助は LLM** | 差分の解析、変更ファイルの分類、テスト結果、カバレッジなどはコードで確定的に求め、LLM には根拠として渡す（kanflow の分析パックと同じ考え方） |
| **LLM の結果は「チェック」として出す** | Checks API の 1 つの提供者になる。既定は**助言（advisory）**で、マージを止めない。プロジェクトの設定で「必須」にもできる |
| **危険なものは自動でマージしない** | 2026-10-30 改定。自動マージはプロジェクトが方式を選ぶ（`04` M-5）。ただし個人情報の流出と DB の破壊は、決定的な規則とローカル LLM の危険の検査（`04` M-6）で **どの方式でも警告付きで止める**。LLM は危険を上げることだけができ、LLM の判断で止める規則を外す経路は作らない。本番のデプロイは人間の承認 |
| **失敗を隠さない** | LLM が応答しない・タイムアウト・出力が不正なときは、チェックを「成功」にせず `error` 状態にし、`FG-LLM-xxxx` で記録する。必須チェックにしている場合の扱い（止める／人の判断で通す）はプロジェクトの設定で明示する |
| **出力は構造化** | JSON スキーマで検証する（重大度、ファイル、行、根拠、提案）。不正なら 1 回だけ再試行し、それでも不正ならエラーにする |
| **入力はデータとして扱う** | 差分やコミットメッセージには攻撃者が書いた文が含まれうる（プロンプトインジェクション）。LLM には変更系の道具を渡さず、出力が操作を起こすことはない |
| **版と記録** | プロンプトはリポジトリ内で版管理する。結果にはモデル名、プロンプトの版、入力のハッシュを記録し、評価と再現に使う |

### 6.2 マージの検証（MR）

| # | 機能 | 内容 | 優先度 |
|---|---|---|---|
| L-1 | **MR の要約** | 変更の目的、影響範囲、リスクの高い箇所を要約する（ja / en / id） | Must |
| L-2 | **AI レビュー** | 差分から、バグの可能性、エラー処理の漏れ、セキュリティ上の懸念をインラインコメントとして出す。重大度は baseline.md の 4 段階に合わせる | Must |
| L-3 | **受入基準との照合** | kanflow の PBI の受入基準を取得し、基準ごとに「差分とテストで満たされているか」を判定して、チェックリストとして表示する（`02` F-4） | Must |
| L-4 | **マージ準備の判定** | 決定的なシグナル（テスト、承認、変更規模、マイグレーション、権限まわりの変更）と L-2 の結果をまとめ、追加のレビュアーが必要な箇所を示す | Should |
| L-R | **危険の検査（AI の層）** | 個人情報・機密の流出と DB の破壊・データの消失の危険を分類し、根拠の行を付けて `forge/risk` に `warn` / `stop` を足す。決定的な規則の結果を下げることはできない。失敗は `stop`（`04` M-6、ADR-0017 Amendment F） | **Must** |
| L-5 | **コンフリクト解消の提案** | 解消案を**別ブランチのコミットとして提案する**。適用は人間が判断する | Could |

### 6.3 パイプラインの検証

| # | 機能 | 内容 | 優先度 |
|---|---|---|---|
| L-6 | **パイプライン定義の変更レビュー** | `.forge-ci.yml` の変更で、シークレットの露出、保護されていないブランチからのデプロイ、外部へのアクセスなど危険な設定を指摘する。**決定的なルール検査を先に行い**、LLM はその補足に使う | Must |
| L-7 | **失敗原因の診断** | 失敗したジョブのログの末尾、エラーコード、直近の変更から、原因の候補と対処を示す。過去の似た失敗も提示する | Must |
| L-8 | **不安定なテストの検出** | 同じコミットで成功と失敗を繰り返すテストを統計で検出し（決定的な処理）、LLM が原因の傾向を説明する | Should |
| L-9 | **デプロイ前の確認** | 本番デプロイの前に、前回のデプロイからの変更を要約し、リスクを示す。承認者の判断材料にする | Should |

### 6.4 処理の流れ（L-2 の例）

```
MR の作成・更新 → イベント merge_request.updated（Outbox）
  → worker: 差分を取得し、確定的な前処理を行う
      （生成ファイルとロックファイルの除外、言語の判定、大きい差分の分割、変更規模の算出）
  → kanflow から受入基準を取得（リンクがある場合。`02` §4）
  → LLM ゲートウェイ: 優先度付きキュー → プロンプトの版を選択 → LLM の呼び出し（タイムアウト付き）
  → 出力を JSON スキーマで検証 → Checks API にチェック「forge/ai-review」を登録
      （結論: success / neutral / failure / error、要約、行単位の注釈）
  → MR の画面に表示。各指摘に「役に立った／誤り」のボタン
```

### 6.5 品質を上げる仕組み（測ってから改善する）

- 指摘ごとの「役に立った／誤り」の評価を記録し、**採用率と誤検知率**を集計する。
- 過去の MR から作った**評価セット**（見逃してはいけない欠陥を仕込んだ差分）を持ち、
  プロンプトやモデルを変えるときは評価セットで比較してから切り替える
  （エージェントモデルの eval と同じ考え方を製品にも持ち込む）。
- 指摘の数には上限を設け、確信度の低いものは出さない（指摘が多すぎると読まれなくなる）。

### 6.6 実行基盤

| 項目 | 方針 |
|---|---|
| モデル | **qwen3.8 27B を基準にする**（kanflow で運用実績がある）。コード向けのモデルを追加する場合は評価セットで比較してから決める |
| 呼び出し方式 | `forge-llm` の `LlmProvider` trait。Ollama API と OpenAI 互換 API（vLLM、llama.cpp server）の両方に対応し、特定の実行基盤に依存しない |
| 文脈の長さ | 用途ごとに設定する。大きい差分はファイル単位に分割してから統合する |
| 同時実行 | ゲートウェイのキューで同時実行数を制限し、優先度を付ける（対話 > MR レビュー > 一括処理） |
| **GPU の共用** | kanflow の Ollama は VRAM に 1 モデルしか常駐させていない。**同じモデルを共用すれば入れ替えは起きないが、混雑すると kanflow のチャットが遅くなる**。当面は共用し、forge 側で同時実行数を絞る。利用が増えたら forge 専用の GPU サーバーを用意する（§11-6） |
| 監視 | 待ち時間、処理時間、タイムアウト率、出力不正率をメトリクスで出し、`forge doctor` で疎通を確認する |

## 8. 段階計画

**元の計画（`00` §8）からの変更点**: MR を M5 から **M3** に前倒しする。理由:
GitHub / GitLab の中核はコードレビューであり、LLM によるマージ検証と kanflow 連携は
どちらも MR を前提にするため。SSH は M3 から M4 に移す（HTTP + トークンで運用を始められる）。

| 段階 | 内容 | 完了条件 |
|---|---|---|

## 9. 非機能要件

| 項目 | 目標（仮） |
|---|---|
| clone / push の性能 | 1 GB のリポジトリの clone が、素の `git daemon` と比べて 1.2 倍以内の時間で終わる |
| API の応答 | 一覧系は p95 で 300 ms 以内（LLM を含む処理は非同期にする） |
| 可用性 | 業務時間中 99.5 %。計画停止は事前に告知する |
| 復旧 | RPO 24 時間（日次バックアップ + WAL で短縮を検討）、RTO 4 時間。手順は Runbook に書き、訓練する |
| セキュリティ | すべての経路で認可を行う。トークンはハッシュで保存する。シークレットは暗号化して保存する。監査ログを残す |
| 観測性 | すべての失敗にエラーコードと `request_id` を付ける。ログは JSON、メトリクスは Prometheus 形式 |

## 10. リスク

| リスク | 対策 |
|---|---|
| 範囲が大きすぎて完成しない | リリース単位（R1〜R3）で価値を出す。Won't を明示し、M8 は需要で選ぶ |
| LLM の指摘の質が低く、使われなくなる | 助言から始める。評価セットと採用率で測ってから改善する。指摘の数を絞る |
| GPU の混雑で kanflow が遅くなる | forge 側で同時実行数を制限し、優先度を付ける。待ち時間を監視し、専用 GPU の判断に使う |
| Office 文書の差分が難しい | 本文の抽出による差分と、LLM による要約を組み合わせる（kanflow の抽出器の考え方を流用） |
| kanflow 側の改修が必要になる | 必要な改修は `02` §8 に列挙した。kanflow の計画と同期する |
| Git のプロトコル実装の不具合 | 自前で実装せず、`git` バイナリを実行する（CLAUDE.md §3-5）。実際のクライアントで結合テストを行う |

|---|---|---|
| 1 | 規模 | §2 の仮置き（開発者 50〜300 人、リポジトリ 〜2,000 個）で設計する |

以下は確定前の質問（記録として残す）。

1. **利用者数とリポジトリの規模**: §2 の仮置き（開発者 50〜300 人）で良いですか？
2. **認証**: 社内 AD / LDAP と連携しますか？ kanflow のユーザーとは email（または社員番号）で突き合わせて良いですか？
3. **権限モデル**: GitLab 型（グループ → プロジェクトの階層、5 段階のロール）で良いですか？
