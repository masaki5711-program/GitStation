- 作成日: 2026-10-26

## 1. 前提 — AI で開発が速くなると、何が起きるか

forge の根幹の目的は AI によるシステム開発の加速（`03`）。開発が速くなると、次のことが起きる。

| 起きること | 結果 | 本書での対策 |
|---|---|---|
| 同時に開いている MR が増える | **MR 同士の衝突** が増える | 衝突の検出と早期の予測（§2） |
| マージの頻度が上がる | テキストとしては衝突しないが、**組み合わせると壊れる変更**（意味的な衝突）で main が壊れる | マージ結果でのパイプライン、マージキュー（§3） |
| AI エージェントが push とパイプラインを繰り返す | 失敗の原因を人が読んで伝えていては遅い | **機械が読める失敗の診断**（§4.3）と、push の前の自己確認（§4.1） |
| パイプラインの定義も AI が書く | 危険な設定（シークレットの露出など）が紛れ込む | 定義の決定的な検査と LLM による確認（§4.1、§4.2） |

**方針**: 判定は決定的な仕組み（git、テスト、ルール）で行い、LLM は解消案と診断の補助に使う
（`01` §6.1 と同じ）。

## 2. コンフリクト（衝突）

### 2.1 機能

| # | 機能 | 内容 | 優先度 | 段階 |
|---|---|---|---|---|
| C-1 | **マージ可否の判定** | MR の更新時と、対象ブランチが進んだときに、worker が `git merge-tree --write-tree` で **作業ツリーなしに** マージを試し、「マージ可 / 衝突（ファイルと箇所）/ 判定不能（エラーコード付き）」を記録する | Must | M3 |
| C-2 | **MR 同士の衝突の予測** | 同じブランチに向けて開いている MR の組について、まず変更ファイルの重なりで絞り（安価）、重なる組だけ `merge-tree` で試す。「この MR は !88 と衝突する見込み」を **両方の作成者と kanflow** に知らせる | **Must** | **M3**（`06` §4.4） |
| C-3 | **リポジトリをまたぐ順序** | 1 つの PBI の MR セット（`02` F-24）で、マージの順序（例: 基盤 → アプリ）を指定し、順序に反するマージを警告する | Should | M4 |
| C-4 | **AI による解消案** | 両側の差分と、両方の MR の PBI・受入基準・要件（`03`）を文脈にして、LLM が解消案を作る。**別ブランチ `conflict/<MR>-<n>` のコミットとして提案** し、そのブランチでパイプラインを通す。適用は人間が承認する | Should | M5 |
| C-5 | **機械的に解消できる衝突** | ロックファイル（`Cargo.lock`、`package-lock.json` など）や生成ファイルは、LLM に任せず **再生成のコマンド** で解消する（プロジェクトの設定でコマンドを登録） | Should | M4 |

### 2.2 C-4 の安全策

- テキストの衝突だけを対象にする。バイナリ、マイグレーション、権限まわりのファイル（設定で指定）は
  提案しない。
- 解消案には、どちらの変更をどう組み合わせたかの説明と、**参照した要件 ID** を付ける。
- 解消案のブランチでパイプラインが失敗したら、提案を取り下げ、失敗の診断（§4.3）を付ける。
- 失敗（LLM の応答なし、出力の不正）は `FG-LLM-xxxx` で記録し、MR には「解消案を作れなかった」と表示する。

### 2.3 イベント（`02` §5.8 に追加）

`merge_request.conflict_detected`（衝突が発生した。相手が MR なら相手も記録）、
`merge_request.conflict_resolved`、`merge_request.conflict_predicted`（C-2）。
kanflow の「開発」タブに「衝突あり」と表示できる。

## 3. main を壊さない仕組み

| # | 機能 | 内容 | 優先度 | 段階 |
|---|---|---|---|---|
| M-1 | **マージ結果でのパイプライン** | MR のパイプラインを、ソースブランチではなく **「ソース + 対象ブランチ」のマージ結果** で実行する（`refs/merge-requests/<iid>/merge`）。意味的な衝突の多くはここで見つかる | Must | M4 |
| M-2 | **チェックの鮮度** | 対象ブランチが進んだら、それより前のマージ結果で出たチェックを「古い」と表示する。必須チェックが古いときにマージを止めるかは、保護ブランチの設定で選ぶ | Must | M4 |
| M-3 | **マージキュー** | マージの承認が済んだ MR を順に並べ、**前の MR を含めたマージ結果** でパイプラインを実行し、成功したものだけをマージする。複数の MR をまとめて試し、失敗したら二分して原因の MR を特定する | **Should（`01` では Could / M8 → 前倒し）** | M4 |
| M-4 | **main が壊れたときの対応** | main のパイプラインが失敗したら、原因のコミット（MR）を特定し、作成者と kanflow に知らせる（`02` F-12）。**revert の MR を自動で下書き** する（マージは人間） | Should | M4 |

| M-5 | **自動マージ（プロジェクトごとに選ぶ）** | 2026-10-30 のユーザーの決定: 「条件付きの自動マージ」と「すべて自動マージ」の **両方を選べるようにする**。設定は `merge.auto` 1 つで、`off` / `reserve` / `conditional` / `full` から選ぶ（下の表） | Must | M4 |

**M-5 の 4 つの方式**

| 方式 | AI が MR を通る状態にした後 | 人間の関与 |
|---|---|---|
| `off` | 何もしない | 人間がマージする |
| `reserve`（既定。ADR-0017 の決定 10 D） | 人間が「承認してマージを予約」すると、CI が緑になった時点で GitStation が本人としてマージする | 予約の 1 回 |
| `conditional` | 下の共通の条件 + AI の仕様照合の承認がそろえば、GitStation が自動でマージする。ただし **保護するパス**（認証・権限、DB のマイグレーション、CODEOWNERS で指定したパス、`.forge/` の設定）に触れる MR は人間の承認を待つ | 保護するパスだけ |
| `full` | 下の共通の条件 + AI の仕様照合の承認がそろえば、パスの例外なく自動でマージする。AI による衝突の解消（C-4）や自動修正（ADR-0017）のコミットも、条件を満たせばそのままマージされる | なし |

- **すべての自動の方式に共通の条件**: マージキュー（M-3）で **前に並ぶ他の MR を含めたマージ結果** のパイプラインが緑、決定的な必須チェックがすべて緑で新しい（M-2）、head の SHA が検証した SHA と同じ、緊急停止が掛かっていない、MR が下書きでない。
- **実行者**: マージは GitStation のサーバーの「自動マージ」の主体が、プロジェクトの設定に基づいて行う。AI のトークン（`is_agent`）自身にはマージの権限を与えない（ADR-0017 §4.0 のまま）。監査とイベントには、方式、AI の承認、通った条件、キューでの位置を残し、kanflow に知らせる。
- **設定できる人**: `reserve` / `conditional` はプロジェクトの Maintainer。`full` は、インスタンスの管理者が許可（`merge.allow_full_auto`）したうえで、プロジェクトの Owner が有効にする。変更は監査に残す。
- **変えないこと**: prod へのデプロイは人間の承認が必須（§5）。main が壊れたときは M-4 で原因を特定し、revert の MR を自動で下書きする（`full` のプロジェクトでは revert の MR も自動マージの対象にできる）。
- **緊急停止**: インスタンス全体とプロジェクトごとに、自動マージを即座に止められる（`gstn mr queue pause` と管理画面）。
- **危険の検査（M-6）が `stop` の MR は、どの方式でも自動マージしない**。
- **マージの順序（2026-10-30 のユーザーの決定: AI の提案 + 規則で検査）**: ローカル LLM がキューの順序を提案し、決定的な規則を満たす範囲で
  自動で適用する。**規則（破れない）**: MR 間の宣言された依存（A が B に依存するなら B が先）、DB のマイグレーションを含む MR は 1 本ずつ・番号順、
  危険の検査の `stop` は通さない、パイプラインは前に並ぶ MR を含めたマージ結果で回す。**LLM が考慮するもの**: 衝突の予測（C-2）で
  ぶつかる MR のどちらを先にすると直す手間が少ないか、他を止めている小さく安全な MR の優先、kanflow の PBI の優先度とスプリントの期限。
  提案の理由は監査とイベントに残し、kanflow に届ける。LLM が使えないときは承認順（FIFO）+ 規則で進める（止めない）。
  順序を変えても検査は省かれず、失敗したら二分で原因の MR を特定する。差分の文で順番を操作されないよう、LLM の提案は規則の検査を通ったものだけを使う。

### M-6 危険の検査（`forge/risk`）— 個人情報の流出と DB の破壊は警告付きで止める

**2026-10-30 のユーザーの要望**: 「ちょっとしたエラーの完全自動マージは構わないが、個人情報流出や DB が消えて破壊するような場合は警告付きでストップ
してくれるようにしたい。そのチェックを Claude Code での CLI でのチェック、そしてローカル LLM での自動マージで行えるようにしたい」。
設計の決定は ADR-0017 の Amendment（2026-10-30）F。

| 結果 | 意味 | 自動マージ |
|---|---|---|
| `ok` | 危険は見つからない | 方式（M-5）のとおり |
| `warn` | 注意が要る（認証・権限、本番の設定、長いロックを取るマイグレーションなど） | 方式のとおり進むが、警告を MR・`gstn`・kanflow に残す |
| `stop` | **個人情報・機密の流出、DB の破壊・データの消失** | **`full` を含むすべての方式で止める**。理由と根拠の行を付けた警告を出し、人間の承認を待つ |

**2 層で判定する（AI は危険を上げることしかできない）**

| 層 | 実行する場所 | 内容 |
|---|---|---|
| 1. 決定的な規則 | サーバーと `gstn`（同じ実装） | 当たったら `stop`。AI の判定で下げられない（プロンプトインジェクションの影響を受けない） |
| 2. ローカル AI | サーバー（LLM ゲートウェイ、Qwen） | 差分・PBI・関連する仕様から、規則で拾えない流出・破壊の危険を分類する。根拠の行を付けた JSON を返し、`warn` / `stop` に上げることだけができる。応答なし・タイムアウト・出力の不正は `stop`（黙って `ok` にしない） |

**規則の例（既定で入れる。プロジェクトは `.forge/risk.yml` で足せるが、既定の規則を外すには Owner の承認が要る）**

| 分類 | `stop` になる変更の例 |
|---|---|
| DB の破壊 | マイグレーションの `DROP TABLE / COLUMN / SCHEMA / DATABASE`、`TRUNCATE`、`WHERE` のない `DELETE` / `UPDATE`、列の型の変更・改名、一意制約や外部キーの削除、トリガーの無効化、**適用済みのマイグレーションの変更**、バックアップ・復元・保持期間・削除のジョブの変更、デプロイの手順での巻き戻し（`migrate revert` など） |
| 個人情報・機密の流出 | 個人情報の列（メール、氏名、社員番号、電話、住所など。プロジェクトで列名を登録）をログ・API の応答・読み取り用のロールに出す変更、伏せ字の処理の削除、新しい外部の送り先、ルートの認証・認可の検査の削除、リポジトリ・プロジェクトの公開範囲を広げる変更、秘密情報らしき文字列、実在らしき個人情報を含むテストデータ |

- **解除**: プロジェクトの Maintainer 以上が、警告を読んだことを明示して承認する（承認に警告の ID を残す）。AI のトークン、サービスアカウント、自動マージの主体は解除できない。
- **Claude Code から**: `gstn risk check`（push の前の手元の差分）、`gstn mr risk <MR>`（サーバーの判定と根拠）。Claude は push の前に自分で確かめられ、
  `stop` のときは理由を読んで直すか、人間に判断を求める。
- **kanflow へ**: `warn` / `stop` と解除は、イベントとして kanflow のプロジェクトにリアルタイムで届く（`02` §5.9）。
- **測る**: 危険な差分の評価セットを持ち、見逃しは評価のケースとして足す。検出率と誤検知率を、`conditional` / `full` を有効にする画面に出す。
- **時期**: 決定的な規則は **M3**（Checks API と同時。`gstn` からも使える）。AI の層は LLM ゲートウェイ（M3 と並行して作り始める）。
  **`conditional` / `full` は、2 層の両方が動いてからでないと選べない**。

**M-3 を前倒しする理由**: AI で MR の数が増えると、M-1 だけでは「両方とも単独では成功したが、
続けてマージしたら壊れた」が頻繁に起きる。マージキューはこれを構造的に防ぐ。

## 4. パイプラインの検証

### 4.1 push の前・MR の時点での決定的な確認

| # | 機能 | 内容 | 優先度 | 段階 |
|---|---|---|---|---|
| P-1 | **定義の検査**（`forge/ci-lint`） | `.forge-ci.yml` を、スキーマ、DAG の循環、存在しない `needs`、タイムアウトの未設定、イメージのダイジェスト固定、**シークレットを保護されていないブランチで使っていないか** などで検査する | Must | M4 |
| P-2 | **実行計画の表示**（`forge ci plan`） | この変更でどのジョブが走るか（ルールの評価結果）を、実行せずに表示する | Should | M4 |
| P-3 | **ローカルでの自己確認** | P-1 と P-2 を CLI（`forge ci lint` / `forge ci plan`）と API で提供する。**AI エージェントが push する前に自分で確認** でき、無駄なパイプラインの実行を減らす | Must | M4 |

### 4.2 LLM による確認

| # | 機能 | 内容 | 優先度 | 段階 |
|---|---|---|---|---|
| P-4 | **定義の変更のレビュー**（`01` L-6） | P-1 で拾えない意図の問題（例: デプロイの条件が広がった、テストのジョブが実質的に無効になった）を指摘する。**P-1 を先に実行** し、その結果を LLM に渡す | Must | M5 |
| P-5 | **デプロイ前の確認**（`01` L-9） | 本番デプロイの承認画面に、前回のデプロイからの変更の要約、関わる PBI と要件、リスクを表示する | Should | M5 |

### 4.3 失敗の診断 — AI エージェントが自分で直せるようにする

| # | 機能 | 内容 | 優先度 | 段階 |
|---|---|---|---|---|
| P-6 | **失敗の指紋** | 失敗したジョブのログから、時刻やパスなどの変わる部分を除いた **指紋** を作り、同じ失敗をまとめる（決定的） | Must | M4 |
| P-7 | **失敗の記憶** | 指紋と、過去にその失敗を直した MR を結びつけて記録する（エージェントモデルの mistake-memory を製品の機能にしたもの）。同じ指紋の失敗が起きたら、過去の直し方を示す | Should | M4 |
| P-8 | **LLM による診断**（`01` L-7） | 指紋で既知の直し方が見つからないときに、ログの要点、エラーコード、直近の変更から原因の候補と対処を示す | Must | M5 |
| P-9 | **診断の API** | 診断の結果を **機械が読める形** で返す（下の例）。AI エージェントはこれを読んで修正し、再び push する | Must | M4（決定的な部分）/ M5（LLM の部分） |
| P-10 | **不安定なテストの検出と隔離**（`01` L-8） | 同じコミットで成功と失敗を繰り返すテストを統計で検出する。隔離（失敗してもパイプラインを止めない）は **期限付き** にし、kanflow の Icebox に修正の項目を作る | Should | M5 |

```json
// GET /api/v1/pipelines/{id}/diagnosis
{
  "pipeline_id": "pl_…",
  "status": "failed",
  "failures": [{
    "job": "test", "step": "cargo nextest run",
    "fingerprint": "fp_7c1e…",
    "error_codes": ["FG-DB-0003"],
    "excerpt": "test reload_within_10s ... FAILED (timeout after 10s)",
    "source": { "log_url": "…", "lines": [812, 840] },
    "known_fixes": [{ "merge_request": "app/portal!61", "summary": "テスト用 DB の接続プールの上限を上げた" }],
    "llm_hypotheses": [{ "cause": "…", "confidence": "medium", "suggested_fix": "…" }],
    "requirements": ["ZEVA-CFG-012"]
  }],
  "as_of": "2026-10-26T10:20:00+09:00"
}
```

- `known_fixes`（決定的）と `llm_hypotheses`（推測）を **分けて返す**。AI エージェントと人が、
  確かな情報と推測を区別できるようにする。
- 失敗したテストに `@req` があれば、関わる要件を返す（`03` §4.3）。

## 5. CI/CD の基本設計（`01` §3.4 の詳細）

| 項目 | 方針 |
|---|---|
| Runner | 別ホストで動き、forge にジョブを取りに来る（外から接続を受けない）。登録はトークン、ジョブごとに短命のトークンを発行する |
| 隔離 | ジョブごとに使い捨てのコンテナ（rootless の Podman / Docker）。ジョブの間で状態を残さない（キャッシュは明示的に指定したものだけ） |
| ジョブのトークン | そのプロジェクトだけ、そのジョブの実行中だけ有効。成果物の取得と、依存するリポジトリの読み取りに限る |
| シークレット | 暗号化して保存する。保護ブランチと保護された環境のジョブにだけ渡し、ログでマスクする |
| タイムアウト | すべてのジョブとステップにタイムアウトを設ける（CLAUDE.md §3-2）。既定値はプロジェクトの設定 |
| 環境とデプロイ | dev / stg / prod。**prod へのデプロイは人間の承認が必須**。凍結期間を設定でき（`02` F-32）、期間中は警告する |
| デプロイの確認 | デプロイ後にヘルスチェックを実行し、失敗したら **決定的なルールで自動ロールバック** する（設定で有効にした環境のみ）。結果は kanflow に届ける（`02` F-34） |
| デプロイの方式 | 最初は SSH（`DeployTarget` trait、`01` §5）。デプロイ先の鍵は forge の外に出さない |
| 観測性 | パイプライン、ジョブ、デプロイのすべての失敗に、エラーコード（新しい領域 `CI`、`DEPLOY`）と `request_id` を付ける |

## 7. 段階計画への反映
