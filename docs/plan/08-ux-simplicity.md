# 08 複雑な流れを、使う人には簡単に見せる（UI / UX の方針）

作成: 2026-10-31（クラウドのセッション）。ユーザーの指示:「結構複雑なフローになっているが、UI 側でなんとかユーザーに使いやすいように検討してほしい」。

対象は `07-team-vibe-coding.md`（W1〜W12）と `02` / `04` / `06` の流れ全体。GitStation の画面は M2、Kanflow の画面は今の ui-kit（`docs/ui-kit.md`）で作る。ロゴとアイコンは `docs/brand/` のファイルを使う。

## 1. 原則

1. **仕組みは裏で動かし、人には「次にやること」だけを見せる。** 作業の宣言、生存確認、イベント、教訓の照合、出力は自動。画面に出すのは、人が判断・入力する所だけ。
2. **入口は 1 つ（Kanflow）。** 誰でも Kanflow から始める。コードや仕様の中身は GitStation の画面へ深いリンクで移り、戻るリンクも必ず付ける。ログインは 1 回（Keycloak の SSO、`platform-integration-iotpf.md` §4）。
3. **人の判断は「承認待ち」の 1 か所に集める。** 計画の承認、仕様の承認、危険（stop）の解除、PO の完了の確定、本番の承認を、どの製品から来たかに関係なく 1 つの一覧で処理する。
4. **役割とプロジェクトの種類で、見せるものを変える。** 開発用の機能は `software` だけ。設備導入・工程改善では仕様書・決めるべき項目・全体計画・段の完了の条件だけ。
5. **Git の言葉を、Git を知らない人に見せない。** 下の言い換えの表を UI の文言の規則にする（i18n の辞書で管理し、ja / en / id）。
6. **少しずつ見せる。** 最初は要約の 1 行。詳しく知りたい人だけが開く（差分、ログ、教訓の根拠）。
7. **止まっている理由を、いつも 1 行で言う。** 「何を待っているか」「誰が」「次に押すボタン」。

### 言い換え（Git を知らない人向けの表示）

| 内部 | 画面の言葉 |
|---|---|
| リポジトリ（spec） | 仕様書 |
| MR / マージ | 変更の申請 / 反映 |
| タグ / 版の公開 | 版を確定 |
| ブランチ | 作業中の版 |
| パイプライン / CI | 自動チェック |
| stop（危険の検査） | 要確認の変更 |
| 作業の宣言（claim） | 担当中 |
| 教訓（lesson） | 過去の対策 |

## 2. 使う人ごとの「ホーム」

| 使う人 | ホームに出すもの | 主に使う所 |
|---|---|---|
| PO / PM | 承認待ち、プロジェクトごとの「今どこ」（段の表示）、遅れと詰まり、完了の候補 | Kanflow |
| 開発者 | 自分の担当中、チームの担当中（ボード）、自分の変更の申請の状態、過去の対策の通知 | Claude Code（CLI）＋ Kanflow のボード |
| 設備・工程の担当 | 自分の仕様書と未決定の項目、全体計画の自分の担当、段の完了の条件の抜け | Kanflow ＋ 文書ポータル |
| 承認者（技術者以外を含む） | 承認待ちだけ（要約・変わった所・承認 / 差し戻し） | Kanflow（スマホでも使える） |
| チームリーダー | 衝突の警告、詰まり、流れの数値（07 §2） | Kanflow のダッシュボード |

## 3. 主な画面

### 3.1 プロジェクトを始める（3 ステップのウィザード）
1. 種類を選ぶ（システム開発 / 設備導入 / 工程改善 / その他）→ 合うベースのリポジトリが自動で決まる（説明付き）
2. 名前・開始日・メンバー
3. 確認: 作られるもの（仕様書、全体計画の案のガントチャートのプレビュー、決めるべき項目の数）→「作成」

裏で、仕様のリポジトリの作成、結び付け、全体計画の案の作成が走る。失敗したら、どこで止まったかと「やり直す」ボタンを出す（`request_id` 付き）。

### 3.2 プロジェクトの「今どこ」（段の表示）
- 一番上に段の帯: **計画 → 仕様 → 実装（または 調達・据付）→ 確認（検収）→ 完了**。今の段が光り、各段に「残り n 件」。
- その下に「止まっている理由」1 行と、次のボタン（例:「支払い条件が未決定です — 仕様書を開く」）。
- 全体計画のガントチャートは、ベースのスケジュールとのずれを色で出す。

### 3.3 仕様書の画面（設備・工程・システム共通）
- 左: 章の目次。右: 本文（Markdown を整形して表示。Git を知らない人は編集もここ、または Claude Code）。
- 上: **決めるべき項目の進み具合**（例「24 項目中 21 決定、必須の未決定 2」）。未決定の項目をクリックすると該当の章へ。
- ボタン: 「Claude と続ける」（Claude Code で開くコマンドをコピー、または Web の AI チャット）、「Word / Excel / PDF で出力」、「承認に回す」（必須の未決定があると押せず、理由を出す）。
- 版の履歴: 「版 1.2（承認: 〇〇、日付）」の一覧と、版どうしの違い（文書の差分を見やすく）。

### 3.4 承認待ち（全製品で 1 つ）
- カード 1 枚 = 判断 1 つ。種類のアイコン（計画 / 仕様 / 要確認の変更 / 完了の確定 / 本番）。
- カードの中身: AI の要約 3 行（ローカル LLM）、変わった所（要約 → 開くと差分）、根拠（AC の対応表、自動チェックの結果、危険の検査の理由）、「承認」「差し戻し（理由は必須）」。
- 期限と、遅れると誰が待たされるかを表示。通知はまとめて（1 日 2 回のダイジェスト、急ぎだけ即時）。

### 3.5 PBI の画面（システム開発）
- 段の帯（計画 → 実装 → 申請 → 反映 → 完了の確定）と「止まっている理由」1 行。
- 受入基準のチェックリスト: 項目ごとに証拠のアイコン（テスト ✓ / 検査記録 / 測定値 / 承認）。証拠がない項目は灰色。
- 担当中: 人のアイコン + AI のアイコン + ブランチ（開発者だけに見せる）。衝突の警告はここに 1 行。
- 変更の申請と自動チェックの状態は、GitStation への深いリンク付きの 1 行。

### 3.6 ボード（スプリント）
- カードに担当中の印（人と AI、色で「動いている / 間もなく失効 / 失効」）。触る範囲が重なるカードの間に警告の線。
- フィルタ:「自分」「AI が担当」「止まっている」。

### 3.7 過去の対策（フィードバックの輪）は「探しに行かせない」
- 失敗した自動チェックの画面、PBI の画面、Claude Code の出力に、当たった対策を **その場で 1 行** 出す（「似た失敗 3 件、対策: …」→ 開くと根拠）。
- 教訓の一覧の画面は、確認する人（Maintainer / SM）と週の要約のためだけ。

## 4. 複雑さを隠すための裏の決まり

- 自動の処理は失敗しても画面を止めない。失敗は「要対応」としてホームの 1 か所に出し、直すボタンか、誰に頼むかを出す（`request_id` 付き。エラーの契約の `user_message`）。
- 同じ情報を 2 か所で入力させない（ベースのスケジュール → 全体計画、MR → PBI のリンク、テスト → AC の証拠は自動）。
- 用語・色・状態の表示を、Kanflow と GitStation で同じにする（共通のデザイントークン。色は `docs/brand` の値が起点）。
- 確定を戻せる操作は「元に戻す」を出し、戻せない操作（版の確定、本番）だけ確認のダイアログを出す。

## 5. 確かめ方（使いやすさの完了の条件）

| 使う人 | 課題 | 目標 |
|---|---|---|
| 承認者（技術者以外） | 仕様の承認を 1 件 | 説明なしで 2 分以内 |
| 設備の担当 | 設備導入のプロジェクトを作り、仕様の未決定の項目を見つける | 5 分以内 |
| PO | 「今どこで、何で止まっているか」を答える | ホームから 1 クリック |
| 開発者 | 誰が何を担当中か、衝突しそうな作業はどれか | ボードを見るだけ |

各役割から 2〜3 人で、作ったら毎回この課題を試す（画面の録画と、迷った所の記録）。迷った所は Kanflow の PBI にする。

## 6. 順序

| 段 | 内容 |
|---|---|
| 第 0〜1 段（Kanflow、今の ui-kit） | ボードの担当中の印（W3）、プロジェクトの「今どこ」と止まっている理由、承認待ちの一覧（Kanflow の中の承認から）、プロジェクトのウィザード（種類とベースのスケジュール）、過去の対策のその場の表示 |
| 第 2 段（GitStation M2 と一緒に） | 仕様書の画面と文書ポータル、言い換えの辞書、承認待ちに GitStation の承認を合流、共通のデザイントークン、SSO |

担当のエージェント（エージェントモデル）: 設計は `frontend-design`、i18n は `ui-i18n-gate` と `i18n-sync-auditor`、見た目は `design-reviewer`、アクセシビリティは `a11y-architect`、操作の確認は `e2e-runner`。
