## 1. 目的の理解

ユーザーの意図を、次のように理解した。違っていれば、最初に直してほしい。

1. **計画から本番まで一気通貫**: kanflow で決めた「やりたいこと」が、人が手で渡さなくても、実装、検証、デプロイまで流れる。
   人は **意図を伝える、判断する、承認する** ことに集中する（バイブコーディング）。
2. **3 つの道具が 1 つの環境として働く**:
   - **kanflow** = 何を作るか（PBI、受入基準、スプリント、優先度）。エンジニア以外も使う入口。ローカル LLM で計画を手伝う。
   - **GitStation** = 作ったものの置き場所と関所（リポジトリ、MR、CI、検証、マージ、デプロイ）。社内で完結する。
   - **Claude Code + エージェントモデル** = 実際に作る手（開発者の PC）。チームの規則、レビュー役、記憶を共有する。
3. **複数人で 1 つのプロジェクト**: 1 人の開発者が複数の AI を走らせ、さらに複数の開発者が同じリポジトリで同時に進めても、衝突や取りこぼしで遅くならない。
4. **これまでの価値観を保つ**: 社内で完結（データ主権）、マージと本番は人が承認、決定的な検査（フック、ゲート）を指示より優先、失敗はエラーコードから診断できる、効果は計測して確かめる。
5. **GitLab でできなかった連携** をする（02 §1）。

## 2. 今の姿と、つながっていない箇所

```
 kanflow ──(180 秒ごとに読むだけ)──> GitLab <──(glab CLI)── Claude Code + エージェントモデル
   │  PBI・受入基準・AI 提案                 MR・CI                    PBI 番号は人が手入力
   └──────────────────── 直接のつながりなし ──────────────────────────┘
```

| # | 箇所 | 今の状態 | 根拠 |
|---|---|---|---|

| G-2 | Claude → kanflow | 進み具合は、ブランチ名と MR のタイトルの PBI 番号を kanflow が **定期取得で拾うだけ**。`PBI #43` の書き方は拾えず、上限を超えた分は二度と取れない | 02 §8.4 |
| G-3 | kanflow の AI → 実装 | kanflow の AI は提案だけで、コードや MR は作らない。タスク分解（`propose_task_split`）と Claude の計画は別々 | 02 §8.4 |
| G-4 | 受入基準 → テスト | 受入基準は 1 つのテキスト。テストとの対応は取っていない。GitStation の `spec-trace` は M4〜M5 の予定 | K-6、03 §5.1 |

| G-9 | ローカル LLM | GPU 1 台を kanflow、検証、自動修正で共有（同時 2 件）。チームの人数と MR の数が増えると、ここが詰まる | K-8、ADR-0017 §3 |

**いちばん大きい問題は G-1 と G-5**。実装の主役は開発者の PC の Claude だが、今の計画では Claude が kanflow と GitStation の **外側** にいる。
計画から実装までを一気通貫にするには、Claude を **両方の正式な利用者（役者）** にする必要がある。

## 3. AI 企業のやり方から取り入れること

公開情報（§9）のうち、この環境に移せるものを選んだ。

| # | やり方 | 出典 | この環境での形 |
|---|---|---|---|
| A-1 | **チケット = 指示文**。チケットを AI に任せると、ブランチと下書きの MR ができる。担当者は人のまま、AI は協力者 | GitHub Copilot coding agent、Linear | kanflow の PBI / タスクから Claude のセッションを始める（§4.1） |
| A-2 | **仕様 → 計画 → 小さなタスク → 実装** を、ファイルとして残す | GitHub Spec Kit、AWS Kiro、Anthropic のベストプラクティス | kanflow の受入基準 → Claude の実装計画 → タスク（§4.2） |
| A-3 | **受入基準を先に失敗するテストにする**。「完了」は AI の申告ではなく、テストとゲートが決める | Anthropic のベストプラクティス、Anthropic 社内の TDD | 受入基準に ID を付け、テストに `@req` で結びつける（§4.3） |
| A-4 | **例外のない規則はフックで強制し、文章は短く** | Anthropic のベストプラクティス | エージェントモデルの方針そのもの。チームで 1 つに統一する（§4.8） |
| A-5 | **並列の作業は、作業ごとに worktree かサンドボックス**。こまめにコミットして戻れるようにする | Anthropic 社内、Claude Code on the web、Codex | 1 タスク = 1 worktree = 1 ブランチ。所有ファイルで分ける（§4.4） |
| A-6 | **人より先に、複数の AI が読むだけのレビュー** をし、重さ順に並べる。AI は承認しない | Anthropic Code Review（実質的な指摘のある PR が 16% → 54%） | エージェントモデルの評価役 + ローカル LLM のチェック（§4.6） |
| A-7 | **レビューの詰まりを構造で減らす**: 小さい MR、積み重ねた MR、マージキュー、危険度で深さを変える | GitHub、Graphite、Mergify | §4.6 |
| A-8 | **AI が読める文脈の API を MCP で出す** | Anthropic（MCP）、AGENTS.md | kanflow と GitStation の MCP サーバー（§4.1、§4.5） |
| A-9 | **AI だけで動かす前の 5 つの問い**: 完了の判定、自己検査、触ってよい範囲、止める条件、承認者 | Anthropic のベストプラクティス | 自動で走らせるときの共通の型（§4.7） |
| A-10 | **計測する。思い込みで判断しない** | DORA 2025、METR（熟練者が AI で 19% 遅くなったのに、20% 速いと感じていた） | 流れの計測（§4.9） |

DORA 2025 の結論は「AI は、組織に今ある強みも弱みも増幅する」である。速さは AI の性能より、**流れ（受け渡し、検査、レビュー、デプロイ）の詰まりの少なさ** で決まる。
この提案の中心も、AI を足すことではなく、**3 つの道具の間の受け渡しをなくすこと** に置く。

## 4. 提案

### 全体像

```
 ┌─ kanflow ───────────────┐   MCP / API    ┌─ 開発者の PC ─────────────────────────┐
 │ PBI・受入基準(ID付き)    │ ─────────────> │ Claude Code + チームのエージェントモデル │
 │ タスク・担当・作業中の表示 │ <───────────── │  /pbi 123 → 計画 → テスト → 実装       │
 │ ローカル LLM: 下書き・分割 │  状態・進捗     │  worktree をタスクごとに 1 つ          │
 └──────────▲──────────────┘                └──────────────┬────────────────────────┘
            │ イベントの履歴（カーソル）                          │ push・MR（エージェントのトークン）
 ┌─ GitStation ────────────┴─────────────────────────────────▼───────────┐
 │ MR・チェック（spec-trace、AI レビュー、ローカル LLM の受入基準照合）・衝突の予測 │
 │ マージキュー・プレビュー環境・デプロイ・文脈 API / MCP・チームの知識          │
 └───────────────────────────────────────────────────────────────────────┘
```

### 4.1 PBI からセッションを始める（G-1、G-2、A-1、A-8）

- **kanflow の MCP サーバー**（エージェントモデル側）を作る。中身は kanflow の既存の `/api/v1` を呼ぶ薄い層。
  - 読む: PBI、受入基準、タスク、コメント、添付、関連 PBI、スプリント。
  - 書く（新しいスコープ `write:dev`）: タスクを「作業中（誰の、どのセッション）」にする、進捗のコメント、MR へのリンク。
  - kanflow の原則（AI は提案し、人が承認して書く）に合わせ、**状態を大きく変える操作（PBI の完了など）は提案として出し、人が kanflow で承認する**。
- **コマンド `/pbi <番号>`**（エージェントモデル）:
  1. PBI と受入基準を読み、足りない点（受入基準がない、曖昧）を開発者に聞き返す。
  2. タスクを「作業中」にし、ブランチ `feat/L<layer>-PBI-<n>-<topic>` と worktree を作る（番号の手入力をなくす）。
  3. 実装計画（§4.2）を作り、開発者の承認を待つ。
  4. 下書きの MR を **早めに** 作る（衝突の予測と「作業中」の表示のため）。
- **kanflow の不具合を先に直す**（小さく、効果が大きい）: PBI 番号の正規表現が `PBI #43` に一致しない件と、取得の上限を超えた分を二度と取らない件（02 §8.4）。

### 4.2 計画を 1 本にする（G-3、A-2）

- 計画の流れを **PBI（何を・なぜ・受入基準）→ 実装計画（どう作るか）→ タスク（小さく、単独でテストできる）** に固定する。
- **役割の分担**:
  - kanflow のローカル LLM: PBI の下書き、受入基準の候補、INVEST のレビュー（今あるもの）。社外に出せない情報を扱える。
  - Claude（エージェントモデルの `planner`）: リポジトリを読んで実装計画とタスク分割を作る。**触るファイルやモジュールをタスクごとに書く**（§4.4 の衝突回避に使う）。
- 実装計画は kanflow の PBI に添付し、タスクは kanflow の `propose_task_split` と同じ「提案 → 承認」の形で登録する。計画が 2 か所に分かれないようにする。

### 4.3 受入基準を、ID 付きの検査できる形にする（G-4、A-3）

- kanflow の受入基準を **項目ごと** にし、安定した ID（例: `PBI-123/AC-2`）を付ける。書き方は「〜のとき、〜する」（EARS か Given-When-Then）にそろえる。
  今のテキストからは、アダプタで分割してもよい（02 の K-6 の方針）。
- Claude は、受入基準ごとに **先に失敗するテスト** を書き、`@req PBI-123/AC-2` で結びつける。
- GitStation の `spec-trace` チェックを、kanflow の受入基準にも使えるようにし、**時期を M3 に早める**（受入基準ごとに、対応するテストがあり、通っているか）。
  ローカル LLM の受入基準の照合（L-3、`spec-conformance`）は、その上に重ねる助言とする。
- 「完了」は、受入基準のすべてにテストがあり、通り、レビューを通ったこと、と機械で判定する。

### 4.4 複数人・複数の AI での並行作業（G-6、A-5）

| 仕組み | 内容 | どこで |
|---|---|---|
| **作業の宣言** | タスクを始めると「誰が、どのセッションで、どのブランチで」作業中かが kanflow のボードに出る。同じタスクを 2 人（2 つの AI）が始めると警告する | kanflow（`write:dev` スコープ） |
| **触る範囲の宣言** | 実装計画に書いた「触るファイルやモジュール」を、作業の宣言と一緒に登録する。範囲が重なるタスクを、計画の時点で知らせる | kanflow + エージェントモデル |
| **早い衝突の予測** | 下書きの MR やブランチが push されるたびに、開いている他のブランチとの衝突（テキストの衝突と、同じファイルの変更）を計算し、両方の作者と kanflow に知らせる。04 の C-2 を **M4 → M3** に早める | GitStation |
| **小さい MR と積み重ね** | 1 タスク = 1 MR を基本にする。依存する MR は積み重ね（stacked）として扱い、上の MR の差分だけをレビューできるようにする | GitStation |
| **マージキュー** | マージ結果で CI を回し、順番に入れる。04 の M-3（M4）のまま、ただし AI による MR の増加に合わせて早めを検討する | GitStation |
| **環境の再現性** | ツールチェーンと依存の版を固定（`rust-toolchain.toml`、Node の版、開発用 DB のコンテナ）。「自分の PC では通る」をなくす | 各リポジトリ |

### 4.5 GitStation を Claude の正式な利用者にする（G-5、A-8）

- **文脈 API と MCP（読み取り）を M5 → M3 に早める**。Claude が使うもの:
  MR の差分とコメント、チェックの結果、CI のログ（エラーコード付き）、診断 API（04 の P-9）、関連する仕様と ADR、ブランチの衝突予測。
- **エージェントのトークン**（ADR-0017 §4.0 の `agent=true`）を、開発者ごとの Claude に発行する。
  - エージェントは push と MR の作成はできるが、**承認とマージはできない**（今の計画どおり）。
  - 監査ログに「誰の、どのエージェントが」したかが残る。
- **クライアント CLI `gstn`（2026-10-30 追加）**: Claude が `gh` / `glab` と同じようにコマンドで GitStation を操作する
  （`01` §3.11）。Web UI と API でできることは原則すべて `gstn` でもでき、`--json`・固定の終了コード・エラーコード付きの失敗・
  `help --json` による自己説明で、AI が手探りせずに使える。MCP サーバーは同じクライアントのライブラリの上に載せる。M1 から段階的に作る。
- **CI の失敗を Claude に返す**: MR のチェックが落ちると、イベントが開発者の Claude に届く（MCP の通知、または次の `/pbi` の開始時）。
  Claude はエラーコードと診断 API から原因を読み、修正して push する。これはエージェントモデルの「失敗 → 既知の修正」の輪を、CI まで広げることになる。

### 4.6 レビューを詰まらせない（G-7、A-6、A-7）

- **3 段のレビュー**:
  1. 開発者の PC で、エージェントモデルの評価役（読むだけ）が先に見る（今の `/review`）。
  2. GitStation のチェックで、ローカル LLM がレビューと受入基準の照合をする（L-2、L-3）。
  3. 人が見る。人には、AI の指摘を重さ順にまとめたもの、受入基準ごとの結果、変更の要約（利用者の言語、F-20）を見せる。
- **危険度でレビューの深さを変える**: 文書だけ、テストの追加だけ、依存の小さな更新などは、ADR-0017 §4.1.3 の「AI の承認を 1 件と数える」区分を使う。
  保護されたブランチと CODEOWNERS の承認は、今の計画どおり必ず人がする。
- **レビュアーの自動割り当て**: CODEOWNERS（仮の値を実際の担当に直す）+ kanflow の作業量（F-7 を Could → Should に上げる）。
- **レビューの依頼を kanflow に出す**（F-29）。開発者は kanflow のボード 1 つで「次にすること」が分かる。

### 4.7 AI だけで走らせる範囲を決める（A-9）

人が見ていない間に AI を走らせるときの共通の型を決める。

| 問い | 決め方 |
|---|---|
| 完了の判定 | 受入基準のテストとゲートがすべて通る（§4.3） |
| 自己検査 | Stop フック（fmt、lint、テスト）と `/review` |
| 触ってよい範囲 | 1 タスク = 1 worktree = 1 ブランチ。実装計画に書いた範囲だけ。保護されたパスは触らない |
| 止める条件 | 回数と費用の上限、同じ失敗の繰り返し（`loop-operator`）、範囲の外のファイルへの変更 |
| 承認者 | MR の承認とマージは人。本番は人が承認した手順だけ |

### 4.8 エージェントモデルをチームで 1 つにする（G-8、A-4）

- **2 つに分かれたエージェントモデルを、共通の部分と製品ごとの部分に分ける**。
  共通の部分（フック、ゲート、記憶の仕組み、評価役、`/pbi` などの連携コマンド）は 1 か所で育て、製品ごとの部分（IoT 向けの評価役、GitStation 向けの規則）は差分として持つ。
- 配布は今のとおり `git pull`（`/model-sync`）。ホストは、GitStation が自分をホストできるようになったら（M1 の出口）、GitStation に移す。
- **チームの知識を共有する**: 失敗の記録（mistakes）は、サーバーでのマージで union が効かない。対策の候補は次の 2 つ。
  (a) GitStation のマージで、`.gitattributes` の `merge=union` を尊重する。
  (b) 記録を Git の外の「チームの知識 API」（GitStation）に置き、エージェントモデルは API で検索する。
  まず (a) を勧める（仕組みが単純で、Git の履歴に残る）。

### 4.9 流れを計測する（G-10、A-10）

- kanflow と GitStation のイベントをつなぎ、**PBI ごとの流れ** を出す:
  Ready → 着手 → 最初の push → MR → レビュー → マージ → デプロイ、それぞれの時間。
- DORA の 4 指標（デプロイの頻度、変更のリードタイム、変更の失敗率、復旧時間）と、**AI が作った MR の手戻り率**（修正の push 回数、差し戻し）。
- **導入の前に、今の値を測っておく**（GitLab と kanflow の今のデータから）。導入の後と比べて、効果を確かめる。

### 4.10 ローカル LLM の使い方を決める（G-9）

- GPU 1 台を kanflow、GitStation の検証、自動修正で共有する。同時 2 件では、チームの MR が増えると詰まる。
- **サーバーで動く AI は Qwen3.8 27B だけ**（決定 D-1）。Claude は開発者の PC でだけ動く。
- **役割を分ける**:
  - 実装と重い推論は、開発者の PC の Claude。
  - 社外に出せない情報の処理と、サーバー側のすべての AI 処理（GitStation の検証、自動修正、kanflow の AI）は、Qwen3.8 27B。
- **GPU の割り当てに優先度を付ける**: kanflow の対話 > MR の必須チェック > 助言のチェック > 自動修正。kanflow にはすでにプロセスをまたぐ調停（`ai-gate`）があるので、GitStation も同じ調停に参加する。
- GPU の増設の判断材料として、待ち時間を計測する（§4.9）。

### 4.11 GitLab を保険として併用する（決定 D-2）

GitLab はやめずに、GitStation と併用する。GitLab の役割は **リポジトリの保険**（GitStation が止まったときの退避先）とする。

| 項目 | 内容 |
|---|---|
| 正本 | GitStation に移ったリポジトリは、GitStation が正本。GitLab は写し |
| ミラー | GitStation から GitLab へ、ブランチとタグを **push のたびに** 送る（push ミラー）。計画書 01 では「Should、M8」だったものを、**M3（最初のチームが移る時点）の Must** に上げる |
| 遅れの監視 | ミラーの遅れと失敗をエラーコードとアラートにし、`forge doctor` で確かめられるようにする。「保険が実は古かった」を防ぐ |
| GitLab 側の書き込み | 通常はミラー用のアカウントだけが書く。開発者は GitLab に push しない（2 か所で別々に変更が進むのを防ぐ） |
| 切り替えの手順 | GitStation が止まったら、runbook の手順で開発者のリモートを GitLab に向け、kanflow の接続先も GitLab に戻す（kanflow はもともと GitLab と連携しているので、そのまま動く）。復旧後は GitLab で進んだ分を GitStation に取り込んでから戻す |
| kanflow の接続 | kanflow は、プロジェクトごとに **どちらか一方だけ** を読む。両方を読むと、同じコミットや MR が二重に表示される |
| 移行中 | 第 0 段から第 1 段の途中までは GitLab が正本。リポジトリごとに GitStation へ移り、移った時点でミラーの向きが「GitStation → GitLab」になる |

## 5. 進め方（段階）

**GitStation の完成を待たずに、流れを先に作る。** GitStation の MR と CI は M3〜M4 なので、それまでは GitLab のまま、kanflow とエージェントモデルの間の流れを作って試す。
GitStation に移るときは、02 §8.1 の互換方式で kanflow の改修なしに切り替える。

| 段階 | 時期の目安 | 内容 | 主な場所 |
|---|---|---|---|
| **第 0 段: 今すぐ** | 2〜4 週 | (1) kanflow の取りこぼしの 2 件を直す。(2) kanflow の `/api/v1` に `write:dev` スコープを足す（作業の宣言、進捗、MR のリンク）。(3) エージェントモデルに kanflow の MCP と `/pbi` を足す。(4) 受入基準を項目ごとにする（ID 付き）。(5) 今の流れの数値を測る | kanflow、エージェントモデル |
| **第 1 段: GitStation M1〜M3** | M3 まで | GitStation の M3 に次を足す・早める: クライアント CLI `gstn`（M1 から）、文脈 API と MCP（読み取り）、早い衝突の予測（C-2）、`spec-trace`（受入基準とテスト）、エージェントのトークン、kanflow 互換の API、イベントの履歴。M3 のパイロットで、1 チームが GitLab から移る | GitStation |
| **第 2 段: M4** | M4 | マージキュー、MR ごとのプレビュー環境、CI の失敗を Claude に返す輪、決定的な自動修正、流れの計測 | GitStation、kanflow |
| **第 3 段: M5** | M5 | ローカル LLM の検証（受入基準の照合を必須へ）、AI レビュー、計画の自動化（PBI → 実装計画の下書き）、GPU の優先度の調停 | 全体 |

## 6. 今の仕様への変更の提案（まとめ）

| 対象 | 変更 | 理由 |
|---|---|---|
| 01 / 03 | 文脈 API と MCP（読み取り）を M5 → **M3** | Claude が実装の主役なので、最初から使える必要がある（G-5） |
| 04 | 衝突の予測 C-2 を M4 → **M3**。マージキュー M-3 の前倒しを検討 | AI と複数人で MR が増える（G-6） |
| 03 | `spec-trace` を kanflow の受入基準にも使い、**M3** から | 「完了」を機械で判定する（G-4） |
| 02 | kanflow 側の改修を「互換 + 取りこぼしの解消」だけでなく、`write:dev` スコープと受入基準の ID に広げる | 双方向の連携（G-1、G-2） |
| 02 F-7 | レビュアーの推薦を Could → Should | レビューの詰まり（G-7） |
| 新規 | 「エージェントのセッション」（誰の、どの AI が、どのタスクを、どのブランチで）を、kanflow と GitStation の共通の概念にする | 複数人の見える化（G-6） |
| 新規 | GitStation のマージで `merge=union` を尊重する | チームの知識の共有（G-8） |
| 01 | GitLab への push ミラーを Should・M8 → **Must・M3**。遅れの監視と切り替えの runbook を付ける | GitLab を保険にする（決定 D-2） |
| エージェントモデル | 共通部分と製品部分に分け、`/pbi` と kanflow の MCP を共通部分に入れる | 1 つのチームの道具にする（G-8） |
| 01（新規 §3.11） | クライアント CLI `gstn` を M1 から段階的に作る（AI が扱いやすいことを最優先）。エージェントモデルの `glab` を使う手順を、移行時に `gstn` に置き換える | Claude が GitStation の正式な利用者になる（G-5） |

## 7. 決めてほしいこと

| # | 質問 | 推奨 |
|---|---|---|
| Q-1 | **データの境界**: Claude（Anthropic のクラウド）に渡してよいもの（コード、PBI の本文、仕様書、ログ）と、ローカル LLM でしか扱わないものの線引き | コードと PBI は Claude に渡してよい（今も Claude Code で開発している）。個人情報、顧客情報、秘密は渡さない。線引きを規則とフックにする |

| Q-3 | **エージェントモデルの正本**: iotpf 用と GitStation 用のどちらを共通部分の正本にするか | iotpf 用（規模が大きく、チームが使っている）を正本にし、GitStation 用の改善（トークンの削減、gateguard など）を取り込む |
| Q-4 | **受入基準の書き方**: EARS（「〜のとき、システムは〜する」）か Given-When-Then か | Given-When-Then（エンジニア以外にも読みやすく、テストに直しやすい） |
| Q-5 | **第 0 段を GitLab のまま始めてよいか** | 始める。流れの検証を GitStation の完成から切り離せる |
| Q-6 | **パイロットのチームとプロジェクト**（01 §11-8 と同じ） | 第 0 段から同じチームで試し、数値を取る |

### 7.1 決定（2026-10-29）

| # | 決定 | 対応する質問 |
|---|---|---|
| D-1 | **サーバーでは Claude を動かさない。サーバーで動く AI は Qwen3.8 27B だけ**。Claude は開発者の PC でだけ動く。CI の失敗は開発者の PC の Claude に返す（§4.5） | Q-2 |
| D-2 | **GitLab はそのまま使い、GitStation と併用する。GitLab はリポジトリの保険**（§4.11） | Q-5 を含む |
| D-3 | 第 0 段は GitLab のまま始める | Q-5 |
| D-4 | 併用の形: **GitStation に移ったリポジトリは GitStation が正本**。push のたびに GitLab へミラーし、GitStation が止まったときだけ GitLab に切り替える（§4.11） | D-2 の詳細 |
| D-5 | データの境界は **3 区分で機械的に強制**: コード・PBI・設計書・秘密を伏せたログは Claude に渡してよい。個人情報・顧客情報・機密の高い仕様は Qwen だけ。秘密はどちらにも渡さない。kanflow の機密の印とフックで守る。社内規程との照合は別途行う | Q-1 |
| D-6 | エージェントモデルの正本は **iotpf 用**（`D:\app\agents_skills_claudecode`）。GitStation 用の改善を共通部分として取り込み、製品ごとの規則は差分として持つ。統合は差分の一覧から少しずつ | Q-3 |
| D-7 | 受入基準は **Given-When-Then**。ID は `PBI-123/AC-2` で、編集しても振り直さない。仕様書のリポジトリ（`::: req`）は今の形式のまま | Q-4 |

Q-6（パイロットのチーム）だけが未決。

## 8. 危険と対策

| 危険 | 対策 |
|---|---|
| AI の MR が増え、人のレビューが詰まる（Anthropic でも、仕事の多くがレビューになった） | 3 段のレビュー、危険度での深さの切り替え、小さい MR、計測（§4.6、§4.9） |
| 「速くなった気がする」だけになる（METR） | 導入の前の数値を取り、比べる（§4.9） |
| AI がテストを弱めて通す | 受入基準のテストは保護されたパスにし、変更には人の承認を要する（ADR-0017 の方針と同じ） |
| ローカル LLM の GPU が詰まる | 役割の分担と優先度、待ち時間の計測（§4.10） |
| 道具の数が増えて、覚えることが増える | 開発者の入口は `/pbi` と kanflow のボードの 2 つに絞る |
