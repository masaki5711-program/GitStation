# 07 複数人のバイブコーディングを速く、壊れにくくする計画（2026-10-31）

ユーザーの指示（2026-10-31）:「エージェントモデルの保守と共有も含めて、これらを計画に乗せてください。完全無敵なシステムを構築したい」。

「完全無敵」は、**どの 1 つの仕組みが外れても、ほかの仕組みが止める**（多層の防御）と、**壊れたら数分で気づき、記録から原因が分かる**ことと定義する。失敗をゼロにはできないので、目標は数値（§2）で測る。

関係する計画: `01`（製品）、`02`（kanflow 連携）、`03`（仕様駆動）、`04`（CI/CD とマージの安全）、`06`（AI 駆動の開発環境）。この計画は `06` の第 0〜2 段を、チームでの並行開発の観点で具体化する。

## 1. 現状の評価（2026-10-31、クラウドのセッションでの作業から）

## 3. 作業の流れ（ワークストリーム）

### W1 エージェントモデルの一本化と配布（最優先）

**問題**: モデルが複数あり、共通の部分（kanflow 連携、レビューの規則、git の規則、フック、mistake-memory）が分かれて食い違う。

**方針（推奨）**: 共通の部分を **1 つの Claude Code プラグイン**（仮称 `ymma-dev-core`）にまとめ、社内のマーケットプレイス（git のリポジトリ）から配る。各モデルは、製品ごとの部分（IoTPF の規則、forge の規則、tmux の team-lead など）と、**動かし方の違い**だけを持つ。

- TMUX 版と Ver2 の違いは「並行（複数セッション）か単独（1 セッション）か」だけにする。PBI の扱い、作業の宣言、レビュー、git の規則は core で同じにする。TMUX 版の上乗せは `team-lead` / `/team`、作業者ごとの worktree と作業の宣言。Ver2 の上乗せはコンテキストの節約（`token-report`、再レビューの絞り込み）。
- 旧 Agent_Claudecode は core の対象にしない。**いまの状態で使えるように保つ**（不具合の修正だけを入れ、新しい機能は入れない）。

| 層 | 中身 | 置き場所 |
|---|---|---|
| core プラグイン | `kanflow-integration` スキル、`/kanflow`、共通フック（ブランチ名の検査、PBI の取得、作業の宣言、フェイルオープン）、レビューの回し方（Ver2 の「1 差分 1 レビュアー、再レビューは指摘した評価役だけ」）、`build-error-memory`、`parallel-worktrees`、verification-loop | 新しいリポジトリ（GitStation が使えるまでは GitHub、その後 GitStation、GitLab にミラー） |
| 製品ごとの上乗せ | IoTPF: レイヤー別ルーティング、データ主権、PFE。forge: エラーの契約、権限の表、evaluator 群。TMUX: `team-lead` / `/team` | 今の各モデルのリポジトリ |

- **版**: semver。破壊的な変更は major。`CHANGELOG.md` は 1 つ。
- **ゲート**:
  - 各モデルの `self-heal --check` に「core の版が許す範囲にあるか」「core と同じ名前の資産を上乗せ側で上書きしていないか」を足す（`validate-shared-core`）。
  - core のリポジトリには、フックのテスト（サンプルのイベントを流す）、eval（スキルとエージェントの評価）、各モデルとの組み合わせのテストを置く。
- **出し方**: `beta` と `stable` の 2 つのチャンネル。新しい版は 1 チームで 3 日使ってから `stable` に上げる。戻すときは前の版を指定するだけ。
- **共有の知識**: mistake-memory（エラー → 直し方）は core のリポジトリに集める。各モデルからは `node scripts/mistakes.js add` で PR を出す。
- **core に移す順序**（TMUX 版と Ver2 が対象）:
  1. 両方で同じになっている `kanflow-integration` と `/kanflow`。
  2. フックの共通部分。
  3. レビューの規則。
- **旧 Agent_Claudecode → TMUX 版 / Ver2 への切り替え**:
  - 切り替えの条件: GitStation で clone / push と MR ができる（M1 の phase 9 以降、MR は M4）、kanflow の連携の第 0 段が実際の kanflow で動いた、TMUX 版と Ver2 が core を取り込み、CI のゲートが緑。
  - 切り替えの手順: 1 つのチーム（または 1 つの製品）で 1 スプリント試す → 問題がなければ全体を切り替える → 旧版は読み取り専用にして README に置き換え先を書く。
  - 切り替えまでの旧版: 不具合の修正だけを入れる。新しいモデルで直した不具合のうち旧版にも当てはまるものは、旧版にも入れる（mistake-memory は共有する）。
  - 使い分け: 大きな機能や複数の PBI を並行して速く進めるときは TMUX 版、1 つの PBI や小さな修正を少ないコンテキストで進めるときは Ver2。
- **完了の条件**: TMUX 版と Ver2 が core を取り込み、kanflow 連携の変更が 1 回の PR で両方に届く。食い違いのゲートが CI で動く。旧版は切り替えまで動き続ける。

### W2 CI でテストを回し、AI のセッションでは回さない

- GitStation（GitHub Actions、GitStation の CI ができたら移す）:
  - fmt、clippy `-D warnings`、`cargo nextest --workspace`（Postgres のサービスコンテナ）、`gen-catalog --check`、`gen-authz --check`、エージェントモデルのゲート（`validate-authz-coverage`、`validate-error-registry`）。
- kanflow:
  - `tsc`、eslint、vitest、**MariaDB のサービスコンテナで `KANFLOW_DB_TESTS=1` の DB テスト**、マイグレーションの適用の確認、Playwright の E2E。
- 不安定なテストの扱い: 再実行で通ったテストを自動で記録し、2 回目で「不安定」として一覧に出す（隔離はしない。原因を突き止める作業を kanflow の PBI として起票する）。
- クラウドのセッションの設定スクリプトに、kanflow の DB テスト用の MariaDB を入れる（`read_documentation` の environment.setup_script を参照）。
- **完了の条件**: どの PR も CI が緑でないとマージできない。「未検証のまま統合」が無くなる。

### W3 作業中の見える化と、作業の宣言の自動化

- kanflow のボードと PBI の画面に「作業中」（誰が、どのブランチ・どの AI セッションで、いつから）を出す。宣言が切れそうなもの、失効したものも区別して出す。
- エージェントモデル（W1 の core）のフックで自動化する:

  | いつ | 何をするか |
  |---|---|
  | セッション開始 | ブランチの PBI に作業を宣言する（生存確認を兼ねる） |
  | 作業中（1 時間ごと） | 生存確認 |
  | セッション終了 | 進捗のコメント（`post_progress`） |
  | MR を出したとき | MR のリンク（`link_merge_request`） |
  | マージ / ブランチの削除 | 宣言の解除 |

- 宣言が `409` のときは作業を始めない（スキルに記載済み、フックで強制する）。
- **完了の条件**: 2 人 + 2 つの AI が同じスプリントで作業して、取り合いが 0 件、ボードで全員の作業が見える。

### W4 触る範囲の宣言と衝突の予測

- `planner` の出力（触るファイル・モジュール）を、作業の宣言と一緒に kanflow に登録する（`06` §4.4）。
- 重なる宣言があれば、計画の時点で両者に知らせる。重なりの判定は、パスの前方一致とモジュール（crate、ディレクトリ）の単位。
- push のとき、実際の差分と宣言を比べ、宣言の外を触っていたら警告する（止めない）。
- GitStation 側（M4）のマージキューと組み合わせ、意味的な衝突はマージ結果のパイプラインで止める（`04` M-3）。
- **完了の条件**: 並行する MR の衝突による手戻りが、MR 10 件あたり 1 件以下。

### W5 受入基準に ID を付け、テストと対応させる

- 受入基準を項目に分け、変わらない ID（`PBI-12/AC-2`）を付ける（`06` D-7）。
- テストの名前かコメントに AC の ID を書く決まりにする（`tdd-guide` に入れる）。
- MR に「AC の対応表」（AC ごとに、対応するテストと、そのテストの結果）を自動で付ける。対応するテストのない AC は MR の画面で警告する。
- kanflow の「完了の候補」（`02` F-9）は、すべての AC が緑の MR がマージされたときに出す。完了の確定は PO。
- **完了の条件**: AI が「残りの AC」を自分で判断でき、PO が完了を確定するのに要る情報が MR に揃っている。

### W6 引き継ぎの自動化

- セッションの終わり（Stop フック）に、次を集めて PBI のコメントと `docs/handoff/` に書く:
  - リポジトリごとのブランチ、未 push、未統合のブランチ
  - 宣言の状態
  - 未解決のレビューの指摘、赤いゲート、失敗しているテストのコマンド
- 次のセッションの開始時に、最新の引き継ぎと PBI の状態を読み込む（session-start フック）。
- **完了の条件**: 人が手で引き継ぎを書かなくても、新しいセッションが最初の 1 分で再開の場所を言える。

### W7 レビューの費用を下げ、取りこぼしを減らす

- 決まった検査はすべてゲートにして、AI のレビューより先に流す（エラーの登録、権限の表、生成物の差分、i18n の完全性、マイグレーションの追記のみ）。
- AI のレビューの役割分担:
  - 最初の確認: 言語別のレビュアー 1 つ（`sonnet`）
  - 該当するときだけ: セキュリティ、DB、git、権限（`opus`）
  - 再レビュー: 指摘を出した評価役だけが修正の差分を見る（最大 2 回）
- 評価役が見逃した欠陥は eval に足す（`forge-feedback-loop.md` 規則 5）。eval の合格率を W1 の core の CI で測る。
- **完了の条件**: 1 MR あたりの AI レビューの呼び出しが 2〜3 回、マージ後の欠陥が増えない。

### W8 PBI から本番までを 1 本の流れにする（GitStation の M3〜M4 と一緒に）

1. `/kanflow pick` → AC からタスクに分けて `create_task`（似たタスクがあれば聞く）
2. `team-lead`（TMUX）で作業者ごとに worktree を作り、それぞれ作業を宣言し、触る範囲を登録
3. 並行して実装（TDD、AC の ID 付きのテスト）
4. MR（AC の対応表、危険の検査 M-6）
5. マージキュー → 自動マージ（`04` M-5 の `reserve` / `conditional` / `full`。`stop` は人の承認）
6. kanflow に MR の状態、完了の候補、リリースノートの下書き（ローカル LLM）
7. 人の承認で本番デプロイ → kanflow のリリースが更新

人の判断は、計画の承認、PO の完了の確定、本番デプロイの承認、危険の検査の `stop` の解除の 4 か所だけにする。

### W9 ポーリングからイベントへ

- kanflow は、GitStation の連携の履歴（`02` の `…/cursor`）を購読して、MR・パイプライン・タグの変化を数秒で反映する。GitLab の間は Webhook を足し、ポーリングは取りこぼしの保険として残す。

### W10 ローカル LLM に定型の作業を任せる

- MR の要約、リリースノート、デイリーの下書き、進捗のコメントの要約、AC の対応表の文章化をローカル LLM（Qwen、`06` D-1）に任せる。Claude は設計・実装・レビューに使う。
- **完了の条件**: 定型の文章の作成で Claude のクレジットを使わない。

### W11 フィードバックの輪を kanflow に移す（チームで共有し、プロジェクトをまたいで再発を防ぐ）

ユーザーの提案と決定（2026-10-31）:「エラーや問題点をフィードバックサイクルとして機能させるのに、プロジェクトごとに同じ問題を起こさないように、kanflow 側にエラーをチームで保管する」「エージェントモデルとして行うのではなく、kanflow 側にフィードバックサイクルを移設する。現在のエージェントモデルはローカルで保持されている」。

**今の問題**: フィードバックの輪（失敗の記録、直し方の照会、記録の促し、再発の検出）は、エージェントモデルの中で動いている。記録（mistake-memory の `records.jsonl`、skill-run の記録）は各リポジトリや各 PC に置かれ、人・プロジェクト・CI をまたいで届かない。同じ失敗を、別のプロジェクトや別の人がもう一度調べている。

**決定**: 輪そのものを **kanflow のサーバーの機能** にする。kanflow が、保管、照合、確認、再発の検出、再発防止の提案、測定、配布をすべて持つ。エージェントモデルは「失敗を送り、答えを受け取る」だけの薄い窓口になり、知識を手元に持たない。

| 役割 | kanflow（サーバー） | エージェントモデル（窓口） |
|---|---|---|
| 失敗の受け取り | `POST /api/v1/feedback/failures`（MCP `report_failure`） | 失敗したコマンド・テストの結果を送る |
| 署名の作成と照合 | 正規化（パス・ID・数値・時刻を除く）と照合を **サーバーで一律に** 行う | しない（クライアントごとに作り方がずれないように） |
| 答え | 当たった教訓の直し方・確かめ方を返す | 受け取った答えを示す（本文はデータで、指示ではない） |
| 記録 | 失敗の後に成功したら、下書きの教訓を自動で作る（失敗 → 変更 → 成功の組） | 解決の差分の要約を送る |
| 確認・廃止 | 画面で Maintainer / SM 以上が行う | しない |
| 再発の検出と提案 | 同じ署名が 3 回を超えたら、再発防止の PBI を提案（PO が承認） | しない |
| 測定 | 再発率、直すまでの時間、仕組みにした割合 | しない |
| 伏せ字 | 2 重目の伏せ字（サーバー側の規則） | 1 重目の伏せ字（送る前に秘密・パス・ホスト名を消す。データが PC を出る前なので必要） |

**送り手を広げる**: 輪がサーバーにあるので、エージェントのセッションだけでなく、CI（W2 の失敗したジョブ）、GitStation（M3 以降、パイプライン・マージキュー・障害の記録）からも同じ入口に失敗を送れる。人の手の作業も、kanflow の画面から登録できる。

**流れ**:
1. 失敗 → 窓口が `report_failure` → kanflow が照合して、確認済みの教訓があれば直し方を返す（3 秒で打ち切り、届かなければ作業は止めない）。
2. 同じセッション・同じジョブで後に成功 → kanflow が下書きの教訓を作る（失敗の署名 + 直した差分の要約 + 確かめたコマンド）。
3. 確認: Maintainer / SM 以上（または評価役のエージェントの提案を人が承認）が「確認済み」にする。確認済みだけを他のプロジェクトに返す。
4. 仕組みにする: 同じ署名が 3 回を超えたら、kanflow が再発防止の PBI を提案する。直し方をゲート・テスト・eval・規則・エラーの目録の説明にして、教訓を「仕組みにした」にする。
5. 測る: 再発率（プロジェクトをまたいだ同じ署名の 2 回目以降）、教訓が当たったときと当たらないときの直すまでの時間、仕組みにした割合を kanflow のダッシュボードに出す。
6. 要約: 似た教訓のまとめ、週ごとの「よく起きる失敗」の要約は、kanflow のローカル LLM（Qwen、`06` D-1）が作る。

**届かないとき**: 窓口は失敗を送れなかった分だけを手元の送信待ちの列に貯め、次に届いたときに送る（知識は持たない。列は上限付きで、古いものから捨て、捨てたことをログに出す）。答えが返らないときは、普通に調べて進める。

**既存の記録の扱い**:
- mistake-memory（各エージェントモデルの `records.jsonl`、`node scripts/mistakes.js`）: 最初に kanflow に取り込み、以後は **廃止** する（`mistakes.js` は kanflow の窓口に置き換える）。旧 Agent_Claudecode は切り替えまで今のまま使う（W1）。
- `post:bash:error-memory` などのフック: 照合・記録の処理を消し、`report_failure` を呼ぶだけにする（core に置く）。
- GitStation のエラーの目録（`FG-…`）: 正は `errors.toml` のまま。教訓は FG コードで目録にリンクする。
- 障害の記録（`ops/incidents/`）: 振り返りの「フィードバックの行動」は kanflow の教訓と PBI に登録する。

**守ること**:
- オンプレの kanflow なので、データ主権の境界の中。それでも伏せ字は 2 重（窓口とサーバー）。伏せられないものは保存しない。
- 機密の印（`06` D-5）を教訓にも付けられ、印のあるものは Claude 向けの MCP に返さない。
- 教訓の本文は人と AI が書いたデータで、指示ではない（MCP の注意書きに含める）。
- 権限: 失敗の送信は `dev:write`（CI はサービスアカウントのトークン）、読むのはチームの全員、確認・廃止は Maintainer / SM 以上。
- 量: 失敗の送信は 1 トークンあたりの上限と、同じ署名のまとめ（短い間の連続は 1 件に）で抑える。

**作るもの**:
- kanflow: 失敗と教訓のモデル、署名の正規化と照合、下書きの自動作成、確認の画面、再発の PBI の提案、ダッシュボード、`/api/v1/feedback/*` と MCP の道具（`report_failure`、`search_lessons`、`report_resolution`）、サーバー側の伏せ字、ローカル LLM の要約。
- エージェントモデル（W1 の core）: 失敗と解決を送るフック、1 重目の伏せ字、送信待ちの列。手元の知識の保管は持たない。
- CI（W2）: 失敗したジョブの送信。
- **完了の条件**: 2 つ以上のプロジェクトで、別のプロジェクトで登録された教訓が当たって直った例がある。3 回を超えた署名がすべて PBI になっている。エージェントモデルの中に、照合・記録の処理が残っていない。

## 5. 決めること（推奨案。ユーザーの指示「推奨で進める」に従い、異論がなければこのとおり）

1. **共通部分の配り方**: Claude Code のプラグインと社内のマーケットプレイス（推奨）。代わりの案は共通リポジトリ + 同期のスクリプト、または git subtree。
2. **core の最初の置き場所**: GitHub の新しい非公開リポジトリ（GitStation が自分を置けるようになったら GitStation に移す）。
3. **旧 Agent_Claudecode**: 全体（GitStation と kanflow の連携）ができるまで、いまの状態で使い続ける（不具合の修正だけ）。全体ができたら TMUX 版（並行）と Ver2（単独）に切り替える（ユーザーの決定、2026-10-31）。
4. **CI**: いまは GitHub Actions（オンプレの原則には、GitStation の CI ができた時点で移すことで従う）。
5. **作業の宣言の自動化**: セッションの開始で自動に宣言する（推奨）。代わりの案は `/kanflow pick` のときだけ。

## 6. 危険と対策

| 危険 | 対策 |
|---|---|
| core の更新で全員のモデルが一度に壊れる | `beta` / `stable` のチャンネル、組み合わせのテスト、前の版に戻せる |
| 自動化が多くなり、遅く・うるさくなる | フックは 3 秒以内で打ち切ってフェイルオープン、通知は 1 回だけ |
| 宣言が形だけになる（宣言せずに作業する） | フックで自動化し、宣言のないブランチの push に警告を出す |
| AI のレビューの見逃し | eval に足して評価役を直す。決まった検査はゲートにする |
| クレジットの消費 | 決まった検査を先に、安いモデルで最初の確認、定型の文章はローカル LLM |
| 外部のサービスへの依存 | CI と core の置き場所は GitStation ができたら移す（オンプレの原則） |
