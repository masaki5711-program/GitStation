## 0. 結論の要約（推奨）

| # | 論点 | 推奨 | 一言の理由 |
|---|---|---|---|
| 1 | 拡張子 | **`.md` のまま。独自の拡張子も二重拡張子（`.qms.md`）も作らない** | 道具・AI・移行の互換性を捨てる理由がない。型は中身に 1 か所だけ書く |
| 2 | ファイル名 | **文書番号をそのままファイル名にする**（`QP-07-001.md`）。題名は中身に書く | 半角英数で壊れない。番号の接頭辞が型を表すので拡張子に型が要らない |
| 3 | 属性 | 先頭の YAML（frontmatter）。**必須は 4 項目だけ**（`doctype`・`id`・`title`・`owner`） | 非エンジニアに YAML を書かせない（画面のフォームが作る）ので少なく |
| 4 | 版・承認・改訂履歴 | **ファイルに書かない。Git と MR の承認から GitStation が作る** | 手書きは必ず食い違う。承認の証跡が改ざんできない形で残る |
| 5 | 本文 | ふつうの Markdown + **ブロック** `::: <種類> <ID>`（03 の `::: req` を一般化） | どのビューアでも読める。要件・危険源・点検項目を ID で引ける |
| 6 | 文書の型 | **型の定義ファイル**（`.forge/doctypes/<型>.yml`）で、必須の項目・見出し・ブロックを決め、CI で検査 | AI への書き方の指示と、機械の検査と、画面のフォームを 1 つの定義から作る |
| 7 | 参照 | `[[QP-07-001]]`・`[[RA-2026-014#H-03]]`（**パスではなく ID で参照**） | ファイルを動かしても切れない。短く、非エンジニアにも書ける |
| 8 | 非エンジニア | 画面で **フォーム + 見たままに近い編集 + 文章の差分 + Word/PDF の出力**。保存の形は常に同じ Markdown | 書き方の違いを利用者に見せない |
| 9 | 同時の編集 | **文書ごとに「改訂中」は 1 つ**（開いている改訂の MR は 1 つ）+ 編集中の表示（期限つきの編集の宣言）。リアルタイムの共同編集は作らない | 承認の単位と編集の単位をそろえる。取り合いを「後で直す」ではなく「始める前に分かる」にする |
| 10 | 電子の承認 | MR の承認を電子の署名として扱う。**承認の直前に本人の再確認**、承認の意味（作成・確認・承認）、**中身のハッシュ（SHA）に結ぶ**、監査の封印 | 押印の代わりに足る証跡（誰が・いつ・何を・どの意味で） |
| 10b | 承認のフェーズ | **リポジトリごとに、確認・承認のフェーズを入れるかを決める**（GitStation のリポジトリの設定。リポジトリのファイルには置かない） | 設定は統制なので、中身を書ける人が外せないように |
| 12 | Word / PDF の出力 | **最後の段に回す**（2026-11-09）。先に「文書の JSON」を作り、出力はそれを入力にする。承認の情報の正は GitStation | 出力の道具（Python・Pandoc・PDF の組版）は、正式の配布の形が決まってから選ぶ |
| 11 | ローカル LLM | 文書の **修正の提案**（画面の中、採否は人）と、**リポジトリの整理の提案**（毎晩の点検 → 報告 → 整理の MR の下書き）。どちらも直接は変えない | 規制の文書を AI が黙って変えない。承認は人だけ |

> 前の回答（チャット）では二重拡張子 `*.qms.md` を勧めたが、深く検討して **取り下げる**。理由は §2.3。

## 1. 前提 — 3 種類の利用者が求めるもの

| 利用者 | したいこと | 困ること |
|---|---|---|
| エンジニア | エディタと Claude Code で書く、`git diff` で読む、CI で検査 | 独自の形式、手で保つ番号、バイナリ |
| 非エンジニア（品質保証・安全衛生・設備・現場） | 雛形から書く、レビューしてもらう、承認をもらう、印刷・配布する、最新版がどれかすぐ分かる | YAML・記号、Git の操作、行単位の差分、エラーが英語や暗号 |
| AI（開発者の Claude Code、サーバーのローカル LLM） | 構造を予測できる、ID で一部だけ取れる、書き方の規則が機械で読める | 自由すぎる書式、巨大なファイル、表の崩れ |

**設計の軸**: 「保存の形（正）は 1 つの厳密な Markdown。人ごとに見せ方と書き方を変える」。
Markdown を非エンジニアに直接書かせることは目標にしない（書いてもよいが、書かなくても済む）。

## 2. 拡張子とファイル名

### 2.1 比べた案

| 案 | 例 | 良い点 | 悪い点 |
|---|---|---|---|
| A. `.md` + frontmatter で型 | `QP-07-001.md` | 道具・AI・GitLab/GitHub の表示がそのまま。型の情報は 1 か所 | ファイル名だけでは型が分からない（→ 番号の接頭辞で分かるようにする） |
| B. 二重拡張子 | `文書管理規程.qms.md` | ファイル名で型が分かる。glob で拾える | 型を 2 か所に書く（名前と中身）ので食い違う。Windows のエクスプローラーは `.md` だけを隠して「`文書管理規程.qms`」と見せる。名前を変えたときに壊しやすい |
| C. 独自の拡張子 | `QP-07-001.gsd` | 「GitStation の文書」と主張できる | エディタ・プレビュー・差分・AI の既定の扱いがすべて効かない。プラグインの保守が Claude に増える。外へ持ち出せない |
| D. フォルダで型 | `qms/procedures/…md` | 人に分かりやすい | 移動で型が変わってしまう。型の正にはできない（並べ方としては使う） |

### 2.2 推奨: A + 「ファイル名 = 文書番号」

```
qms/
  QM-001.md                 # 品質マニュアル
  procedures/
    QP-07-001.md            # 文書管理規程
    QP-07-001.en.md         # その英訳（§7.4）
  forms/
    QF-07-001.md            # 様式（雛形）。記入済みの記録はここに置かない（§6.4）
safety/
  RA-2026-014.md            # リスクアセスメント
  RA-2026-014/              # その添付（写真・図）
    press3-guard.jpg
equipment/
  URS-L3-001.md             # 設備要求仕様
spec/
  ZEVA-CFG.md               # システム仕様（03 の構造化仕様）
```

- **ファイル名は半角英数と `-` だけ**。日本語の題名は frontmatter の `title`。理由: Windows・macOS（濁点の正規化の違い）・URL・
  `git` の表示（`core.quotepath`）・zip で日本語のファイル名は壊れやすい。画面と出力の Word/PDF では題名で見せるので、利用者はファイル名を意識しない。
- **ファイル名と `id` が一致しない場合は lint のエラー**（1 つの正を保つための検査）。
- フォルダは人のための並べ方。型の判定には使わない。

### 2.3 二重拡張子を取り下げた理由（前の回答の訂正）

1. 型を名前と中身の 2 か所に持つことになり、「No silent failures / 1 か所の正」の考え方に合わない。
2. 文書番号の接頭辞（`QP`・`RA`・`URS`）が既に型を表している。二重拡張子は同じ情報の 3 回目。
3. Windows の既定の表示で、非エンジニアに `.qms` が拡張子のように見え、名前の変更で壊しやすい。
4. AI が型で探したいときは `doctype` で索引（GitStation の API / MCP）を引けばよく、ファイル名の glob に頼る理由がない。

**接尾辞を使うのは言語だけ**（`QP-07-001.en.md`）。言語は「同じ文書の別の版」で、型ではないため（§7.4）。

## 3. frontmatter（属性）

### 3.1 書くもの

```yaml
---
doctype: safety.risk-assessment   # 必須。型の定義（§5）の名前
id: RA-2026-014                   # 必須。文書番号。ファイル名と一致。一度付けたら変えない
title: プレス機 No.3 リスクアセスメント  # 必須
owner: safety-team                # 必須。責任を持つグループ（GitStation のグループ。個人名にしない: 異動で古くなる）
classification: internal          # 任意（型の既定あり）。public / internal / confidential。06 D-5 の AI の振り分けに使う
review_cycle: 12M                 # 任意（型の既定あり）。定期見直しの周期
related: [URS-L3-001, QP-07-001]  # 任意。関連する文書（本文の [[ ]] とは別に、文書どうしの関係として）
lang: ja                          # 任意（既定 ja）
---
```

- **必須は 4 項目だけ**。型ごとの追加の項目（安全なら `regulations`、URS なら `equipment` など）は型の定義で決める。
- 値は **型の定義の選択肢から選ぶ** ものを多くする（自由記述を減らす。画面ではプルダウンになる）。

### 3.2 書かないもの（GitStation が導く）

| 情報 | 正 | 理由 |
|---|---|---|
| 版数（第 3 版） | GitStation の文書の索引（§6.1） | 手で上げ忘れる・二重に上げる |
| 承認者・承認日 | MR の承認の記録（監査の表、ADR-0018 で封印） | ファイルに書いた名前は誰でも書き換えられる。証跡にならない |
| 改訂履歴（いつ・誰が・何を・なぜ） | MR のタイトルと「改訂の理由」の欄 + コミット | 同上。出力の Word/PDF には自動で表を入れる |
| 状態（起案中・承認済み・発行済み） | ブランチと MR とタグ | §6.2 |
| 最終更新日 | Git | |

**注意 — 03 §4.2 との食い違い**: 03 の例は frontmatter に `status: draft / review / approved / deprecated` と `owners` を書いている。
この案では `status` を書かない（廃止だけは §6.2 の `retired` で書く）。03 を直すかは §11 Q1 で決める。

### 3.3 機密区分の扱い（注意）

- `classification` は **AI への渡し方の判断の材料** であり、アクセス制御ではない。読める人はリポジトリの権限（`authorize()`）で決まる。
- **区分を下げる変更**（`confidential` → `internal`）は、MR で目立つ警告と、**リポジトリの設定（DB）で決めた承認者**の承認を必須にする（下げたうえで AI に渡す、という抜け道を塞ぐ。§13 の 5）。
- 機密の文書は、機密のリポジトリに分けるのが基本（ファイル単位の読み取り権限は作らない。Git の仕組み上、作れない）。

## 4. 本文

### 4.1 基本: ふつうの Markdown（CommonMark + GFM の表）

- 見出し・箇条書き・表・リンク・画像・Mermaid の図。HTML の直書きは禁止（lint で検出。出力と安全のため）。
- **1 文 1 行**（句点で改行）で保存する。差分が文単位になり、レビューと AI の編集が楽になる。整形の道具（§8.2）が自動で行うので、人は気にしなくてよい。
  - **日本語の落とし穴**: Markdown は段落の中の改行を空白として表示するため、和文の間に余計な空白が出る。GitStation の表示と出力は
    「和文と和文の間の改行は詰める」処理を入れる（必須。入れないと 1 文 1 行が使えない）。

### 4.2 ブロック — 文書の中の「ID で引ける単位」

03 §4.2 の `::: req <ID>` を一般化する。種類は **型の定義で許可したものだけ** 使える。

```markdown
## 3. 危険源の特定とリスクの見積り

::: hazard H-03 severity=3 likelihood=2
スライドの下降中に、ガードの開口部から手が入る。
対象の作業: 金型の交換、詰まりの除去。
:::

::: control C-03a for=H-03 type=engineering
ガードにインターロックを付け、開いたら停止する（[[URS-L3-001#REQ-L3-012]]）。
:::
```

| 種類（例） | 使う型 | 中身 |
|---|---|---|
| `req` | システム仕様・URS | 要件（03 と同じ） |
| `hazard` / `control` | リスクアセスメント | 危険源・低減措置 |
| `check` | 点検・受入の基準 | 点検項目、判定の基準 |
| `decision` | URS・計画 | 決めるべき項目（W12 の `checklist.yml` を本文に取り込む案。§10 の 2） |
| `term` | 用語集 | 用語の定義 |
| `step` | 規程・手順書 | 手順の 1 段（実施する役割の属性。外から `[[QP-07-001#S-3]]` で引ける） |
| `record` | 規程・手順書 | 残す記録（様式の文書番号・保管期間の属性。記録そのものは置かない、§6.4） |

- **ブロックの ID は文書の中で一意、一度付けたら変えない**（03 と同じ。廃止は `status=deprecated` の属性 — 今の `spec_doc` と 03 の言葉。ADR-0026 §2）。外からは `[[RA-2026-014#H-03]]`。
- **書くときはブロック、見るときは表**。FMEA やリスクの一覧のような横に広い表は、Markdown の表で書くと編集も差分も破綻する。
  1 行を 1 ブロックで書き、表示と Word の出力で表に組む。
- `:::` は対応していないビューア（GitLab など）でも、記号が見えるだけで本文は読める（壊れ方が穏やか）。

### 4.3 参照

| 書き方 | 意味 |
|---|---|
| `[[QP-07-001]]` | 文書（表示は「QP-07-001 文書管理規程」） |
| `[[RA-2026-014#H-03]]` | 文書の中のブロック |
| `[[specs/zeva-engine:ZEVA-CFG-012]]` | 他のリポジトリ（`.forge/repo.yml` で版を固定したもの。03 §4.4 / X1） |

- パスではなく ID で解決する。**壊れた参照は lint のエラー**。
- ふつうのリンク `[文](https://…)` は外部の資料に使う。社内の文書どうしは `[[ ]]`。

### 4.4 添付・図・データ

- 図は Mermaid を第一（差分が取れる）。写真・図面は `<文書番号>/` のフォルダに置く。大きいもの（目安 5 MB 超）は Git LFS（要検討）。
- **計測値などの大量の表データは CSV に分け**、本文から参照する。Markdown の表は 30 行・6 列程度まで。
- 取引先から受け取る PDF・図面は「添付」として置き、本文の正にはしない（03 §4.1 の文書仕様の扱いと同じ）。

## 5. 文書の型の定義（`.forge/doctypes/<型>.yml`）

1 つの定義から、**(a) lint の検査、(b) 画面のフォーム、(c) 新規作成の雛形、(d) AI への書き方の指示、(e) Word/PDF の出力の形** を作る。

```yaml
# .forge/doctypes/safety.risk-assessment.yml（案）
name: safety.risk-assessment
label: { ja: リスクアセスメント, en: Risk assessment, id: Penilaian risiko }
id_pattern: '^RA-\d{4}-\d{3}$'
defaults: { classification: internal, review_cycle: 12M }
fields:                                  # frontmatter の追加の項目
  regulations: { type: list, required: true, label: { ja: 関係する法令 } }
  equipment:   { type: ref, doctype: equipment.urs, required: false }
sections:                                # 必須の見出し（順番も検査）
  - { title: 対象と範囲 }
  - { title: 危険源の特定とリスクの見積り, blocks: [hazard] }
  - { title: リスク低減措置, blocks: [control] }
  - { title: 残留リスク }
blocks:
  hazard:
    id_pattern: '^H-\d{2}$'
    attrs: { severity: { type: int, min: 1, max: 4 }, likelihood: { type: int, min: 1, max: 4 } }
  control:
    id_pattern: '^C-\d{2}[a-z]?$'
    attrs: { for: { type: blockref, kind: hazard, required: true },
             type: { enum: [elimination, engineering, administrative, ppe] } }
rules:                                   # 型の固有の検査（決定的なものだけ）
  - every_hazard_has_control             # 措置のない危険源はエラー
approval_hint:                           # 承認のフェーズの「推奨」だけ。実際に入れるかと承認者は、リポジトリの設定（§6.3.1）
  review: [safety-team]
  approve: [plant-manager]
export: standard-ja                       # 出力の定義（§7.3 の .forge/export/<名前>/）
```

- 型の定義は **版を持ち、ベースのリポジトリ・マーケットプレイスで配る**（09 §3・W12・W15）。各リポジトリは版を固定して使う。
- **lint は決定的な検査だけ**（必須の項目・見出し・ID の形・重複・壊れた参照・型の規則）。「内容が十分か」は AI の助言（仮想 DR、09 §5）に分ける
  （ADR-0003 と同じ線引き）。
- 最初に用意する型の候補: `qms.manual`・`qms.procedure`・`qms.form`・`safety.risk-assessment`・`equipment.urs`・`spec.system`（03 の構造化仕様）・`glossary`。

## 6. 文書の管理（QMS の要求との対応）

### 6.1 版（改訂番号）— **Git の版とは別に、文書ごとの版が要る**

Git の版はリポジトリ全体に付くが、QMS は「QP-07-001 の第 3 版」のように **文書ごと** の版を求める。案:

- 承認された MR が `main` に入り、その MR が **文書の中身** を変えていたら、GitStation が文書の版を 1 つ上げ、
  文書の索引（DB）とタグ `doc/QP-07-001/r3` に記録する。
- **決定（2026-11-09）**: MR に「軽微な訂正」の印を付けたら版を上げない（履歴には残る）。
  - 「軽微」を誰でも付けられると、中身の変更を版を上げずに通す抜け道になる。**軽微の印の MR も、型の必須の承認者の承認を要る**（承認者が「軽微か」も判断する）。
  - 決定的な検査で「軽微」と矛盾するもの（ブロックの属性の変更、ブロックの追加・削除、数値の変更、見出しの変更）があれば、印を付けられない（lint のエラー）。

### 6.2 状態

| 状態 | 正 |
|---|---|
| 起案中 | ブランチの上にだけある / MR が下書き |
| レビュー中 | MR が開いている |
| 発行済み（最新版） | `main` にあり、文書の版が付いている |
| 廃止 | frontmatter の `retired: { date, replaced_by }`（廃止も MR の承認で行う）。ファイルは消さない |

### 6.3 電子の承認（2026-11-09: 進めると決定）

押印・サインの代わりに足るには、**誰が・いつ・何を・どの意味で** 承認したかが、後から否認・改ざんできない形で残る必要がある。
今の MR の承認（ADR-0024 §8）は「誰が・いつ・どの SHA を」を既に持つ。足りないものを足す。

| 要素 | 今（ADR-0024） | 足すもの |
|---|---|---|
| 誰が | Keycloak のログイン（ADR-0021）の本人 | **承認の直前の再確認**（直近 N 分以内のログインでなければ Keycloak で再ログイン。`max_age` / `prompt=login`）。席を離れた画面で他人が押せないように |
| 何を | 承認を head の SHA と target に結ぶ（新しいコミットで失効） | 承認の記録に **文書ごとの中身のハッシュ**（`id`・文書の版・ファイルの blob の SHA）を入れる。出力の PDF にも同じ値を印字し、紙と電子を突き合わせられる |
| どの意味で | 「承認」の 1 種類 | **承認の意味**（リポジトリの設定のフェーズで決める §6.3.1: 作成 `authored` / 確認 `reviewed` / 承認 `approved`）。グループごとに意味を割り当てる（例: 安全衛生 = 確認、工場長 = 承認） |
| 否認できない | 監査の表（ADR-0018 で追記だけ・封印） | 承認の画面に **承認の文言**（「私は QP-07-001 第 4 版（予定）の内容を確認し、承認します」。版はマージで確定する、§13 の 4）を出し、押した文言ごと記録する |
| 代理 | 代理実行（ADR-0025）は本人が GitStation の画面で確認 | 文書の承認は **代理を禁止**（既定）。Kanflow からの承認を認めるかは **リポジトリの設定（DB）** で決め、認めても本人の再確認の画面を通る場合だけ（§13 の 5） |

- フェーズごとの必須の承認者のグループと意味（§6.3.1 のリポジトリの設定）を、MR のマージの条件にする（ADR-0024 の承認の数に、グループと意味の条件を足す）。
- **起案者は自分の MR を承認できない**（既にある規則 `FG-REVIEW-0013`）。AI（ボット）も承認できない（ADR-0017）。
- 出力の PDF の承認欄は、この記録から作る（氏名・意味・日時・ハッシュの先頭）。手で書く欄は作らない。
#### 6.3.1 フェーズをリポジトリごとに決める（2026-11-09 決定）

| 設定 | 意味 | 向く例 |
|---|---|---|
| フェーズなし | ふつうの MR の承認（ADR-0024 の承認の数）だけ。電子の署名の追加分（再確認・意味・文言）は使わない | システム仕様、社内の手引き、下書きの置き場 |
| 承認だけ | 「承認」のフェーズ 1 つ。電子の署名の追加分を使う | 小さな部署の規程 |
| 確認 → 承認 | 2 つのフェーズ。**確認が全部そろってから承認できる**（順番を強制。承認者は確認の結果を見て押す） | QMS の規程・手順書、リスクアセスメント、URS |

- 設定は **GitStation のリポジトリの設定**（DB。画面と API。変更は監査に残る）に置き、`.forge/` のファイルには置かない。
  理由: ファイルにすると、リポジトリに書ける人が「フェーズなし」に変える MR を出せる（統制を中身と同じ権限で外せてしまう）。
- 各フェーズの承認者のグループと人数も、リポジトリの設定で決める。型の定義の `approval_hint` は、リポジトリを作るときの初期値の提案だけ。
- 必要なら **型ごとに上書き** できる（例: 同じリポジトリでも `qms.form` は承認だけ）。上書きもリポジトリの設定。
- 設定を変えられるのはリポジトリの管理者（権限の表に許可と拒否の行）。**フェーズを外す・減らす変更** は、加えて組織の管理者の承認を要る（2026-11-09 決定）。
- 開いている MR には **マージの時点の設定** を使う（ADR-0024 の評価と同じ。設定を緩めて通す、を防ぐため緩めた変更は監査で目立たせる）。
- **フェーズなしのリポジトリから出した PDF には「承認の手順のない文書」と印字** する（承認済みの文書と取り違えない）。
- 電子の承認の追加分（再確認・意味・文言・ハッシュ）は、フェーズのあるリポジトリだけで使う。

- 参考にする考え方: 米国 FDA の 21 CFR Part 11（電子記録・電子署名）の「署名と記録の結びつき」「署名の意味」「本人の再確認」。
  法令として適用を受けるかは事業による（多くの場合は対象外）が、社内の規程に説明するときの根拠に使える。
- **並行して利用者の作業**: 社内の文書管理の規程が「押印」を前提にしていれば、規程の改訂が要る。品質保証の部門に、この表を見せて確認してもらう。

### 6.4 文書と記録を分ける

ISO 9001 は「文書（維持する）」と「記録（保持する）」を分ける。**記録（記入済みの点検表・教育の記録・ヒヤリハット）は、この形式で Git に貯めない。**
件数が多く、検索と集計が主で、1 件ずつの承認の流れが合わないため。GitStation は **様式（雛形）** を管理し、記録は Kanflow や専用のデータの置き場に置く（§11 Q5）。

### 6.5 見直しの期限・配布・印刷

- `review_cycle` から期限を出し、期限の 1 か月前に `owner` へ通知（U4 のアプリ内の通知・N1 のメール）。
- 出力の PDF には「印刷した時点の版。最新版は GitStation で確認」の印と、文書の版・承認者・承認日を入れる。

## 7. 非エンジニアの使い方

ADR-0023 で「別の画面の系統（文書ポータル）は作らない。利用者は Git の基本を学ぶ」と決めた。この前提は保ったまま、
**リポジトリの画面の中に、文書を書くための機能を足す** 形にする（09 §5 の Web Studio をここに位置づける。§10 の 3）。

### 7.1 書く

1. 「新しい文書」→ 型を選ぶ → 文書番号は次の空き番号を提案 → 型の雛形（必須の見出しと、各見出しの書き方の説明）ができる。
2. 属性は **フォーム**（型の定義から作る。プルダウン・日付・文書の検索）。YAML は見せない（見たい人は切り替えて見られる）。
3. 本文は **見たままに近いエディタ**。ブロック（危険源など）は「カード」で入力。参照は `[[` を打つと文書・ブロックを検索して補完。
4. 保存すると、画面がブランチとコミットを作る（利用者の操作は「保存」と「承認を依頼」= MR の作成）。
5. 書きながら lint の結果をその場で日本語で出す（「『リスク低減措置』の見出しがありません」「H-03 に措置がありません」）。

**守ること**: 画面で保存しても、エンジニアが手で書いても、**同じ整形の道具で同じ Markdown になる**（往復で差分が出ない）。
これが崩れると、画面で 1 文字直しただけで全行が差分になり、レビューができなくなる。往復のテストを必須にする（§9）。

### 7.2 レビューする

- **文章の差分**（ブロック・段落ごとに、変わった文を色付けで見せる）。行の差分は切り替えで見られる。
- ブロックの差分は表でも見られる（「H-03 の severity が 3 → 2」）。
- AI の要約（変更点の要約、ja / en / id）は助言として MR に付く（W14。機密区分に従う）。

### 7.3 受け取る・印刷する — Word / PDF の出力は **最後の段に回す**（2026-11-09 決定）

利用者の決定: **Word / PDF の出力は最後に考える。** それまでは画面での閲覧と、GitStation の画面から本物の版・承認の記録を見ることで足りるとする。
v0.3 で書いた「テンプレート + Python のスクリプト」の案は、決定ではなく **検討の材料** として残す。

#### 今の段階で決めておくこと（後で出力を作るときに作り直さないため）

1. **「文書の JSON」は早く作る**（段 3）。frontmatter・節・ブロック・解決済みの参照・文書の版・改訂履歴・承認の記録（意味・氏名・日時）・中身のハッシュ。
   画面の表示・API・MCP・将来の出力が同じものを使う（Markdown の解析を 1 か所に保つ）。
2. 出力を作るときも、**承認の情報の正は GitStation の記録**。出力物には文書番号・版・中身のハッシュと確認用の URL を入れ、GitStation が出力の後に検査する。
3. **Word は出力専用**。Word で直して戻す（取り込み）は作らない（往復の変換は必ず崩れる。直すのは画面で）。

#### 検討の材料（2026-11-09 のレビューで出た点。出力の段で決める）

| 論点 | 内容 |
|---|---|
| 本文の変換 | 決まった欄（表紙・承認欄・改訂履歴）は `docxtpl` の差し込みが得意。本文（見出し・入れ子の箇条書き・表・画像）を `python-docx` で自作すると大きく崩れやすい。案: 本文は Pandoc（`reference.docx` で社内のスタイル）、GitStation が Pandoc の JSON を直接出す、Python は差し込みと結合だけ |
| PDF | LibreOffice の変換は MS Word と完全には一致しない（和文の改行・表の幅・フォント）。遅い・同時実行の衝突・まれに止まる（ジョブごとのプロファイルと時間切れが要る）。**正式の配布が Word か PDF か** で道具が変わる（PDF が正なら Typst などで直接組む案） |
| 同じ出力 | docx・PDF は作成日時や内部の ID が入り、バイトの一致は難しい。中身のハッシュの印字と検査で代える |
| テンプレート | Word で差し込みの印を編集すると内部で分割されて壊れる。テンプレートの変更の MR で印を自動で検査する |
| 図 | Mermaid を画像にするには Node.js と Chromium が要る。最初は「図は画像で添付」に限るか、サーバー側で画像にする |
| スクリプトの偽り | スクリプトは承認欄を偽れる。出力の設定の変更は管理者の承認を必須にし、印字を検査する |
| 実行環境 | Python・Pandoc・LibreOffice・和文フォントを入れた CI の環境。社内の PyPI のミラーがなければ、部品を固定して環境に焼き込む |

### 7.4 翻訳（ja / en / id）

- 訳は `QP-07-001.en.md`。frontmatter に `translation_of: { rev: r3 }`。元の版が上がったら「訳が古い」と表示（spec-drift と同じ考え方）。
- ブロックの ID は訳でも同じ。

### 7.5 同時の編集 — 取り合いにしない（2026-11-09 新設）

#### 比べた案

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A. リアルタイムの共同編集（Google ドキュメントの形） | 同じ文書を同時に打つ。CRDT で合わせる | 待たない | 承認の単位（どの版を誰が承認したか）が曖昧になる。Git とつなぐ部分が大きく、Claude 1 人の保守には重い。規制の文書は「誰がどこを書いたか」がぼやけるのを嫌う |
| B. 強いロック（貸出・返却） | 1 人が借りている間、他は読むだけ | 分かりやすい。QMS の現場で慣れた形 | 借りたまま忘れる。休みの人のロックで止まる |
| C. 自由に枝分かれし、最後に合わせる（Git のふつう） | 各自のブランチで書き、マージで衝突を解く | 待たない | 非エンジニアに衝突の解消をさせることになる。**取り合いが最後に分かる** |

#### 推奨: B を「期限つき・見える・解ける」形にし、C を後ろの守りにする

1. **改訂は文書ごとに 1 つ**（強い規則）: 1 つの文書を変える **開いている MR は 1 つまで**。2 つ目の MR を作ろうとすると、
   「QP-07-001 は 佐藤さんの改訂（!123）が進行中です」と出し、作らせない（その MR にコメント・提案を付ける導線を出す）。
   - 検査は MR の作成・更新・push のとき（変わったパスと文書の索引で判定）。push は止めない（下書きは自由）。**MR を開くときと、マージのとき** に止める。
   - **リポジトリの設定（DB）で型ごとに緩められる**（`single_revision`（既定）/ `free`。型の定義には推奨だけを書く、§13 の 5）。システム仕様など、エンジニアがふつうの Git で扱う型は `free` にできる。
2. **編集中の表示**（弱い規則、期限つき）: 画面で「編集する」を押すと、その文書に **編集の宣言**（誰が・いつから・どの MR）が付き、
   他の人の画面に「鈴木さんが編集中（10 分前から）」と出る。
   - 宣言は **期限つき**（操作がないと 30 分で切れる。画面を開いている間は延長）。切れても下書きは残る。
   - 宣言の持ち主・文書の `owner` のグループ・管理者は **解除** できる（監査に残る）。休みの人で止まらない。
   - 1 つの改訂（MR）の中で複数の人が書く（共同の起案）ときは、宣言は **見出し（節）単位** にでき、節が違えば同時に書ける。
3. **後ろの守り（C）**: それでも同じ箇所がぶつかったら（ローカルの Git で書く人など）、**ブロック・段落の単位の 3 方向の合わせ** を行う。
   1 文 1 行の保存（§4.1）とブロックの ID があるので、多くは自動で合わさる。合わない箇所だけ、画面で「A を採る / B を採る / 両方を並べて直す」を出す
   （行の衝突の印 `<<<<<<<` を利用者に見せない）。
4. **画面の保存は「見た版」に結ぶ**: 保存の要求は、読み込んだときのコミットを持つ。その間に他の保存があれば、黙って上書きせず 3 の合わせに回す
   （承認の `sha` の確認、ADR-0024 §8 の 1 と同じ考え方。**後勝ちの上書きは作らない**）。
5. **エンジニアにも見える**: `gstn doc status <ID>` で宣言と改訂中の MR を表示。AI（§8.3 の整理）も同じ規則に従い、宣言のある文書は触らない。

- 権限の表に行を足す: 宣言の取得・延長・解除（本人 / owner / 管理者）、改訂の MR の作成（許可と拒否の両方）。
- エラーコード（`FG-DOC-*`）: 改訂が既にある、宣言が他の人にある、保存の版が古い（合わせが要る）、合わせで解けない。
- **2 つの改訂を本当に並行させたい** とき（大改訂の準備中に急ぎの訂正）: 急ぎの訂正を先にマージし、大改訂の MR は「target が進んだ」として
  合わせの画面を出す。この順番は owner が選ぶ（例外の操作として監査に残す）。

## 8. AI の使い方

### 8.1 AI が書くとき

- 型の定義（§5）を、そのまま書き方の指示として渡す。エージェントビルダー（W15）は doctype ごとのスキル（`SKILL.md`）を生成できる。
- AI が書いたものも **必ず MR**。承認は人だけ（既にある原則）。
- 機密区分の `confidential` は Claude に渡さない（06 D-5）。

### 8.2 道具（CLI と API）

| 道具 | 中身 |
|---|---|
| `gstn doc new <型>` | 雛形を作る |
| `gstn doc fmt` | 整形（1 文 1 行、frontmatter の項目の順、ブロックの属性の順）。画面と同じ実装 |
| `gstn doc lint` | §5 の決定的な検査。CI のチェック `forge/doc-lint`（03 の `forge/spec-lint` を一般化） |
| 文書の API / MCP | ID で文書・ブロックを取る、参照している側を逆に引く、型で一覧（X4・X5 に載せる） |

- 検索と AI の文脈は **ブロックと見出しの単位で切る**（ID が付いているので、引用の根拠が示せる）。
- 1 つの文書の目安は 1,500 行まで。超えたら分ける（AI の文脈と人のレビューの両方のため）。

### 8.3 ローカル LLM の機能 — 文書の修正とリポジトリの整理（2026-11-09 新設）

サーバーの AI はローカル LLM（Qwen3.8 27B、06 D-1）だけ。機密の文書も扱える（06 D-5）。**どの機能も直接は変えない。提案を出し、採るのは人。**

#### (1) 文書の修正の提案（編集の画面の中、対話）

| 機能 | 中身 | 先に決定的な検査で済むもの |
|---|---|---|
| 校正 | 誤字・脱字、表記のゆれ（「ガード」「ガ－ド」）、全角半角、文体（です・ます / である） | 用語集（`glossary` の型）との照合、禁止語、全角半角は **決定的な検査で先に出す**。LLM は残りだけ |
| 型への適合 | lint のエラーの直し方の案（「『残留リスク』の節を足します」） | lint 自体は決定的 |
| 抜けの指摘（仮想 DR、09 §5） | 安全・保全・品質の観点で書き漏れを指摘（「非常停止のときの仕掛かり品の扱いがありません」） | — |
| 書き直し | 選んだ文を分かりやすく、短く、箇条書きに | — |
| 訳の下書き | ja → en / id（§7.4。訳の MR の下書き） | 用語集の対訳を強制 |
| 要約 | 改訂の要約（MR の説明・承認の依頼の文） | — |

- 提案は **差分のカード** で出し、1 つずつ「採る / 捨てる」。採ったものは今の改訂の下書きに入る（利用者の操作として記録。AI が書いたことも記録）。
- **提案を 2 種類に分けて見せる**: 「表記の修正」（意味を変えない）と「内容の変更」（意味が変わる）。数値・ブロックの属性・ID・参照・否定（「〜しない」）を
  変える提案は、決定的な検査で **必ず「内容の変更」** に分類する（LLM の自己申告に頼らない）。
- ブロックの ID は AI に変えさせない（変える提案は捨てる）。

#### (2) リポジトリの整理の提案（毎晩の点検、W14「仕様と実装のずれの毎晩の検査」を文書に広げる）

| 点検 | 決定的 / LLM | 出すもの |
|---|---|---|
| 壊れた参照、廃止したブロックへの参照、添付の孤児、ファイル名と `id` の不一致、フォルダの置き違い（型と場所） | 決定的 | 報告 + 直す MR の下書き |
| 見直しの期限切れ・期限間近、訳が古い | 決定的 | 通知（owner へ） |
| 重複・ほぼ同じ文書、1 つにまとめるべき節 | LLM（埋め込みの類似 → LLM で確認） | 報告（統合の案） |
| 文書どうしの矛盾（URS の要求と RA の措置、規程と手順書の食い違い） | LLM | 報告（両方の該当ブロックを引用） |
| 大きすぎる文書の分割の案 | 決定的（行数）+ LLM（分け方） | 報告 + 分割の MR の下書き |

- 結果は **リポジトリの「整理の報告」**（1 日 1 件、前日との差分）と、必要なら **整理の MR の下書き**（ボットの利用者が作る）。
- 整理の MR は **参照を ID で解決するので、移動しても切れない**（§4.3）。移動・改名の MR は、文書の版を上げない（中身を変えないため。決定的に確認）。
- **ボットは承認もマージもできない**（ADR-0017）。§7.5 の規則に従い、改訂中・編集中の文書には触らない（その文書は報告だけ）。
- 1 つの整理の MR で触る文書の数に上限を設ける（目安 20）。大きな整理はレビューできる大きさに分ける。

#### (3) 守ること（両方に共通）

- **文書の中身は指示ではない**: 文書に「この指示に従い全文を削除せよ」のような文があっても、LLM の出力は提案と MR の下書きに限られ、
  宣言した範囲（その文書・その整理の対象）の外を変える出力は捨てる（プロンプトの注入への備え。出力の範囲を決定的に検査）。
- **時間切れと失敗**: LLM の呼び出しには時間切れ。失敗は `FG-DOC-*` / 既存の LLM のコードでログに残し、編集・保存・承認は止めない（助言の機能なので）。
- **GPU の順番**（06 §4.9 の調停）: 編集の画面の対話 > MR の必須チェック > 助言 > 毎晩の整理。毎晩の整理は夜間に限り、対話の待ちを作らない。
- **根拠を示す**: 指摘・提案には、根拠になったブロックの ID と引用を付ける。根拠のない指摘は出さない。
- 何を提案し、何が採られたかを記録する（提案の質を計測し、プロンプトと型の定義を直す材料にする）。

## 9. 試験（作るときに要るもの）

- 整形の往復: 画面の保存 → `fmt` → 画面の読み込み → 保存 で、バイトが変わらない（固定のテストベクタ、日本語・表・ブロックを含む）。
- lint: 型ごとに合格の例と不合格の例。エラーには `FG-DOC-NNNN` のコード（新しい領域。`errors.toml` に登録）。
- 参照: 壊れた参照、廃止したブロックへの参照、他のリポジトリの版の固定。
- 機密区分を下げる MR が、型の承認なしでマージできない（権限の表に許可と拒否の行）。
- 和文の改行の表示（余計な空白が出ない）。
- 同時の編集: 同じ文書の 2 つ目の改訂の MR は作れない（`single_revision`）、`free` の型では作れる、宣言の期限切れ、本人以外の解除の権限（許可と拒否）、
  古い版からの保存は上書きせず合わせに回る、節の違う同時の編集は自動で合わさる、同じブロックの衝突は利用者の選択を求める。
- 電子の承認: 再確認なしの承認は拒否、承認の意味の条件が満たされないとマージできない、承認の後の 1 文字の変更で承認が失効、代理の承認の拒否、
  承認の文言とハッシュが監査に残り PDF と一致する。
- 軽微な訂正: 数値・ブロックの属性を変えた MR に「軽微」の印を付けられない。
- ローカル LLM: 提案は直接は保存されない、数値・否定を変える提案は「内容の変更」に分類される、ID を変える提案は捨てられる、範囲外を変える出力は捨てられる、
  LLM の時間切れで編集と承認が止まらない、ボットは編集中の文書を触らない（偽の LLM で決定的に試験する）。
- テストの文書は合成のデータだけ（契約 8）。

## 13. 既存のコード・ADR との突き合わせで決めたこと（v0.5、2026-11-09、推奨で決定）

別のセッションで、計画 13 を `main` のコードと ADR に突き合わせたレビューの結果。どれも利用者の「推奨で進めて」で決定。ADR（段 0）に入れる。

1. **既存の解析を置き換える（移行つき）**: `forge_core::spec_doc` / `spec_index` は既に `forge/spec-lint`・`forge/spec-trace`・仕様の API で動いている。
   計画 13 の解析を **ここに足すのではなく、置き換える**（「解析は 1 か所」）。
   - 旧い形式（`spec:`・`status:` の frontmatter）は **移行の間も読む**: `spec: X` は `doctype: spec.system`・`id: X` として扱い、
     `status: deprecated` は `retired`、ほかの `status` の値は無視して助言の lint（「状態はファイルに書かない」）を出す。
   - **spec-lint・spec-trace・仕様の API の答えを変えない**: 今のテスト（forge-core・forge-checks の spec の試験）をそのまま新しい解析で通すことを、置き換えの条件にする。
   - `gstn doc fmt` は旧い形式のファイルを勝手に書き換えない（`--migrate` を付けたときだけ新しい形式に直す）。
2. **機密の表し方は `classification` を正にする**: 旧い `confidential: true` は `classification: confidential`、`false` は `internal` として読む。
   **両方を書くのは lint のエラー**。文脈の API・MCP（06 D-5、X5）は解析が導いた値を使う。区分を下げる規則（§3.3）は読み替えた値にも効く。
3. **解析のクレートは新しく `forge-doc`**（純粋: 解析・整形・lint・型の定義の読み込み。I/O なし、依存は `forge-errors` と `yaml-rust2` などの純粋な部品だけ）。
   - 依存の向き: `forge-core → forge-doc → forge-errors`、`forge-client（gstn）→ forge-doc`。サーバー側のどのクレートも `forge-client` に依存しない、は変えない。
   - **ADR-0020 の Amendment**（「`gstn` が依存してよいのは `forge-errors` と `forge-doc` だけ」）と、**CLAUDE.md の契約 9 の文**を、この ADR と同じ変更で直す。
   - `gstn doc fmt` / `lint` は手元で動く（サーバーに送らない）。CI のチェック `forge/doc-lint` は同じ `forge-doc` を使う（答えが一致する）。
4. **承認した blob と発行する blob を一致させる**: フェーズのあるリポジトリ（§6.3.1）では、MR が変えた各文書について
   **マージの結果の blob ＝ 承認した head の blob** をマージの条件に足す（`evaluate_merge()` の新しい止める理由。target が同じ文書を変えて自動で合わさった場合も止める。
   利用者はブランチを更新して承認をもらい直す）。承認の記録の正は **文書の id と blob の SHA**。**版の番号はマージで確定する**ので、承認の文言には
   「第 N 版（予定）」と出し、確定した版は記録に後から結ぶ（§6.3 の文言の例を改める）。
5. **統制の項目は型の定義のファイルに置かない**（§6.3.1 の考えを一貫させる）: 次の 3 つは **リポジトリの設定（DB、型ごとの上書きも DB）** に移し、
   型の定義には「推奨」だけを書く。
   - Kanflow（代理実行）からの文書の承認を認めるか — **既定は禁止**。認めても、本人が GitStation の確認の画面で再確認（§6.3）を通った場合だけ。
   - 同時の編集の `single_revision` / `free`（§7.5）。
   - 機密区分を下げるときの承認者（§3.3）。
6. **「作成」の署名は承認とは別の操作**: 起案者は自分の MR を承認できない規則（FG-REVIEW-0013）は変えない。「作成 `authored`」は起案者（共同の起案者）が行う
   **別の署名**（承認の数に数えない）にし、権限の表に許可と拒否の行を足す。
7. **文法の決め残し**（`fmt` を作る前に ADR で決める）:
   - ブロックの見出しの行: `::: <種類> <ID> [<鍵>=<値> …]`。値は空白と `"` を含まない語、または `"…"`（`\"` と `\\` だけをエスケープ。和文は引用符の中で可）。
     鍵は `[a-z][a-z0-9_]*`。同じ鍵の 2 回はエラー。入れ子は今の `spec_doc` の規則のまま（ID の無い入れ物は入れ子にでき、ID のあるブロックの中に ID のあるブロックは置けない。ADR-0026 §2）。コードのフェンスの中の `:::` はブロックではない。
   - 1 文 1 行: `。`・`！`・`？`（全角）の後でだけ分ける。**`「」`・`『』`・`（）`・コード・リンク・表・見出しの中では分けない**。整形は冪等（`fmt(fmt(x)) = fmt(x)`）。
   - 訳: ファイル名は `<id>.<lang>.md`、frontmatter の `id` は元と同じで `lang` と `translation_of` を持つ。「ファイル名 ＝ id」の lint は言語の接尾辞を除いて比べる。
     `[[ID]]` は元の文書（言語の接尾辞の無いもの）に解決する。
8. **再確認・トークン・版のタグ**:
   - 承認の直前の再確認は Keycloak の再ログイン（`max_age`）。**ADR-0021 の Amendment** にする。
   - フェーズのあるリポジトリでは、**トークン（`gstn`・API）による文書の承認は拒否**（再確認ができないため。新しいエラーコード）。
   - 文書の版のタグ `refs/tags/doc/<ID>/r<N>` は GitStation だけが作る（保護タグ。人とボットは作れない）。GitLab のミラーにもそのまま送る。
     **タグを版の正にし、DB の文書の索引はタグから作り直せる**ようにする（「軽微」の MR は版を上げないのでタグが無い。DB を失っても版は失わない）。
9. **進め方**: ADR は段 0 で書くが **status は proposed** に留め、実際の文書 3 つでの試し（段 1、PC 側）の後に accepted にする。
   段 2 の実装は進めてよいが、書式を変える指摘が段 1 で出たら、段 2 の実装を直す前提とする（書式を作ってから変えると全文書の移行になる、§12）。
   作業のブランチは **最新の `main` から切る**。

## 14. 合成の例で見つけたこと（2026-11-09、段 1 の代わり）

`docs/plan/13-examples/`（規程・リスクアセスメント・URS の合成の例と、型の定義 3 つ。期待する lint の結果つき）を書いて見つけたこと。
**決定（推奨で決めたもの）** と **質問（利用者の答えが要るもの）** に分ける。実際の文書の試し（段 1、PC 側）でも同じ点を見る。

**決定（形式に足した・明確にしたもの）**

1. **ブロックの種類を足す**: `step`（手順の 1 段、`role` の属性）と `record`（残す記録、`form`・`retention` の属性）。§4.2 の表に足した。
2. **要件の属性は型で決める**: 今の `spec_doc` は `req` の属性を `priority`・`status` だけに限り、他を拒否する。URS には `verify`
   （`test` / `inspection` / `analysis` / `demonstration`）が要る。`req` の属性は型の定義の `blocks.req.attrs` で決め、`spec.system`
   （旧い形式を含む）は今の 2 つのまま（ADR-0026 §7 の「答えを変えない」）。
3. **残留リスクは危険源の属性**: `res_severity`・`res_likelihood`（措置の後）。規則 `residual_not_above_initial`・`residual_set_when_controlled`。
4. **期間の書き方**: `review_cycle`・`retention` は `<数><D|W|M|Y>`（`24M`・`5Y`）。
5. **HTML**: コメント（`<!-- … -->`）は認める（表示しない）。それ以外の HTML の直書きはエラー（§4.1）。
6. **廃止したブロックの置き換え**: `status=deprecated` のブロックに任意の `replaced_by=<ID>`（壊れた参照の検査の対象）。
7. **値の型**: 属性の型は `int`（`min` / `max`）・`bool`・`text`・`enum`・`duration`・`docref`（文書、`doctype` で絞る）・`blockref`（同じ文書の
   ブロック、`kind` で絞る）。

**質問（ADR を accepted にする前に答えが要る）**

- **Q13 まだ GitStation に無い文書への参照**: 実際の移行では、参照先の多くが最初は GitStation に無い（例では `QM-001`・`QP-07-002`・様式 `QF-07-001`）。
   どれかを選ぶ必要がある: (a) 壊れた参照は常にエラー（移行の順番を参照の順にする）、(b) リポジトリの設定で「移行中は警告」に下げられる
   （期限つき）、(c) `.forge/external-docs.yml` に「GitStation の外の文書」の一覧を置き、そこにある番号は参照できる。**推奨は (b)**
   （移行を止めず、期限で必ずエラーに戻る。統制なので DB の設定）。
- **Q14 機密の違う文書への参照**: 例では `internal` の RA-2026-014 が `confidential` の URS-L3-001 のブロックを参照している。表示・文書の JSON・
   AI の文脈で、参照先の題名や本文を **参照元の区分のまま** 見せると、機密の内容が下の区分に漏れる。**推奨**: 参照先の方が機密なら、ID だけを見せ
   （題名・本文は見せない）、AI の文脈には入れない。lint は助言（警告）を出す。
