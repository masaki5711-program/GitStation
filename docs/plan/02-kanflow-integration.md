## 1. 目的

要件（kanflow の PBI・受入基準・スプリント）と、実装（forge のブランチ・MR・
パイプライン・デプロイ）を **双方向に** 結びつける。単なるリンクの表示にとどめず、
**要件の情報をマージの判断に使い、開発の事実を計画と振り返りに戻す。**

### GitLab ではなぜ実現できなかったか

| GitLab での限界 | forge で可能にすること |
|---|---|
| 外部の課題管理ツールとの連携は、ほぼリンクの表示と、`Closes #123` による自動クローズに限られる | イベントに基づいて状態を双方向に同期する。kanflow 側のルール（PO による完了確認など）も守る |
| マージの条件に外部ツールの状態を入れるには、CI のジョブで外部 API を呼ぶなどの工夫が要る | **Checks API** に kanflow を直接の提供者として登録できる（§5.4） |
| AI 機能（GitLab Duo）はクラウド前提で、社外にコードを出せない環境では使えない | ローカル LLM で、**PBI の受入基準と差分を突き合わせる** |
| 自前のプロジェクト管理ツールの文脈（スプリント、ベロシティ、デイリースクラム）を、コードレビューやデプロイに反映できない | 両方のデータを持つ前提で機能を設計できる |

## 2. 用語と識別子

| 用語 | kanflow 側 | forge 側での参照形式（提案） |
|---|---|---|
| プロジェクトの結びつけ（バインディング） | Project | kanflow のプロジェクト 1 つに、forge の **仕様（`spec`）とシステム開発（`system`）のリポジトリを複数** 結びつけられる。**kanflow の画面から API で登録・解除できる**（`03` §7.1） |
| PBI | ProductBacklogItem（プロジェクト内の連番 `displayId`） | **`PBI-<displayId>`**（例: `PBI-123`）。**既存の kanflow の形式をそのまま使う**（ユーザー確認済み） |
| タスク | SprintBacklogItem | `PBI-<displayId>.<n>`（例: `PBI-123.2`。PBI 内での連番。**提案**。K-3 を確認してから決める） |
| Icebox | IceboxItem | `ICE-<n>`（例: `ICE-45`。**提案**） |
| リリース | ReleaseBacklogItem（`releaseVersion`） | 版の文字列（例: `v1.4.0`）で突き合わせる |
| ユーザー | User（`email`、`employeeNumber`） | email で突き合わせる。社員番号は補助に使う |

- 参照はコミットメッセージ、ブランチ名、MR のタイトルと説明から検出する。検出の正規表現は
  バインディングごとに設定できる。
- **実際の書き方は 1 通りではない**（現在の「開発」タブの表示から確認、§8.3）。
  ブランチ名は `fix/L2-pbi-43-e1-until-precision` のように **小文字で、途中に接頭辞が付く**。
  MR のタイトルは `(PBI #43)` の形。既定の検出規則は **大文字小文字を区別せず、
  `PBI-43` / `pbi-43` / `PBI #43` / `PBI#43` / `PBI_43` のいずれも拾う**（`/(?<![a-z0-9])pbi[-_ ]?#?(\d{1,7})(?![0-9])/gi`。
  2026-10-30 訂正: 以前の `(?i)\bpbi[-_ #]?(\d+)\b` は区切りが 1 文字だけなので `PBI #43` を拾えず、`\b` は `x_pbi-4` も拒む。
  kanflow の第 0 段 K1 と同じ規則にし、バインディングの既定値は kanflow の規則と一致させる）。
  `pbi-430` を `pbi-43` と誤認しないよう、数字の後ろは境界で区切る。検出規則には、実際に
  使われている書き方の一覧をテストケースとして持たせる。
- 例: ブランチ `feature/PBI-123-login-form`（**既存の kanflow の規則**）、コミット `fix(auth): lock after 5 failures (PBI-123)`。
- **`PBI-123` はプロジェクト内の連番なので、それだけではどのプロジェクトか決まらない。** どのプロジェクトかはバインディングで決める。forge のリポジトリが結びついている kanflow のプロジェクトの中で `PBI-123` を探す。1 つのリポジトリを複数の kanflow のプロジェクトに結びつけることは禁止する（参照があいまいになるため）。
- forge の内部と API では、作業項目を **`(kanflow のプロジェクト ID, PBI-123)` の組** で識別する。
- 自動で検出するほか、MR の画面から手動でリンクを付け外しできる。

## 4. 作業項目プロバイダ（forge → kanflow の契約）

forge は kanflow を直接知らない。`WorkItemProvider` という **汎用の契約** を定め、
kanflow はその契約を実装する（forge 内の Issue や、将来の他のツールも同じ契約で差し込める）。

### 4.1 forge 側の trait（概略）

```rust
pub trait WorkItemProvider: Send + Sync {
    /// 参照の文字列（PBI-123 など）を作業項目に解決する。
    async fn resolve(&self, ctx: &CallCtx, r: &WorkItemRef) -> Result<WorkItem, ForgeError>;
    /// 開発の事実（MR のマージなど）を通知する。状態をどう変えるかは提供者が決める。
    async fn notify(&self, ctx: &CallCtx, ev: &DevEvent) -> Result<NotifyOutcome, ForgeError>;
    /// 参照の検出に使う正規表現（バインディングごと）。
    fn ref_pattern(&self, binding: &Binding) -> &Regex;
}
```

### 4.2 kanflow が実装する HTTP API（提案）

ベースパス: `https://<kanflow>/api/integration/v1`。認証は forge 用の連携トークン
（`Authorization: Bearer`）。**すべてのリクエストに `X-Request-Id`** を付け、kanflow 側の
ログでも追跡できるようにする。

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/projects/{project_id}` | プロジェクト（ID、名前、メンバーとロール、今のスプリント） |
| `GET` | `/projects/{project_id}/work-items/{ref}` | 作業項目 1 件（PBI / タスク / Icebox） |
| `GET` | `/projects/{project_id}/work-items?refs=PBI-1,PBI-2` | まとめて取得（MR に複数の参照があるとき） |
| `POST` | `/projects/{project_id}/work-items/{ref}/dev-events` | 開発イベントの通知（§5.5 の形式）。冪等キーでの重複排除が必須 |
| `POST` | `/projects/{project_id}/icebox` | Icebox への登録（F-12、F-16） |
| `GET` | `/sprints/{id}/members/workload` | 担当者別の負荷（F-7） |

**`GET /projects/{project_id}/work-items/PBI-123` の応答例**

```json
{
  "ref": "PBI-123",
  "type": "pbi",
  "title": "ログイン失敗が続いたらアカウントをロックする",
  "status": "ready",
  "user_story": "管理者として、不正ログインを防ぐために、連続失敗時にロックしたい",
  "acceptance_criteria": [
    { "id": "ac-1", "text": "5 回連続で失敗したら 30 分ロックする" },
    { "id": "ac-2", "text": "ロック中はエラーメッセージで解除時刻を示す" }
  ],
  "sprint": { "id": "spr_...", "name": "Sprint 24", "status": "active" },
  "po": { "email": "po@example.internal" },
  "assignees": [{ "email": "dev@example.internal" }],
  "tasks": [{ "ref": "PBI-123.1", "title": "ロック判定", "status": "in_progress" }],
  "url": "https://<kanflow>/projects/.../backlog/...",
  "updated_at": "2026-10-26T09:00:00+09:00"
}
```

- 受入基準は **項目ごとの配列** で返す（F-4 で項目単位に判定するため）。kanflow が受入基準を
  1 つのテキストで持っている場合は、アダプタ側で行ごとに分割する。
- 失敗時は `{ "error": { "code": "...", "message": "..." }, "request_id": "..." }`。
  forge はこれを `FG-INT-xxxx`（連携のエラー）に対応づけて記録する。

## 5. forge の外部 API（kanflow ほかの外部システム向け）

### 5.1 共通の約束

| 項目 | 方針 |
|---|---|
| 形式 | REST + JSON。ベースパス `/api/v1`。**OpenAPI 3.1 を Rust のコードから生成**する（`utoipa`。導入時に `search-first` で比較する） |
| バージョン | URL に含める。v1 の中では後方互換を保つ（フィールドの追加のみ可）。破壊的な変更は v2 |
| 認証 | 個人アクセストークン、サービスアカウントのトークン（どちらもスコープ付き・有効期限必須・ハッシュで保存）。OAuth2 は M8 |
| 識別子 | 外部に出す ID は不透明な文字列。MR はプロジェクト内の連番 `iid` も持つ |
| 一覧 | カーソル方式のページング（`?cursor=…&limit=…`）。`Link` ヘッダで次のページを示す |
| 書き込み | `Idempotency-Key` ヘッダで再送しても二重に実行しない |
| 楽観ロック | 応答の `ETag` を `If-Match` で送ると、競合したときに `412` を返す |
| エラー | `{ "error_code": "FG-…", "user_message": "…", "request_id": "…" }`。内部の情報は出さない（CLAUDE.md §3-3） |
| 流量制限 | トークンごと。`429` と `Retry-After` を返す |
| 追跡 | 受け取った `X-Request-Id` を引き継ぐ。なければ forge が発行し、応答ヘッダで返す |

### 5.3 代理実行（kanflow の利用者として操作する）

kanflow の画面で「ブランチを作る」を押したとき、forge では **押した本人** として
権限を判定し、監査ログにも本人を残す必要がある。

- kanflow はサービスアカウントのトークンに、ヘッダ `Forge-Act-As: user:<email>` を付けて呼ぶ。
- このヘッダを使えるのは、`act_as` スコープを持つサービスアカウントだけ。
- 認可は **サービスアカウントの範囲（結びつけたプロジェクト、許可した操作）と、本人の権限の
  共通部分** で判定する。判定は `forge-auth` の単一判定点で行い、権限マトリクスに行を加える。
- 監査ログには「kanflow（○○さんの代理）」と記録する。
- **セキュリティ上重要な設計のため、ADR と `security-reviewer` のレビューを必須にする。**
  将来は OAuth2 の認可コード方式（本人が同意する）に置き換えられるようにする。

### 5.4 Checks API（kanflow は作業項目チェックを登録する）

| メソッド | パス | 内容 |
|---|---|---|
| `POST` | `/projects/{id}/commits/{sha}/checks` | チェックの作成 |
| `PATCH` | `/projects/{id}/checks/{check_id}` | 状態の更新 |
| `GET` | `/projects/{id}/commits/{sha}/checks` | 一覧 |

```json
{
  "name": "kanflow/work-item",
  "status": "completed",
  "conclusion": "failure",
  "summary": "リンク先の PBI-123 が Ready ではありません（Not Ready）",
  "details_url": "https://<kanflow>/...",
  "annotations": []

```

- `status` は `queued` / `in_progress` / `completed`。`conclusion` は `success` / `neutral` /
  `failure` / `error` / `action_required`。
- チェックの名前は提供者ごとに名前空間を分ける（`ci/…`、`forge/…`、`kanflow/…`）。
  サービスアカウントは自分の名前空間にしか書き込めない。

### 5.5 Webhook（forge → kanflow ほか）

> **改訂あり（ADR-0016、2026-10-27）**: 末尾の「11. ADR-0016 による改訂」が優先する。

**イベントの種類**: §5.8 の全量と同じ（Webhook とイベントの履歴 API は同じイベントを届ける）。主なもの: `push`、`merge_request.opened|updated|approved|merged|closed|reopened`、
`review.submitted`、`check.completed`、`pipeline.started|succeeded|failed`、
`deployment.started|succeeded|failed`、`tag.created`、`work_item.linked|unlinked`。

**共通の形式**

```json
{
  "id": "evt_01J…",
  "type": "merge_request.merged",
  "occurred_at": "2026-10-26T10:15:00+09:00",
  "project": { "id": "prj_…", "path": "app/portal" },
  "actor": { "id": "usr_…", "email": "dev@example.internal", "via": null },
  "work_items": [{ "provider": "kanflow", "project_id": "<kanflow のプロジェクト ID>", "ref": "PBI-123" }],
  "data": { "iid": 87, "target_branch": "main", "merge_commit_sha": "…" }
}
```

| 項目 | 方針 |
|---|---|
| 署名 | `Forge-Signature: t=<unix秒>,v1=<HMAC-SHA256(secret, t + "." + body)>`。受信側は 5 分を超えて古いものを拒否する（再送攻撃の対策） |
| ヘッダ | `Forge-Event`（種類）、`Forge-Delivery`（配信 ID。受信側の重複排除に使う） |
| 配信 | worker が Outbox から送る。タイムアウト 10 秒、指数バックオフで最大 24 時間再試行し、それでも失敗したらデッドレターに入れて `FG-INT-xxxx` を記録する |
| 履歴 | 配信履歴の閲覧と、手動での再送 API（`POST /hooks/{id}/deliveries/{id}/redeliver`） |
| 順序 | 順序は保証しない。受信側は `occurred_at` と、必要なら API で最新の状態を確認する |

### 5.6 kanflow → forge のイベント

kanflow で PBI の受入基準や状態が変わったら、forge に通知してもらう
（受入基準の AI 照合のやり直しと、作業項目チェックの更新に使う）。

| メソッド | パス | 内容 |
|---|---|---|
| `POST` | `/api/v1/integrations/{id}/events` | kanflow からのイベントの受信（`work_item.updated`、`sprint.started|completed`、`release.updated`）。署名の方式は §5.5 と同じ |

### 5.7 イベントの履歴 API（定期取得でも取りこぼさない）

> **改訂あり（ADR-0016、2026-10-27）**: 末尾の「11. ADR-0016 による改訂」が優先する。

kanflow は現在、GitLab を **定期的に取得する** 方式で連携しており、**MR を処理した後
（マージ・クローズ後）は取得できない** という問題がある（§8.2）。forge はこれを、
定期取得のままでも取りこぼしが起きない API で解決する。Webhook（§5.5）は受信口を
作れる連携先のための選択肢とし、**kanflow には第一にこの API を使ってもらう。**

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/v1/integrations/{id}/events?after=<cursor>&limit=100` | 連携に関係するイベントを、発生順に、カーソルの続きから返す |

```json
{
  "events": [
    { "cursor": "c_000981", "id": "evt_…", "type": "merge_request.merged",
      "occurred_at": "2026-10-26T10:15:00+09:00",
      "work_items": [{ "provider": "kanflow", "project_id": "<kanflow のプロジェクト ID>", "ref": "PBI-123" }],
      "data": { "project": "app/portal", "iid": 87, "title": "…", "merged_by": "dev@example.internal",
                "source_branch": "feature/PBI-123-login-form", "url": "…" } }
  ],
  "next_cursor": "c_000981",
  "has_more": false
}
```

| 約束 | 内容 |
|---|---|
| **取りこぼしがない** | イベントは Outbox（`01` §4.2）に、状態の変更と同じトランザクションで書かれる。カーソルは単調に増え、欠番を返さない |
| **何度読んでも同じ** | 同じカーソルからは同じイベントが返る。kanflow は処理が終わってからカーソルを保存すればよい（途中で落ちても読み直せる） |
| **対象を絞る** | 連携に結びついたプロジェクトで、作業項目にリンクしているイベントだけを返す（サービスアカウントの権限の範囲内） |
| **保持期間** | 90 日（設定可能）。保持期間より古いカーソルを指定したら `410 Gone` と `FG-INT-0007` を返す（黙って途中から返さない）。kanflow は開発状況 API（§5.2）で全体を取り直す |
| **リンクは消えない** | 作業項目とのリンクは、検出した時点で forge が保存する。**ブランチが削除されても、MR がマージ・クローズされても、リンクと履歴は残る** |

### 5.8 フル連携 — kanflow に届けるイベントの全量

現在の連携では **クローズした（マージせずに閉じた）MR が kanflow に出ない**（§8.2）。
forge では「どの状態の変化を届けるか」を連携の契約として列挙し、**列挙したすべての変化を
例外なくイベントにする**。ここにない変化は届かない、ということも契約の一部にする。

**MR のライフサイクル**

```
           ┌────────── reopened ──────────┐
           ▼                              │
 opened ─▶ open（draft ⇄ ready）─┬─▶ merged（終端）
           │  updated / pushed   │
           │  review_requested   └─▶ closed（マージせずに閉じた）
           │  approved / unapproved
           │  commented / thread_resolved
```

| イベント | いつ | kanflow での表示（例） | kanflow への影響（F-8。バインディングの設定で変更可） |
|---|---|---|---|
| `merge_request.opened` | MR が作られた | 「MR 作成」 | タスクを `in_progress` に |
| `merge_request.draft_changed` | ドラフト ⇄ レビュー可 | 「レビュー可になった」 | — |
| `merge_request.pushed` | ソースブランチに新しいコミット | MR の下にコミットを追加 | — |
| `merge_request.updated` | タイトル・説明・対象ブランチの変更 | 表示の更新 | **参照が増減したら `work_item.linked` / `unlinked` も出す** |
| `merge_request.review_requested` | レビュアーの指定 | 「レビュー依頼: ○○」 | — |
| `merge_request.approved` / `unapproved` | 承認・承認の取り消し | 「承認 1/2」 | — |
| `merge_request.commented` | コメント・スレッドの解決 | 件数のみ（本文は forge へのリンク） | — |
| `merge_request.merged` | マージされた | 「マージ済み」 | タスクを `done` の候補に |
| **`merge_request.closed`** | **マージせずに閉じた** | **「クローズ（未マージ）」と、閉じた人・理由** | **タスクを `done` にしない。** そのタスクに開いている MR が他にないときは「MR なし」と表示する |
| `merge_request.reopened` | 閉じた MR を開き直した | 「再オープン」 | `opened` と同じ扱い |
| `merge_request.source_branch_deleted` | マージやクローズ後のブランチの削除 | 表示しない（記録のみ） | — |
| `merge_request.conflict_detected` / `conflict_resolved` | 対象ブランチとの衝突の発生・解消（`04` §2） | 「衝突あり」 | — |
| `merge_request.conflict_predicted` | 開いている別の MR と衝突する見込み（`04` C-2） | 「!88 と衝突の見込み」 | 両方の PBI に表示 |

**MR 以外**

| 分類 | イベント |
|---|---|
| ブランチ | `branch.created`（参照を含むブランチが作られた）、`branch.deleted`、`push`（MR のないブランチへの push） |
| コミット | `commit.linked`（参照を含むコミットが既定ブランチに入った。main の取り込みだけのマージは除外、§8.3 O-4） |
| チェック | `check.completed`（CI、AI レビュー、受入基準の照合。結論が変わったときだけ） |
| パイプライン | `pipeline.started`、`pipeline.succeeded`、`pipeline.failed`、`pipeline.canceled` |
| デプロイ | `deployment.started`、`deployment.succeeded`、`deployment.failed`、`deployment.rolled_back` |
| タグ・リリース | `tag.created`（F-10 でリリースと対応づける） |
| リンク | `work_item.linked`、`work_item.unlinked`（手動の付け外し、タイトルの編集による増減） |

**フル連携の約束**

| 約束 | 内容 |
|---|---|
| 状態の網羅 | MR の状態の遷移（上の図）のすべての矢印に、ちょうど 1 つのイベントが対応する。**遷移の一覧から自動でテストを作り**、イベントが出ない遷移があればテストが落ちる |
| 終端の状態も届く | `merged` と `closed` はどちらも終端の状態として必ず届き、その後もリンクと履歴は残る |
| 今の状態も取れる | イベントの履歴（§5.7）とは別に、開発状況 API（§5.2）は **開いている・マージ済み・クローズの MR をすべて** 状態付きで返す（`?state=all` が既定） |
| 追加は後方互換 | イベントの種類を増やしても、v1 のまま。kanflow は知らない種類を読み飛ばせばよい |
| 段階 | MR・ブランチ・コミット・リンクは第 1 段（M3）、パイプライン・デプロイは第 2 段（M4）、AI 系のチェックは第 3 段（M5） |

### 5.9 マージ状況のリアルタイム表示（2026-10-30 追加）

**ユーザーの要望**: 「マージされていったものは、リアルタイムで kanflow 側のプロジェクトに流していって見られるようにする。警告などを含めて」。
自動マージ（`04` M-5）と危険の検査（`04` M-6）で、人の手を介さずにマージが進むようになるため、kanflow のプロジェクトで **何がいつ、どの方式で
マージされ、何が警告付きで止まっているか** をすぐ見られることを必須にする。

| 項目 | 方針 |
|---|---|
| 届け方 | **Webhook（§5.5）で数秒以内に押し出す**。取りこぼしは §5.7 のイベントの履歴をカーソルで読んで埋める（両方とも同じイベント）。kanflow は Webhook を受けたら画面に即時に反映し、定期取得は補助に下げる |
| 届けるイベント | §5.8 の MR の全量に加えて: `merge_request.auto_merged`（方式・通った条件・キューでの位置・マージ結果のパイプライン）、`merge_request.risk_flagged`（`warn` / `stop`、分類、理由、根拠のファイルと行）、`merge_request.auto_merge_stopped`（止めた理由）、`merge_request.risk_acknowledged`（人間が警告を読んで解除した。誰が・どの警告を）、`merge_request.autofix.*`（AI の自動修正の開始・コミット・結果）、`merge_queue.paused|resumed`（緊急停止） |
| kanflow での見え方 | プロジェクトに「マージの流れ」（時系列。自動・人・予約の区別、警告の印）を出す。PBI の「開発」タブにも同じ内容を出す。**`stop` は目立つ警告として出し、誰の判断待ちかを示す**（Maintainer への通知） |
| 設定 | **リポジトリと kanflow のプロジェクトを結びつけたら、追加の設定なしで届く**（連携の設定は簡略に、のユーザーの方針）。Webhook の宛先と署名の鍵は、結びつけの操作の中で自動で登録する |
| 個人情報 | 警告の本文には、根拠の **ファイルと行の位置と分類** だけを載せ、差分に含まれる個人情報らしき値そのものは載せない |
| 段階 | M3: MR の全量と `risk_flagged`（決定的な規則）。M4: `auto_merged`・`auto_merge_stopped`・`autofix.*`・`merge_queue.*`。M5: AI の層の `risk_flagged` |
| kanflow 側の改修 | Webhook の受信口（署名の検証、`Forge-Delivery` での重複排除）と「マージの流れ」の画面。今の kanflow は Webhook の受信がない（§8 の K-5）ので、第 1 段の改修に加える |

## 6. LLM の道具の提供（F-18）

kanflow のチャットは、JSON Schema で宣言した道具をサーバー側のハンドラで実行する方式。
forge はこれと同じ形の **読み取り専用の道具** を提供する。

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/v1/ai-tools` | 道具の一覧（名前、説明、JSON Schema） |
| `POST` | `/api/v1/ai-tools/{name}/invoke` | 道具の実行（代理実行のヘッダで、利用者の権限の範囲に限る） |

| 道具 | 答えられる質問の例 |
|---|---|
| `get_work_item_dev_status` | 「PBI-123 の開発はどこまで進んでる？」 |
| `list_failing_pipelines` | 「今のスプリントで失敗しているパイプラインは？」 |
| `get_flow_metrics` | 「レビュー待ちが長いのはどのプロジェクト？」 |
| `list_open_merge_requests` | 「承認待ちの MR は？」 |
| `get_recent_deployments` | 「先週、本番に何をリリースした？」 |

- kanflow の方針（道具の数を絞る、数値は道具が返し LLM は計算しない、結果に `as_of` を付ける、
  一覧には上限を設ける）に合わせる。
- 将来は同じ道具を MCP サーバーとしても公開する（`01` §3.8 の運用 API / MCP と共通化する）。

## 7. 段階ごとの実装範囲

### 8.1 既存の「開発」タブとの互換（移行の方針）

kanflow はすでに GitLab と連携しているため、forge は **その連携を壊さずに置き換え、
そのうえで拡張する** 順に進める。

| 段階 | 内容 |
|---|---|
| **互換（第 1 段の最初）** | 既存の連携が定期取得している GitLab の API のうち、kanflow が使っているものを forge でも提供する。kanflow 側は接続先の URL とトークンを変えるだけで、「開発」タブが動き続ける。**移行の日に kanflow の改修を必要としない**。ただし、この段階では §8.2 の取りこぼしは残る |
| **取りこぼしの解消（第 1 段）** | kanflow の取得処理を、イベントの履歴 API（§5.7）をカーソルで読む方式に切り替える。**kanflow 側の改修はこの部分だけ**で、定期取得という仕組みはそのまま使える |
| **拡張（第 1 段〜）** | forge の契約（§4、§5）に沿った情報を追加で提供する。チェックの結果、AI レビューの要約、受入基準の照合結果、デプロイの状況などを「開発」タブに出せるようにする |
| **整理（第 2 段以降）** | 互換用の口を使う箇所がなくなったら、互換方式を廃止する時期を決める |

- 互換のために提供する範囲は、**kanflow が実際に使っている部分だけ** に限る
  （GitLab の API 全体を再現することはしない）。
- 互換の口も、認可の単一判定点、エラーコード、監査ログの対象にする。
- 互換の範囲を決めるには、最新の kanflow の連携部分のコードを読む必要がある（§10-1）。

### 8.2 現在の連携の問題 — MR の処理後に取得できない

| 項目 | 内容 |
|---|---|
| 症状 | **クローズした（マージせずに閉じた）MR が「開発」タブに出ない**（ユーザーからの報告、2026-10-26）。マージ済みの MR は表示される（§8.3） |
| 原因の仮説 | ~~定期取得が「開いている MR」と「マージ済みの MR」だけを対象にしている~~ → **最新のコードで否定された**（`state=all` で取得し、行を消さない）。本当の原因の候補は §8.4 の「取りこぼしの原因」を参照 |
| 構造上の原因 | いずれの仮説でも、**「今の状態」を取りに行く方式は、取得と取得の間に起きた変化を取りこぼす** |
| forge での解決 | (1) **フル連携（§5.8）**: クローズを含むすべての状態の変化をイベントにする。(2) 状態ではなく **イベントの履歴** をカーソルで読ませる（§5.7）。(3) リンクを検出した時点で保存し、ブランチが削除されても消さない。(4) 開発状況 API（§5.2）は、開いている・マージ済み・クローズの MR をすべて返す |
| 回帰テスト（M3 で作る） | **マージせずにクローズした MR の `merge_request.closed` が返り、開発状況 API にも「クローズ」で出ること**／クローズ → 再オープン → マージが順に返ること／「ブランチを削除するマージ」のあとでもリンクとイベントが取得できること／取得の間隔中に「開く → クローズ」が起きても両方のイベントが返ること／保持期間を過ぎたカーソルは 410 になること |
| 移行の手当て | GitLab 時代に取りこぼした過去の MR は、forge に移行するときに Git の履歴（マージコミットとブランチ名）から復元し、イベントとして取り込めるか検討する |

- kanflow が呼ぶ GitLab の API（§8.1 の互換の範囲）: `GET /projects/:id`、`/merge_requests`（一覧と 1 件。`head_pipeline` のため）、`/repository/{branches,commits,tags,tree,compare,files/:path/raw}`、`/releases`（`gitlab-client.ts:184-219`）。

**取りこぼしの原因（§8.2 の訂正。本番では未確認）**
1. 正規表現が `PBI #43` に一致しない（`#` があるため）。O-1 で見たタイトルの書き方そのものなので、ブランチ名に番号がない MR はつながらない。

### 11.1 §5.5 Webhook と §5.8 のイベント名

| 項目 | 改訂 |
|---|---|
| イベント名 | `push` は **`repository.pushed`** に改名する（§5.8 の `push`（MR のないブランチへの push）も同じ）。名前は `<集約>.<過去形の動詞>` で 2〜4 段。`merge_request.autofix.applied` のような 3 段も可 |
| `repository.pushed` の大きさ | 1 回の push に 1 件。ref の更新は最大 100 件 + `total_refs`、コミットは ref ごとに 20 件 + `total_commits`。超えた分は `refs_truncated: true` で明示し、受け手は API で取る（黙って切り詰めない）。payload は 64 KiB まで |
| 署名 | `Forge-Signature: t=<unix秒>,v1=<HMAC-SHA256(secret, t + "." + delivery_id + "." + body)>`。`delivery_id` は `Forge-Delivery` ヘッダと同じ値。`t` は再試行のたびに作り直す。秘密の入れ替えの 24 時間は新旧 2 つの `v1` を付ける。受信側は 5 分を超えて古いものを拒否する |
| `actor` | 例から `email` を除く（payload に email は入れない）。**`user_email` スコープを持つ連携にだけ**、読み取りの時点で `actor.email` を足す（**kanflow の連携には与える**、ユーザー決定 2026-10-27）。`actor.via` は必ず出す（代理実行は kanflow）。外部向けの ID は不透明な文字列（`prj_…`、`usr_…`、`evt_…`）。`project.path`・MR のタイトル・ブランチ名・表示名は、その時点の表示用のスナップショット |
| 送り先 | 運用者の許可リスト（`webhook.allowed_targets`）に載せたホストだけ。**既定は空**なので、登録するまで Webhook は配れない。`https` だけ。ループバック・リンクローカル・メタデータなどは常に拒否 |
| 種類ごとの可視性 | Webhook に出せる既定の種類は `integration` の分類（`merge_request.*`、`repository.pushed`、`branch.*`、`tag.created`、`pipeline.*`、`check.*`、`work_item.*`、`commit.linked`。プロジェクトの Reporter 以上）。`member.*`・`protected_ref.*`・`deployment.*` は種類を明示した Webhook だけ、`token.*` とインスタンス全体のイベントは出さない |
| 無効化 | 50 回続けて失敗するか 24 時間失敗し続けたら自動で無効にする（`FG-INT-0011`） |

### 11.2 §5.7 イベントの履歴 API

- **カーソルは不透明な文字列**（例の `c_000981` は書式の例にすぎず、読み取らない）。連携・`epoch`・見えるイベントの集合（`VisibleSet`）に結びついた AEAD で暗号化した値で、
  別の連携のカーソル・改ざん・書式の誤りは `400`（`FG-INT-0008`）。
- **可視性は読むたびに判定**する。連携に結びついたプロジェクト（最大 200）× イベントの種類の分類を `authorize()` で判定し、連携の `event_types`（許可リスト）で狭める。
  `project_id` のないイベント、`member.*`・`token.*` などは連携に決して出さない。結びつけの解除・非公開化・権限の喪失の後は、新旧どちらのイベントも返さない。
  `Forge-Act-As` は履歴の読み取りには使えない。
- **`GET /integrations/{id}/events/cursor`** は「その連携に見える最後のイベントの位置」を返す。410 からの復旧は、先にこのカーソルを取る → 開発状況 API（`state=all`）で全体を取り直す → 取っておいたカーソルから読む、の順。
- **読み取り**: `limit` は既定 100・最大 500、応答は 2 MiB まで。`has_more` は `next_cursor` の後に見えるイベントが残っているときだけ true。
  見えるイベントが残っていなければ `next_cursor` は先頭まで進む。流量制限は連携ごと（`429`）。少なくとも 1 回の配信なので、kanflow は `id`（`evt_…`）で重複を除く。
- **`410 Gone`（`FG-INT-0007`）の理由**（本文は `reason` だけ。黙って途中から返さない）:

  | `reason` | 意味 |
  |---|---|
  | `retention` | カーソルが保持期間より古い（保持は既定 90 日、最小 7 日） |
  | `epoch_mismatch` | DB の復元・巻き戻しで `epoch` が作り直された |
  | `ahead_of_head` | カーソルが現在の先頭より先を指す |
  | `visible_set_changed` | 結びつけ・所属・ロール・グループの階層・可視性・`event_types` のどれかが変わり、見えなかった間の隙間を飛ばさないため |

- **送出先に届かない間は `503`**: forge は監査の封印の送出先との比較が成功するまで、連携の履歴を `503`（`FG-DB-0012`）で閉じる（ADR-0018 §5）。forge の画面と git の操作は動き続ける。kanflow は 503 を一時的な失敗として再試行する。
- **kanflow → forge の受信（§5.6）**: 本文は 64 KiB まで。署名は `abs(now - t) ≤ 300 秒`（§11.1 と同じ署名の方式）を、監査やジョブを書く前に検証する。
  **存在しない連携の `{id}` と署名の不正は同じ `401`**（`FG-INT-0005`）。重複排除は署名された本文の中のイベント ID（保持 7 日）。

## 13. 連携の実装の順序（2026-10-30、クラウドのセッション。ユーザーは推奨案で進めることを指示）

planner がこの時点の両方のコードを確かめた結果（kanflow `81dca6a`、GitStation `claude/brave-cray-w62c35`）:

- §8.4 の取りこぼし 2 件は **まだある**（`pbi-keys.ts:6`、`gitlab-client.ts` の `paged()`、`git-sync.ts:74`）。「クローズした MR が出ない」は表示の不具合ではなく、この 2 件の結果（`git-format.ts` は `closed` を表示し、MR の行は消さない）。
- ブランチの行は、ブランチが消えると消える（`pruneBranches`）。パイプラインの取得の失敗はログなしで捨てられている。
- `write:dev` はまだない（kanflow のスコープは read / backlog / sprint / task / comment / icebox / daily）。
- GitStation 側の前提（管理者の履歴と `…/cursor`、サービスアカウントのトークン、`work_items`、Web の振り分け）はまだない。連携の表を先に作っても、書き手も読み手もない。

**決定（推奨案 B）**: いまは kanflow の第 0 段を GitLab のまま進め、取り込み元を差し替えられる薄い層（`DevSource`）を入れる。GitStation 側の連携の土台（`integrations` / `integration_bindings`、`prove_visible`、FG-INT-0007/0008/0012、権限の行）は、M1 の管理者の履歴とサービスアカウントのトークンができてから作る。kanflow の `GitStationSource` は M3。

| MR（kanflow） | 内容 | 順序 |
|---|---|---|
| K1 `feat/L4-git-pbi-keys` | 検出の正規表現（上の §2）とテストのベクタ | K2 と並列 |
| K2 `feat/L4-git-sync-watermark` | 上限で打ち切ったら位置を進めない、打ち切りとパイプラインの取得の失敗をログに出す | K1 と並列 |
