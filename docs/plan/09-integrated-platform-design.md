# 09 統合プラットフォーム基本設計（整理版）と、ポータル・Keycloak の共通ログイン

作成: 2026-10-31（クラウドのセッション）。元はユーザーがまとめた設計書 `source/2026-10-31-integrated-platform-draft.md`（「GitStation × Kanflow × Agent_Claudecode_ver2 統合プラットフォーム基本設計書」）。この文書は、その内容を **今までの計画（00〜08）と突き合わせて整理し、ずれを直し、作業の流れ（W）に割り当てたもの**。加えて、ユーザーの指示「IoT プラットフォームのポータルの共通の入口からログインする。ログインは Keycloak を使う」を §8 に入れた。

**元の設計書との関係**: 元の設計書はビジョンと構想（なぜ・何を）、この文書は実装の割り当て（どこで・どの順で・何に気を付けて）。食い違いは §9 に一覧し、この文書の決定（推奨）を正とする。

## 1. ビジョン（元の §0〜§2 の要約）

- 人の仕事を「作業」から「**基準の設定（Set: Kanflow）・規約に沿った実装（Keep: エージェント）・証拠に基づく承認と改善（Adjust: GitStation）**」へ移す。
- 個人のバイブコーディングを、チームの統制と資産化の輪に乗せる。
- GitLab などの既存の道具の限界（技術者以外の壁、あいまいな意図の構造化、エージェントの統制、仕様と実装のずれ、検収の負荷）を、3 つのシステムの直結で越える。

| システム | 位置づけ | 主な役割 |
|---|---|---|
| Kanflow | 上流: 意図の定義と指令（PM・現場・技術者以外の窓口） | 要望 → PBI・タスク・受入基準、Spec-Gate、多言語、教訓のデータベース、承認待ち |
| エージェントモデル（Ver2 / TMUX 版） | 中流: 自律の実装と検証 | プロジェクト専用の `CLAUDE.md`・スキル・規則・フックで実装、ヘッドレスの検証と画面の証拠、仮想デザインレビュー |
| GitStation | 下流: 資産・CI/CD・ナレッジ | コードと文書の版の管理、プレビューの環境、帳票のビルド、エージェントビルダーとマーケットプレイス |
| IoT プラットフォームのポータル + Keycloak | 入口 | 1 回のログイン、アプリの一覧、自分宛ての項目（§8） |

ローカル LLM を「常駐・低遅延・費用なしの門番」として、Claude Code の前後に置く（W14 を具体化）。

| 段 | 機能 | 置き場所 | 割り当て |
|---|---|---|---|

## 3. プロジェクトごとのエージェントの編成（元の §4）

**決定**: 「1 プロジェクト = 1 リポジトリ」。エージェントの設定（`CLAUDE.md`、`.claude/`、`.mcp.json`）は、GitStation の**エージェントビルダー**がプロジェクトのリポジトリに直接生成してコミットする。メンバーは 1 つ `git clone` するだけで、そのプロジェクト専用の Claude Code の環境になり、`git pull` で最新になる。

### 3.1 リポジトリの標準の構成（Claude Code の公式の構成に合わせる）

```text
project-repository/
├── CLAUDE.md                     # 生成（基本の雛形 + 仕様の要約 + 有効な部品 + 独自の規則）
├── .mcp.json                     # 生成（Kanflow / GitStation の MCP）
├── .claude/
│   ├── settings.json             # 生成（permissions と hooks）
│   ├── settings.local.json       # 個人用（.gitignore）
│   ├── rules/                    # 規則（99-kanflow-lessons-learned.md は Kanflow から生成）
│   ├── agents/                   # サブエージェント
│   ├── skills/<name>/SKILL.md    # スキル
│   ├── commands/                 # スラッシュコマンド
│   └── hooks/                    # フックのスクリプト
├── .gitstation/agent.lock.json   # マーケットプレイスの部品と版の固定
├── docs/specs/                   # 仕様書（Markdown、W12）
└── src/                          # コード（または設備仕様の本編）
```

**フックの実装言語の決定（元の設計書から変更）**: 元の例は `bash .claude/hooks/*.sh`。開発者の PC には Windows があるため、**フックは Node.js（CommonJS、標準モジュールだけ）** にする（今のエージェントモデルと同じ。フェイルオープン、3 秒で打ち切り、ブロックは `exit 2` だけ）。`settings.json` は `node .claude/hooks/<name>.js` を呼ぶ。

### 3.2 W1 との関係（共通プラグインからの変更）

07 の W1 では「共通部分を Claude Code のプラグイン `ymma-dev-core` で配る」としていた。元の設計書の方式（エージェントビルダーがリポジトリに生成し、`agent.lock.json` で版を固定）に **置き換える**:

| 項目 | 07 W1（旧） | この文書（新） |
|---|---|---|
| 配り方 | プラグインのマーケットプレイス | **GitStation のマーケットプレイス + エージェントビルダーがプロジェクトのリポジトリに生成** |
| 版の固定 | プラグインの版 | `.gitstation/agent.lock.json`（部品ごとの版） |
| 更新 | プラグインの更新 | ビルダーが差分をプレビューし、更新の MR を作る（世代の移行も同じ） |
| 共通の部品の中身 | `ymma-dev-core` | **マーケットプレイスの最初の部品の集まり**として同じもの（Kanflow 連携、作業の宣言、レビューの規則、git の規則、フック） |
| GitStation ができるまで | — | 今の TMUX 版 / Ver2 のリポジトリをそのまま使う。部品の切り出し（W1）は、マーケットプレイスの部品の形（`SKILL.md` の階層、frontmatter）で行っておき、ビルダーができたら移す |

TMUX 版と Ver2 は、ビルダーの**ベースモデル**（アダプター）として表す: `claude-code-v2`（単独）と `claude-code-tmux`（並行。`team-lead` / `/team` を足す）。

## 4. エージェントビルダー（元の §5）

- **抽象の定義（IR）と出力のアダプターを分ける**コンパイラの構造。AI 側の構成が変わっても GitStation 本体を直さない。
- 4 つの要件: (1) アダプターの定義から画面（スキル・サブエージェント・規則・フック・MCP の選択）を描く、(2) `target-adapter.yaml` で出力の場所と形式（ディレクトリのコピー / ファイル / JSON のマージ）を決める、(3) 廃止した部品は `enabled: false` で次のビルドで安全に消す、(4) Dry-Run のプレビューと、選択を保ったままの世代の移行の MR。
- データの形: `.gitstation/agent.lock.json`（`schema_version`、`project_id`、`project_type`、`adapter_id`・`adapter_version`、`linked_specs`、`marketplace_items`（skills / sub_agents / rules / hooks、版、仕様から自動で選ばれたかと理由）、`custom_rules`）と `target-adapter.yaml`（元の設計書 §5.2 の例のとおり）。
- **推薦**: 仕様書（`docs/specs/*.md`）をローカル LLM で読み、要件（決済連携、オフライン、多言語など）からマーケットプレイスの部品をチェックボックスで提案。決めるのは人。
- **守ること**（追加）: ビルダーの生成も MR で入れる（直接のコミットはしない）。マーケットプレイスの部品は署名と版を持ち、フックのスクリプトは CI でテスト（通常の入力で exit 0）してから公開する。部品の公開の権限は権限の表に行を足す。
- 割り当て: **新規 W15**（GitStation、M4 の後。マーケットプレイスと部品の形は W1 で先に作る）。

## 5. 設備仕様（Spec-as-Code）への展開（元の §6、07 W12 と統合）

| 要素 | ソフトウェア開発（`software_dev`） | 設備仕様・工程設計（`equipment_spec`） |
|---|---|---|
| リポジトリの中身 | コード、API 定義、DB スキーマ、システム仕様 | 設備要求仕様書（URS）、工程フロー、FMEA、検収基準、保全チェックリスト |
| スキル | 型安全、デザイントークン、E2E の生成 | 安全規格（インターロック）、理論サイクルタイム、過去トラの照合、4M 変動の対策 |
| サブエージェント | アーキテクト、セキュリティ、QA | 安全衛生、保全性（MTTR）、品質保証（異常時の処理）、多言語の技術翻訳 |
| CI | ビルド・テスト・ステージングへのデプロイ | 仕様の矛盾・抜けの検査（Spec Lint）、改訂履歴と承認欄付きの PDF / Word のビルド |

- **仮想デザインレビュー（DR）**: 執筆中に安全・保全・品質のサブエージェントがクロスチェックし、非常停止時の仕掛り品の処理や消耗品の交換時間などの書き漏れを指摘する。
- **2 つの使い方**: パワーユーザーはクローンしてローカルの Claude Code（Local Clone）。現場の担当や技術者以外は GitStation の Web の文書エディタ（Web Studio）で、同じ `.claude/` のスキルを読み込んだ AI と対話して書く。
- **プロジェクトの種類の名前をそろえる**: ビルダーの `project_type` と Kanflow の `projectType` を 1 つの一覧にする（`software_dev` = `software`、`equipment_spec` = `equipment`（新規）、`process_improvement`、`general`）。
- W12 の「ベースのリポジトリ（決めるべき項目・ベースのスケジュール・出力のスクリプト）」は、`equipment_spec` のベースモデルの一部として配る。

## 6. チームの再発防止の輪（元の §7、07 W11 と統合）

元の「Team Immunity Loop」の 5 段を W11 に取り込む:

1. **入力と蓄積（Kanflow）**: タスクの「手戻りの記録」、差し戻しのコメント、テストの失敗、設備仕様の考慮漏れ、DR の指摘、現地の立ち上げの不具合 → 教訓のデータベース（W11 の `failure_event` / `lesson`）。
2. **抽象化してガードレールにする（Kanflow のローカル LLM）**: 固有名詞に依存しない再発防止の規則（禁止事項・必須チェック）に変換。例「日時は UTC で保存し、表示層だけで現地時刻に変換する」。
3. **エージェントの資産に入れる（GitStation のビルダー）**: 深刻度と性質で 3 か所に入れる。
   - 知識: `.claude/rules/99-kanflow-lessons-learned.md` に追記
   - 物理ブロック: 検知できるものは `PreToolUse` のフックの検査条件に追加
   - 全社の資産: 汎用のものはマーケットプレイスのスキル・審査のサブエージェントへ昇格
4. **他のメンバーへの伝播**: `SessionStart` のフックが最新の規則を取り込み、Kanflow から「今の担当に似た過去のミス」を取得してセッションの冒頭に入れる。
5. **事前の警告（Spec-Gate へ還流）**: 似たタスクの起票の時に、Kanflow が過去の失敗を示し、受入基準に対策を加える提案をする。

**守ること（元の設計書への追加。誤った規則が全員の作業を止めないため）**:
- 規則への変換は**提案**で、人（Maintainer / SM 以上）の確認を経たものだけを注入する（W11 の「確認済み」）。
- `PreToolUse` のブロックの追加は必ず MR で、テスト（ブロックすべき例とすべきでない例）を付ける。誤検知の報告で 1 クリックで無効にできる。
- 注入は直接のコミットではなく MR（自動マージの `reserve` 以上で反映）。

| ミスの種類 | Kanflow への入力 | 他のメンバーの Claude Code への反映 |
|---|---|---|
| 実装・設計のミス（API のずれ、型の不整合） | MR の差し戻し、タスクの「手戻り」ラベル | `99-kanflow-lessons-learned.md` に規則 + `PreToolUse` でのブロック |
| 要件・仕様の考慮漏れ（例外処理、権限） | 検収時のバグ、プレビューでのピン止めの指摘 | Spec-Gate のチェックリストに追加 + 審査のサブエージェントの監査項目 |
| 設備仕様の過去トラの再発（安全インターロック、保全性） | DR の指摘、現地の立ち上げの不具合 | 設備用のスキルの必須の記載項目に昇格 |

## 7. システム間の API（元の §8 を、実装済みの API に合わせて整理）

| 元の設計書の API | 用途 | 対応（実装済み / 予定） |
|---|---|---|
| Kanflow `GET /api/v1/projects/{id}/active-context?user=` | フックが担当のタスク・受入基準・関連の仕様・注意すべきミスを取得 | **新規**（W3 / W11）。既存の `my_tasks`・`get_pbi`・`list_claims`・`search_lessons` をまとめた 1 回の呼び出しにする。利用者はトークンの本人（`?user=` は付けず、トークンから決める） |

| GitStation `POST /api/v1/repos/{id}/agent-builder/compile` | 選んだ部品から `.claude/` 一式を生成 | W15（MR を作る） |

## 8. ポータルと Keycloak による共通のログイン（新規 W17）

ユーザーの指示（2026-10-31）:「IoT プラットフォームにはポータルのログインがあり、共通の入口からログインする予定。それに合わせて作る。ログインは Keycloak を使う」。Kanflow 側の既存の検討は `Kanflow/docs/platform-integration-iotpf.md` §4。

### 8.1 構成

```text
利用者 → IoT プラットフォームのポータル（アプリの一覧、自分宛ての項目）
           │ 1 回のログイン（Keycloak、OIDC）
           ├─ Kanflow（OIDC クライアント kanflow）
           ├─ GitStation（OIDC クライアント gitstation）
           ├─ 文書ポータル / Web Studio（GitStation の画面）
           └─ BankMasalah など他のアプリ
```

- **Keycloak の realm は IoT プラットフォームのものを共有**し、アプリごとに OIDC のクライアント（`kanflow`、`gitstation`）を作る。
- **利用者の同一性**: Keycloak の `sub` を主キーに、社員番号（`employeeNumber` ↔ `staff_id`、`me_user`）で各アプリの利用者と結ぶ。最初のログインで利用者を作るか結ぶ（メールアドレスの一致だけでは結ばない）。
- **入場の可否**はクライアントロール（例 `access`）、**細かい権限は各アプリ**（GitStation は `authorize()` と権限の表、Kanflow は既存の役割）。Keycloak のグループ・ロールは粗い入場の判断と、管理者の付与の元にだけ使う。
- **ログアウト**: 1 回のログアウトで全アプリから出る（バックチャネルのログアウト）。権限の変更・退職は Keycloak のセッションの失効ですぐ反映。

### 8.2 GitStation でやること（M2 の画面と一緒に）

- Web のログインを Keycloak の OIDC（認可コード + PKCE）にする。セッションは GitStation のものを使い、Keycloak の失効・バックチャネルのログアウトを受けて切る。
- 利用者の表に外部の ID（`idp`, `sub`）を足す（**マイグレーションは追記**）。管理者・無効化（D 段で作った規則）は今のまま GitStation で判断する。
- **git の操作と API はトークンのまま**: `git clone` / `push`（Smart HTTP の Basic）と Claude Code の MCP は、今の個人アクセストークン（ADR-0019）を使う。トークンの発行の画面は Keycloak でログインした後に使う。CI・連携はサービスアカウントのトークン（M1 で作る）。
- 新しい失敗にはエラーコードを登録（例: OIDC の検証の失敗、利用者の結び付けの失敗、Keycloak に届かない）。Keycloak に届かないときは、ログイン済みのセッションと git のトークンは使い続けられる（新しいログインだけできない）。
- 判断は ADR に記録（ADR-0019 の Amendment か新しい ADR）。

### 8.3 Kanflow でやること

- Auth.js の Keycloak プロバイダ（既存の検討のとおり）。今のパスワードのログインは 2〜4 週の並行の後に止める。
- **API トークンの扱い（既存の検討から変更を推奨）**: 既存の検討は「個人アクセストークンを Keycloak のサービスアカウントに寄せる」。しかし Claude Code の MCP・作業の宣言・承認は**本人として**動く必要があり、サービスアカウントでは本人が分からない。そこで: **人が使うトークン（MCP・`dev:write`）は Kanflow の個人のトークンのまま**（発行は Keycloak でログインした後）、**システム間（CI・GitStation からの送信）は Keycloak のサービスアカウント**、にする。
- W13（Kanflow からのデプロイ）の「本人の権限で GitStation を呼ぶ」は、Keycloak のトークン交換（token exchange）で本人の GitStation 用のトークンを得る形にする。

### 8.4 ポータルとの連携

- ポータルのアプリの一覧に Kanflow・GitStation・文書ポータルを載せる。
- **自分宛ての項目**: 08 の「承認待ち」と担当のタスクを、ポータルにも要約で出す（Kanflow の API から。詳細はリンクで Kanflow へ）。
- 画面の上部の共通のヘッダー（アプリの切り替え、利用者、ログアウト）はポータルのものにそろえる。GitStation のロゴ・アイコンは `docs/brand/` のファイルを使う。

### 8.5 完了の条件

ポータルから 1 回ログインして、Kanflow・GitStation・文書ポータルを行き来でき、ログアウトが全部に効く。Keycloak で無効にした人は、次の操作から入れない。git のトークンと MCP は本人として動き続ける。

## 9. 元の設計書との食い違いと、この文書の決定

| # | 元の設計書 | この文書の決定（推奨） | 理由 |
|---|---|---|---|
| 1 | フックは bash（`.sh`） | Node.js（CommonJS、標準モジュールだけ） | 開発者の PC に Windows がある。今のエージェントモデルと同じ |
| 2 | 規則・フックを GitStation が自動でコミット | 確認済みの教訓だけを MR で入れる。ブロックのフックはテスト付き | 誤った規則が全員の作業を止めないため |
| 3 | ステータスを「検収待ち」へ自動で遷移 | タスクの「検収待ち」は自動で可。PBI の完了は PO が確定 | Kanflow の原則（大きな状態の変更は人） |
| 4 | Kanflow の API のパス（`active-context`、`tasks/{id}/status`、`incidents/extract-rule`） | §7 の対応表どおり、実装済みの API に合わせる | 二重の API を作らない |
| 5 | `?user={git_user}` で担当を引く | トークンの本人から決める | 他人の担当を引けないようにする |
| 6 | 共通部分の配り方 | 07 W1 のプラグインを、エージェントビルダーとマーケットプレイスに置き換える（§3.2） | 1 プロジェクト 1 リポジトリの方式に合わせる |
| 7 | Kanflow の個人トークンを Keycloak のサービスアカウントに寄せる（既存の検討） | 人のトークンは個人のまま、システム間だけサービスアカウント | MCP・承認は本人として動く必要がある |
| 8 | Web Studio の AI | 社内の文書・製造のデータを扱うので、既定はローカル LLM。Claude を使うかはプロジェクトの設定で決め、機密の印のあるものは渡さない | データ主権 |
