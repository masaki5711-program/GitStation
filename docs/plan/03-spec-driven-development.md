# 仕様駆動開発 — 仕様リポジトリとシステム開発リポジトリ（v0.1 ドラフト）

- 作成日: 2026-10-26
- 関連: 全体計画 `01-product-plan.md`、kanflow 連携 `02-kanflow-integration.md`
- 状態: **確定（2026-10-26。§9 を推奨案で決定）。** ADR-0004 に記録した。

> **2026-11-01 利用者の決定で変更**（ADR-0023）:
> 1. **リポジトリの種類 `spec` / `system` の区別をやめた。** すべてのリポジトリは同じ種類。リポジトリの仕様はそのリポジトリの `spec/` に置く（§3 の案 A を既定）。
>    複数のシステムで共有する仕様は、特別な種類のないふつうのリポジトリに置き、他のリポジトリが `.forge/repo.yml` で版を固定して参照する（§4.4）。「仕様を持つ」は中身（`spec/` の有無）から導き、ラベルでは決めない。
> 2. **文書ポータルをやめた。** 画面の系統はリポジトリの画面 1 つ。利用者は Git の基本を学んでから使う。
> 3. **リポジトリをまたぐ連携は、まだ作らない。M3 の、はっきり分けた項目にする**（§8.1）。順序は (a) `.forge/repo.yml` の解析と仕様の参照 → (b) 仕様のずれの通知 → (c) Kanflow のプロジェクト ↔ 複数のリポジトリの登録。
> - 残すもの: 要件 ID、`@req`、`spec-lint` / `spec-trace` / `spec-conformance` / `spec-drift`、AI 向けの文脈 API、PBI の下書き。外すのは、spec / system の区別と、文書ポータルだけ。
> - **読み方**: 以下の「`spec` リポジトリ」は「共有する仕様を置いたふつうのリポジトリ」、「system リポジトリ」は「それを参照するふつうのリポジトリ」と読む。種類としての `spec` / `system` はない。取り消した記述は ~~打ち消し線~~ で残す。

## 1. 目的

**根幹の目的は、AI によるシステム開発を加速すること。** そのために、
「仕様 → PBI → 実装 → 検証 → デプロイ」を 1 本のルートとしてつなぎ、
AI がどの段階でも **正しい仕様を、機械的に、根拠付きで** 参照できるようにする。

| 今の課題（想定） | 仕様駆動のルートで解決すること |
|---|---|
| 仕様が Word / Excel やチャットに散らばり、AI に渡す文脈を人が毎回集めている | 仕様をリポジトリで版管理し、forge が **AI 向けの文脈** をまとめて返す（§6） |
| 仕様のどの要件をどの MR が実装したか分からない | 要件に **安定した ID** を付け、PBI・MR・テストと結びつける（§4） |
| 仕様を変えたとき、どのコードに影響するか分からない | 結びつきから **影響範囲** を出し、kanflow に PBI の下書きを作る（§5） |
| AI が書いたコードが仕様を満たしているか、人がすべて読んで確かめている | 決定的なチェック（要件にテストがあるか）と、LLM による照合で検証する（§5.4） |

## 2. ~~リポジトリの種類~~ → リポジトリに種類はない（2026-11-01 変更）

~~forge に登録するリポジトリに **種類（kind）** を持たせる。`spec`（仕様）と `system`（システム開発）で、画面（文書ポータル / 開発者向け）、マージの条件、権限の既定値を変える。~~

**変更後**: すべてのリポジトリは同じ種類のリポジトリである（ADR-0023）。

| 問い | 答え |
|---|---|
| 仕様はどこに置くか | そのリポジトリの `spec/`（既定。コードと同じ MR で変えられる） |
| 複数のシステムで共有する仕様は | ふつうのリポジトリに置く。他のリポジトリは `.forge/repo.yml` の `specs:` で、タグで版を固定して参照する（§4.4） |
| 「このリポジトリは仕様を持つか」は | 中身から導く（`spec/` がある、要件ブロックがある）。ラベルでは決めない |
| 画面 | リポジトリの画面 1 つ。Git の基本を学んでから使う |

- `.forge/repo.yml` の `kind:` の項目はなくす。画面・マージの条件・権限の既定値を、種類で変えることはしない。
- DB の `repositories.kind` の列は、マイグレーションが追記のみなので残るが、使わない（ADR-0023）。

## 3. 同じリポジトリか、別のリポジトリか（2026-11-01: 案 A を既定、共有は「ふつうのリポジトリ + 版の固定の参照」）

### 3.1 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A 同じリポジトリ | system リポジトリの中に `spec/` を置く | 仕様とコードを **1 つの MR で同時に** 変えられる。AI は 1 回の checkout で両方を読める | 1 つの仕様が複数のリポジトリにまたがるとき（実例: PBI-43 は 2 リポジトリ）に置き場所が決まらない。仕様の承認者にコードの権限が要る。仕様の版とコードのブランチが混ざる。Git を知らない人が触りにくい |
| B 別のリポジトリ | `spec` リポジトリを独立させ、system リポジトリから参照する | 1 つの仕様を複数のリポジトリで共有できる。仕様の承認・公開の流れと権限を独立させられる。文書ポータルと相性が良い | 仕様とコードがずれやすい。AI に渡す文脈を集める仕組みが要る。リポジトリをまたぐ変更の調整が要る |
| ~~★C 併用（推奨）~~ → **2026-11-01 取り下げ**（`spec` という種類を前提にしていたため。A を既定にし、共有する仕様だけ B の形をふつうのリポジトリで取る） | **製品・業務レベルの仕様は `spec` リポジトリ（B）**、**部品レベルの設計（API の定義、内部設計、ADR）は system リポジトリ内の `spec/`（A）**。forge は両方を **同じ仕組み（§4）で索引する** | A と B の長所を使い分けられる。B の短所（ずれ、文脈集め）は forge の索引・チェック・文脈 API が埋める | 置き場所の判断基準が要る（§3.2） |

### 3.2 置き場所の判断基準（~~案 C~~ → 2026-11-01: 次の問いで決める。どれも「ふつうのリポジトリ」）

| 問い | はい → | いいえ → |
|---|---|---|
| 複数のリポジトリやチームが同じ仕様を参照するか | 仕様を置くふつうのリポジトリ（他は `specs:` で版を固定して参照） | 次の問いへ |
| ~~Git を知らない人が書く、または承認するか~~ | ~~`spec` リポジトリ~~（2026-11-01: 区別しない。Git の基本を学んでから使う前提） | — |
| コードと同時に変わるべきか（API の定義、DB の設計） | そのリポジトリの `spec/`（既定） | 仕様を置くふつうのリポジトリ |

**考え方**: AI の開発を加速するうえで効くのは「置き場所」ではなく、**要件の ID、
結びつき、文脈の取り出し方が統一されていること** である。仕様は既定ではそのリポジトリの `spec/` に置き（案 A）、
複数のリポジトリにまたがる PBI（現在の運用の実例）のための共有する仕様は、ふつうのリポジトリに置いて版を固定して参照する。
どちらも forge は同じ仕組み（§4）で索引する。~~Git を知らない人の参加（範囲 D）を、`spec` 種類と文書ポータルで扱う~~ は、
2026-11-01 にやめた（ADR-0023）。

## 4. 仕様の形式と、要件の ID

### 4.1 2 種類の仕様

| 種類 | 形式 | AI から見た扱い |
|---|---|---|
| **構造化仕様**（システム開発向け） | Markdown + 先頭のメタデータ（YAML）+ **要件ブロック** | そのまま読める。要件を ID で引ける |
| **文書仕様**（設備仕様など） | Word / Excel / PDF（リポジトリに置く。~~文書ポータルで管理~~ は 2026-11-01 にやめた） | 本文を抽出してテキスト化する。要件の ID は、LLM が候補を出し、人が確定する |

### 4.2 構造化仕様の例

```markdown
---
spec: zeva-engine/config
title: 設定管理
status: approved        # draft / review / approved / deprecated
owners: [po@example.internal]
---

## 設定の再読み込み

::: req ZEVA-CFG-012
設定ファイルの変更は、再起動せずに 10 秒以内に反映されること。
受入: 変更から反映までの時間を計測するテストがある。
:::

::: req ZEVA-CFG-013 priority=must
不正な設定は反映せず、エラーコードを記録して直前の設定で動き続けること。
:::
```

- **要件の ID は一度付けたら変えない**（削除は `deprecated` にする）。結びつきの基準になるため。
- ID の接頭辞は `spec` リポジトリごとに設定し、forge が重複を検出する。
- 形式の検査（ID の重複、必須項目、壊れた参照）は、仕様の MR の **決定的なチェック** にする。

### 4.3 結びつき（トレーサビリティ）

```
要件 ZEVA-CFG-012（共有する仕様のリポジトリ v1.4）
  └─ PBI-43（kanflow。要件 ID を参照）
       ├─ MR !87（system リポジトリ A。PBI-43 を参照）
       │    └─ テスト test_reload_within_10s（コメントの `@req ZEVA-CFG-012`）
       └─ MR !12（system リポジトリ B）
            └─ デプロイ prod v2.3.0
```

| 結びつき | 書き方 | 検出 |
|---|---|---|
| PBI → 要件 | kanflow の PBI に要件 ID を記入（`02` の連携 API で forge が取得） | kanflow |
| MR → PBI | ブランチ名・タイトルの `pbi-43`（`02` §2） | forge |
| テスト → 要件 | テストのコメントや名前に `@req ZEVA-CFG-012`（言語を問わない） | forge が既定ブランチを索引 |
| system → spec の版 | `.forge/repo.yml` の `specs:`（§4.4） | forge |

### 4.4 他のリポジトリの仕様を参照する（2026-11-01: 一般化。`kind:` の項目はなくした）

```yaml
# .forge/repo.yml（どのリポジトリでも同じ）
specs:
  - repo: specs/zeva-engine      # 共有する仕様を置いたふつうのリポジトリ
    version: v1.4                # 準拠する仕様の版（タグで固定）。"track: main" も可
    scope: [ZEVA-CFG-*]          # このリポジトリが担当する要件
  - path: spec/                  # このリポジトリ自身の仕様（既定）
```

- **版を固定する**ので、「このコードはどの版の仕様に準拠しているか」が常に決まる。
- 仕様の新しい版が公開されると、forge は「v1.4 → v1.5 で ZEVA-CFG-012 と 013 が変わった。
  このリポジトリは v1.4 のまま」と表示する（§5.2）。

## 5. 仕様に基づくシステム開発のルート

### 5.1 全体の流れ

```
 ① 仕様の作成・改訂（仕様を置いたリポジトリの MR。~~文書ポータルからも~~ はやめた）
      │  形式チェック → 承認 → 版の公開（タグ v1.5）
      ▼
 ② 影響の分析（forge）── 要件の差分 × 結びつき → 影響するリポジトリ・PBI・テスト
      │  イベント spec.released
      ▼
 ③ PBI の下書き（kanflow）── LLM が要件からユーザーストーリーと受入基準を下書き → PO が確定 → Ready
      ▼
 ④ 実装（system リポジトリ）── PBI からブランチ → AI 向けの文脈（§6）→ 人と AI エージェントで実装 → MR
      ▼
 ⑤ 検証（チェック）── forge/spec-trace（決定的）＋ forge/spec-conformance（LLM）＋ CI
      ▼
 ⑥ マージ・デプロイ ── 要件の状態を「実装済み（v2.3.0）」「本番反映済み」に更新
      ▼
 ⑦ 逆向きの還流 ── 実装中に見つかった仕様の不足・矛盾は、MR から「仕様の変更依頼」として
                    spec リポジトリの MR の下書きを作る → ① に戻る
```

### 5.2 影響の分析（②）

- 公開された版と、前の版との **要件単位の差分**（追加・変更・廃止）を出す。
- 結びつき（§4.3）から、影響する system リポジトリ、PBI、テストを列挙する。
  **計算はコードで行い**、LLM は変更の要約（ja / en / id）だけを行う。
- 結果は kanflow に届け（`02` のイベント）、変更された要件に対応する PBI の下書きを
  Icebox に作る（③）。

### 5.3 AI による実装（④）

- 開発者のブランチ作成時に、forge が **文脈のまとめ**（§6）を用意する。
- AI エージェント（ローカル LLM、または開発者が使う AI ツール）は、文脈 API か MCP で
  要件、関連コード、過去の MR を取得し、**要件 ID を引用しながら** 実装とテストを書く。
- テストには `@req` を付ける規則にする。これで ⑤ の決定的なチェックが効く。

### 5.4 検証（⑤）

| チェック | 種類 | 内容 |
|---|---|---|
| `forge/spec-lint` | 決定的 | 仕様の MR で、要件 ID の重複、必須項目、壊れた参照を検査する |
| `forge/spec-trace` | 決定的 | MR の PBI が参照する要件のうち、`@req` の付いたテストがないものを列挙する。**「テストのない要件」が残っていれば `failure`**（必須にするかはプロジェクトの設定） |
| `forge/spec-conformance` | LLM（助言） | 要件の本文と差分・テストを突き合わせ、要件ごとに「満たしている / 一部 / 根拠なし」を示す（`01` L-3 の拡張。受入基準と要件の両方を見る） |
| `forge/spec-drift` | 決定的 | リポジトリが参照する仕様の版が、公開済みの最新版より古いときに `neutral` で知らせる（M3 のリポジトリをまたぐ連携の (b)。§8.1） |

### 5.5 要件の状態

forge は要件ごとに状態を集計し、**要件の一覧（トレーサビリティ表）** を表示する。

| 状態 | 条件 |
|---|---|
| 未着手 | 要件に結びつく PBI がない |
| 計画済み | PBI がある |
| 実装中 | PBI に開いている MR がある |
| 実装済み | MR がマージされ、`@req` のテストが既定ブランチで成功している |
| 本番反映済み | 実装済みのコミットを含むデプロイが本番で成功した |

## 6. AI 向けの文脈 API — 加速の中心

AI に毎回人が文脈を集めて渡す手間をなくす。forge が、作業に必要な文脈を
**根拠（版、ファイル、行）付きで** まとめて返す。

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/v1/context/work-item?provider=kanflow&project_id=…&ref=PBI-43` | PBI の文脈: ユーザーストーリー、受入基準、参照する要件の本文（固定された版）、関係するリポジトリ、関連コードの場所、過去の関連 MR の要約 |
| `GET` | `/api/v1/context/requirement/{req_id}?version=v1.5` | 要件の文脈: 本文、版の履歴、結びつく PBI・MR・テスト・デプロイ |
| `GET` | `/api/v1/context/merge-request/{project}/{iid}` | MR のレビュー用の文脈: 差分、要件、受入基準、チェックの結果 |

- 返す内容には上限を設け、**どこから取った情報か**（リポジトリ、版、パス、行）を必ず付ける。
  AI の出力の検証と、人による確認のため。
- 同じ内容を **MCP サーバー** としても提供する（道具: `get_work_item_context`、`get_requirement`、
  `search_requirements`、`get_trace_matrix`）。開発者の AI エージェントと、forge 内の LLM 検証の両方が使う。
- 権限は呼び出した本人の範囲に限る（認可の単一判定点）。

## 7. kanflow からの利用 — 複数のリポジトリの登録と API

kanflow のプロジェクトに、**リポジトリを複数登録** でき、
kanflow の画面から forge の API を使えるようにする。~~仕様のリポジトリとシステム開発のリポジトリ~~ の区別はない（2026-11-01）。
**この節の機能は M3 の「リポジトリをまたぐ連携」（§8.1）の (c) で、まだ実装していない。**

### 7.1 バインディングの登録（kanflow から）

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/v1/repositories?q=…` | 登録できるリポジトリの検索（操作する人が見られるものだけ。~~`kind=spec|system`~~ の絞り込みはない） |
| `GET` | `/api/v1/integrations/{id}/bindings?kanflow_project_id=…` | kanflow のプロジェクトに登録済みのリポジトリの一覧 |
| `POST` | `/api/v1/integrations/{id}/bindings` | リポジトリの登録 |
| `PATCH` `DELETE` | `/api/v1/integrations/{id}/bindings/{binding_id}` | 設定の変更（ブランチ名の規則、タスクの自動完了など）、登録の解除 |

```json
// POST /api/v1/integrations/{id}/bindings
{
  "kanflow_project_id": "<kanflow のプロジェクト ID>",
  "repository": "specs/zeva-engine",
  "role": "spec",   // ~~2026-11-01 廃止: role は持たない~~
  "settings": { "requirement_prefix": "ZEVA" }
}
```

- 登録は kanflow の PO / SM が画面から行う。forge は **代理実行（`02` §5.3）** で、
  操作した本人がそのリポジトリの Maintainer 以上かを確認する。
- 1 つの kanflow のプロジェクトに、リポジトリを何個でも登録できる。
  **コードを持つリポジトリを複数の kanflow のプロジェクトに登録することは禁止する**
  （`PBI-123` の解決があいまいになるため。`02` §2）。共有する仕様のリポジトリ（他から `specs:` で参照されるもの）は
  複数のプロジェクトで共有してよい（要件 ID は全体で一意のため）。どちらかは、種類ではなく結びつけの設定
  （PBI をこのリポジトリのブランチ・MR に解決するか）で決める。詳細は (c) の設計で決める。

### 7.2 仕様の情報を kanflow で使う

| メソッド | パス | kanflow での使い方 |
|---|---|---|
| `GET` | `/api/v1/specs/{repo}/versions` | 仕様の版の一覧（公開日、変更の要約） |
| `GET` | `/api/v1/specs/{repo}/requirements?version=…&q=…` | PBI の編集画面で要件を検索して参照に追加する |
| `GET` | `/api/v1/specs/{repo}/diff?from=v1.4&to=v1.5` | 版の差分を要件単位で表示する |
| `GET` | `/api/v1/specs/{repo}/trace?version=…` | 要件の状態（§5.5）の一覧。kanflow のダッシュボードとレポートに表示する |
| `GET` | `/api/v1/integrations/{id}/events?after=…` | `spec.released`、`requirement.status_changed` も届く（`02` §5.7、§5.8） |

### 7.3 kanflow で便利になること

| # | 機能 | 内容 |
|---|---|---|
| S-1 | **要件から PBI を作る** | 仕様の新しい版で追加・変更された要件から、PBI の下書きを Icebox に作る（LLM がユーザーストーリーと受入基準を下書きし、要件 ID を自動で参照に入れる） |
| S-2 | **PBI の画面に要件の本文** | PBI が参照する要件の本文（固定した版）を表示する。kanflow の `referenceDoc` を、自由記述から要件 ID の参照に発展させる |
