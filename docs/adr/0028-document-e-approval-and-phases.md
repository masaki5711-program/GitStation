# ADR-0028: 文書の電子の承認と、リポジトリごとの承認のフェーズ

**Date**: 2026-11-09
**Status**: proposed（計画 13 §6 と §13 の 4〜6・8 を ADR にした。実装は計画 13 §12 の段 4。accepted は段 1 の試しと、品質保証の部門の確認
（押印の代わりになるか）の後）
**Deciders**: Masaki Fujikawa（ユーザー）、Claude

## Context

QMS の規程・リスクアセスメント・URS の承認を、押印の代わりに GitStation の MR の承認で行う（計画 13 §6.3、2026-11-09 決定）。押印の代わりに足るには
「誰が・いつ・何を・どの意味で」が否認・改ざんできない形で残る必要がある。今の MR の承認（ADR-0024 §8）は「誰が・いつ・どの head の SHA を」を持つが、
(a) 承認は `(head_sha, target_branch)` に結びつき、**target の先端が進んでも失効しない** ため、自動で合わさった結果の文書が、承認者の見た中身と
違いうる。(b) 本人の再確認が無い。(c) 意味（確認・承認）が 1 種類。(d) 起案者は自分の MR を承認できない（FG-REVIEW-0013）ので、「作成」の署名を
承認の形では持てない。

## Decision

1. **フェーズはリポジトリごと**（計画 13 §6.3.1）: なし / 承認だけ / 確認 → 承認（確認が全部そろってから承認できる）。各フェーズの承認者のグループと人数、
   型ごとの上書きも含め、**GitStation のリポジトリの設定（DB。画面と API。変更は監査）** に置く。`.forge/` のファイルには置かない。
   変更はリポジトリの管理者。**フェーズを外す・減らす変更は、組織の管理者の承認も要る**。開いている MR にはマージの時点の設定を使い、緩めた変更は監査で目立たせる。
2. **統制の項目は DB の設定に置く**（型の定義には推奨だけ。ADR-0026 §5）:
   - Kanflow（代理実行、ADR-0025）からの文書の承認を認めるか — **既定は禁止**。認めても、本人が GitStation の確認の画面で 3 の再確認を通った場合だけ。
   - 機密区分を下げる変更（`confidential` → `internal` など）の承認者。
   - 同時の編集の緩め（ADR-0027）。
3. **本人の再確認**（**ADR-0021 の Amendment**）: フェーズのある承認の直前に、直近 5 分以内の Keycloak の認証でなければ再ログインさせる（OIDC の `max_age`、
   ID トークンの `auth_time` を確かめる）。**トークン（`gstn`・API）による文書の承認は拒否**する（再確認ができないため。`FG-AUTH-*` の新しいコード、
   権限の表に拒否の行）。
4. **承認した blob ＝ 発行する blob**（**ADR-0024 の Amendment**）: フェーズのあるリポジトリでは、MR が変えた各文書について、
   **マージの結果の blob が、承認した head の blob と同じ** であることをマージの条件にする（`evaluate_merge()` の新しい止める理由。target が同じ文書を変えて
   自動で合わさった場合も止める。利用者はブランチを更新して承認をもらい直す）。ロックの下でもう一度確かめる（ADR-0024 のマージの実行と同じ）。
5. **承認の記録**（監査の表、ADR-0018 で追記だけ・封印）: 承認者・日時・**意味**（`reviewed` / `approved`）・**承認の文言**（押した文言そのもの）・
   **文書ごとの id と blob の SHA**・再確認の時刻。文言には「QP-07-001 第 N 版（予定）」と出す — **版の番号はマージで確定する**（6）ので、確定した版は
   マージの後に記録へ結ぶ。
6. **文書の版**: 承認済みで文書の中身を変えた MR が `main` に入ると、その文書の版を 1 つ上げ、**タグ `refs/tags/doc/<ID>/r<N>`** を GitStation が作る
   （保護タグ。人とボットは作れない。GitLab のミラーにもそのまま送る）。**タグを版の正にし、DB の文書の索引はタグから作り直せる**。「軽微」の印の MR は
   版を上げずタグも作らない（印は型の必須の承認者の承認を要し、数値・ブロックの属性・ブロックの増減・見出しを変えた MR には付けられない — 決定的な検査）。
7. **「作成」の署名は承認とは別の操作**: 起案者（共同の起案者）が行い、承認の数に数えない。FG-REVIEW-0013（自分の MR は承認できない）は変えない。
   権限の表に許可（起案者）と拒否（それ以外）の行を足す。
8. **代理の承認の禁止**: 文書の承認を、ほかの人やボット・AI が代わりに行うことはできない（ADR-0017 のボットの承認の禁止に加えて）。2 の例外（本人の確認の画面を
   通る Kanflow）だけ。
9. フェーズの **なし** のリポジトリでは、再確認・意味・文言・blob の一致の条件（3〜5）を使わない（ふつうの MR の承認）。そこから将来 PDF を出すときは
   「承認の手順のない文書」と印字する（段 8）。

## Alternatives Considered

### 承認の設定をリポジトリのファイル（`.forge/`）に置く
- **Pros**: 版管理され、レビューできる
- **Cons**: 書ける人が「フェーズなし」に変える MR を出せる（統制を中身と同じ権限で外せる）
- **Why not**: 統制は DB と別の権限に置く

### target の先端が進んだら、すべての承認を失効させる
- **Pros**: 単純
- **Cons**: 関係の無い文書・コードの変更でも承認がやり直しになる
- **Why not**: 変えた文書の blob の一致だけを条件にすれば、必要なときだけやり直しになる

### 版の番号を承認の時点で決める
- **Pros**: 文言に確定した版を出せる
- **Cons**: 同じ文書の別の MR が先に入ると番号が食い違う
- **Why not**: 承認の正は blob の SHA。版はマージで確定し「予定」と表示する

## Consequences

### Positive
- 承認と発行される中身が必ず一致し、承認の意味・文言・本人の再確認が証跡に残る
- 統制をファイルの書き手が外せない

### Negative
- Keycloak の再ログインの流れ（ADR-0021）、`evaluate_merge()` の新しい理由（ADR-0024）、監査の新しい項目、文書の索引と版のタグの仕組みが要る
- フェーズのあるリポジトリでは `gstn` から承認できない（画面か、許可した Kanflow の確認の画面だけ）

### Risks
- 社内の規程が押印を前提にしている → 品質保証の部門の確認が accepted の条件（利用者の作業、並行）
- タグが多くなる（文書の数 × 版） → GitLab のミラーの負荷を段 4 で測る
- DB を失ったときの「軽微」の印 → 版はタグが正なので失わない。印そのものは監査の封印（ADR-0018）とバックアップ（O1）で守る
