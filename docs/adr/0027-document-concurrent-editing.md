# ADR-0027: 文書の同時の編集 — 改訂は文書ごとに 1 つ、期限つきの編集の宣言

**Date**: 2026-11-09
**Status**: proposed（計画 13 §7.5 と §13 の 5 を ADR にした。実装は計画 13 §12 の段 4。accepted は段 1 の試しの後）
**Deciders**: Masaki Fujikawa（ユーザー）、Claude

## Context

非エンジニアを含む複数の人が同じ文書を直すと、Git のふつうの流れ（各自のブランチ → マージで衝突を解く）では、取り合いが最後に分かり、
衝突の解消を非エンジニアにさせることになる。リアルタイムの共同編集は、承認の単位（どの版を誰が承認したか）を曖昧にし、Git とつなぐ部分が
大きい。利用者は「取り合いにならないこと」を求めた（計画 13 §7.5、2026-11-09）。

## Decision

1. **改訂は文書ごとに 1 つ**: 1 つの文書（`id`）を変える **開いている MR は 1 つまで**（`single_revision`）。2 つ目は **MR を開くときと
   マージのとき** に止める（push は止めない。下書きは自由）。止めたときは、進行中の MR を名指して案内する（`FG-DOC-*`）。
   判定は MR の変えたパスと文書の索引（id ↔ パス）で行う。訳（`<id>.<lang>.md`）は元とは別の文書として数える。
2. **緩めるのはリポジトリの設定（DB）だけ**: 型ごとに `single_revision`（既定）/ `free` を選べる。**型の定義のファイルには推奨だけ**を書く
   （ファイルに書ける人が統制を外せないように。ADR-0028 §2 と同じ考え）。変更は監査に残る。
3. **編集の宣言**（弱い規則）: 画面の「編集する」で、文書に宣言（誰が・いつから・どの MR）を付け、他の人に「編集中」を見せる。
   - 期限は操作がなければ **30 分**（画面を開いている間は延長）。切れても下書きは残る。
   - **解除**できるのは、宣言の持ち主・文書の `owner` のグループ・リポジトリの管理者（監査に残る）。
   - 1 つの改訂の中の共同の起案では、宣言を見出し（節）の単位にでき、節が違えば同時に書ける。
4. **後勝ちの上書きは作らない**: 画面の保存は、読み込んだときのコミットを持つ。その間に他の保存があれば、ブロック・段落の単位の 3 方向の合わせに回し、
   合わない箇所だけ利用者に選ばせる（`<<<<<<<` を見せない）。
5. **例外の並行**（大改訂の準備中の急ぎの訂正）: 文書の `owner` が明示の操作で 2 つ目を許す（監査に残る）。急ぎの方を先にマージし、
   大改訂の MR は合わせの画面に回る。フェーズのあるリポジトリでは、ADR-0028 §4 の「承認した blob ＝ マージの結果の blob」により、
   合わせた後に承認をもらい直す。
6. **ボット・AI** も同じ規則に従う（宣言のある文書・改訂中の文書は触らない。計画 13 §8.3）。`gstn doc status <ID>` で宣言と改訂中の MR を見せる。
7. **権限の表**に行を足す: 宣言の取得・延長・解除（本人 / owner / 管理者、許可と拒否）、例外の並行の許可、設定の変更。

## Alternatives Considered

### リアルタイムの共同編集（CRDT）
- **Pros**: 待たない
- **Cons**: 承認の単位が曖昧、「誰がどこを書いたか」がぼやける、Git との橋渡しが大きく保守が重い
- **Why not**: 規制の文書には承認の単位の明確さが要る

### 強いロック（貸出・返却）
- **Pros**: 分かりやすい
- **Cons**: 借りたまま忘れる、休みの人で止まる
- **Why not**: 期限・見える・解ける形（3）にして弱点を消し、強い規則は「開いた MR は 1 つ」（1）に置いた

### Git のふつうの流れだけ
- **Pros**: 作るものが無い
- **Cons**: 取り合いが最後に分かり、非エンジニアに衝突の解消をさせる
- **Why not**: 後ろの守り（4）としてだけ使う

## Consequences

### Positive
- 取り合いが「始める前に分かる」。承認の単位（1 つの MR）と編集の単位がそろう

### Negative
- 文書の索引（id ↔ パス）を MR の作成・マージの判定に使うため、索引の正しさに依存する
- 急ぎの訂正は例外の操作が要る

### Risks
- 索引が古く、2 つ目の改訂を見逃す → マージのときにも判定し直す（MR を開くときだけに頼らない）
- 宣言の期限切れで同時に書く → 4 の合わせで黙った上書きは起きない

## 実装の状況（段 4 の前半、2026-11-23）

- **作ったもの**: 文書の索引と文書の版（Git とマージ済みの MR から導く。ファイルには何も書かない）、改訂は 1 つの規則、編集の宣言。
  - 改訂中の文書は MR ごとに `forge.merge_request_documents`（migration `20270105100000`）に記録する。MR を開くとき（forge-web）と、
    版ごとの `check.spec_index` の仕事（forge-checks）で、マージベースと head の間で blob が変わった `.md` のうち文書（`doctype` と
    `<id>.md`、訳は `<id>.<lang>.md`）を導く。最も早く開いた MR が改訂を持つ。
  - **MR を開くときに止める**（`FG-DOC-0006`、409。型の定義 `.forge/doctypes/` の無いリポジトリでは何も読まない。導けない・5 秒を超えるときは止めずに記録して通す＝fail open。版の仕事でも同じで、仕事は失敗させない）。push は止めない。版の仕事が 2 つ目の改訂を見つけたら記録し
    （`forge.doc_revision.second_revision`）、`GET …/documents/{doc_id}/status` で `holds: false` と見せる。
  - 編集の宣言は `forge.document_edit_claims`（文書ごとに 1 つ、30 分、データベースの時計）。取得・延長・自分の解除は
    `DocumentEditClaim`（Developer 以上、人だけ）、他人の宣言の解除は `DocumentEditClaimRevoke`（Maintainer 以上、人だけ、監査
    `document.edit_claim.revoked`）。他人の生きた宣言は `FG-DOC-0007`。MR を開くと、その作者の宣言は解ける。**監査に残るのは他人の宣言の解除（revoke）だけ**（取得・延長・自分の解除は監査しない。ADR の 3 の「解除は監査に残る」は他人の解除を指す）。1 人が 1 つのプロジェクトで持てる生きた宣言は 20 まで。
  - 文書の版: `GET …/documents/{doc_id}/versions`。既定のブランチに適用されたマージのうち、文書の blob を変えたものが次の版。マージキューの着地も同じマージの記録（`merge_request_merges`）を残すので数える。
  - `gstn doc status|versions|claim|release`。
- **まだ作っていないもの**（段 4 の後半 part B、承認を変える別のブランチの後）: **マージのときに止める**（`evaluate_merge`）、
  電子の承認の追加分（ADR-0028）、「軽微な訂正」の印、版のタグ `refs/tags/doc/<id>/r<N>`、リポジトリの設定
  `single_revision` / `free`（今はすべて `single_revision`）、owner のグループによる解除、節の単位の宣言、画面（段 5）。

## Amendment（2026-11-28、マージの負荷試験 a-burst M4）— 一時的な失敗では MR を作らない（fail closed）

- **起きたこと**: a-burst（1 つのプロジェクトで同時に 32 の作成、深さ 2）で、MR を開くときの文書の導出が 58 回 5 秒の予算を使い切り、
  `forge.doc_revision.unavailable`（「one-revision rule is skipped this time」、warn）を出して **規則を確かめずに MR を作っていた**。
  マージのときに止める part B はまだ無いので、版の仕事の印（`second_revision`、ログと `held: false`）だけが残り、2 つ目の改訂が
  そのままマージできた。版の仕事も同じ予算で `Skipped` になると、その MR は持ち主として記録されず、後の MR も止まらない。
- **決めたこと**: MR を開くときに **一時的な理由で規則を確かめられなければ、作らずに `FG-DOC-0009`（503、繰り返してよい）で答える**。
  - `reason=budget`: 導出が予算（5 秒）を超えた。`reason=git`: git の手順が時間切れ・混雑・起動できない（FG-GIT-0001 / 0002 / 0004）。
  - `reason=lock_busy`: プロジェクトの改訂のロックが 2 秒で空かない（前は直列にせずに作っていた）。
  - `reason=refuse_unavailable`: 開いている改訂をデータベースから読めない（前は warn で通していた）。
  - 何も書かないので、利用者・クライアントはそのまま作り直せばよい。
- **変えないこと**: git が読めない文書（オブジェクトの欠け、壊れたリポジトリ）は一時的ではないので、段 4 のレビュー HIGH 1 の通り
  fail open のまま（記録して通し、版の仕事が後で記録する）。型の定義の無いリポジトリは今まで通り 1 回の小さな一覧だけ。
  版の仕事（`record_version`）も仕事を失敗させない（HIGH 2）まま。MR を開くときに記録できているので、版の仕事が飛ぶだけでは穴にならない。
- **代償**: 負荷の高いときに MR の作成が 503 を返しうる（前は黙って規則を飛ばしていた）。a-burst の道具は 503 `FG-DOC-0009` を
  再試行するように直す必要がある（別の変更）。予算そのものを超える理由（同時の作成と列車の組み立ての git の起動）は計画 18 の Q / P レーンで扱う。
