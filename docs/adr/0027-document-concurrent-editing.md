# ADR-0027: 文書の同時の編集 — 改訂は文書ごとに 1 つ、期限つきの編集の宣言

**Date**: 2026-11-09
**Status**: proposed（計画 13 §7.5 と §13 の 5 を ADR にした。実装は計画 13 §12 の段 4。accepted は段 1 の試しの後）
**Deciders**: Masaki Fujikawa（ユーザー）、Claude

## Context

非エンジニアを含む複数の人が同じ文書を直すと、Git のふつうの流れ（各自のブランチ → マージで衝突を解く）では、取り合いが最後に分かり、
衝突の解消を非エンジニアにさせることになる。リアルタイムの共同編集は、承認の単位（どの版を誰が承認したか）を曖昧にし、Git とつなぐ部分が
大きい。利用者は「取り合いにならないこと」を求めた（計画 13 §7.5、2026-11-09）。

## Decision

1. **改訂は文書ごとに 1 つ**: 1 つの文書（`id`）を変える **開いている MR は 1 つまで**（`single_revision`）。2 つ目は **MR を開くときと
   マージのとき** に止める（push は止めない。下書きは自由）。止めたときは、進行中の MR を名指して案内する（`FG-DOC-*`）。
   判定は MR の変えたパスと文書の索引（id ↔ パス）で行う。訳（`<id>.<lang>.md`）は元とは別の文書として数える。
2. **緩めるのはリポジトリの設定（DB）だけ**: 型ごとに `single_revision`（既定）/ `free` を選べる。**型の定義のファイルには推奨だけ**を書く
   （ファイルに書ける人が統制を外せないように。ADR-0028 §2 と同じ考え）。変更は監査に残る。
3. **編集の宣言**（弱い規則）: 画面の「編集する」で、文書に宣言（誰が・いつから・どの MR）を付け、他の人に「編集中」を見せる。
   - 期限は操作がなければ **30 分**（画面を開いている間は延長）。切れても下書きは残る。
   - **解除**できるのは、宣言の持ち主・文書の `owner` のグループ・リポジトリの管理者（監査に残る）。
   - 1 つの改訂の中の共同の起案では、宣言を見出し（節）の単位にでき、節が違えば同時に書ける。
4. **後勝ちの上書きは作らない**: 画面の保存は、読み込んだときのコミットを持つ。その間に他の保存があれば、ブロック・段落の単位の 3 方向の合わせに回し、
   合わない箇所だけ利用者に選ばせる（`<<<<<<<` を見せない）。
5. **例外の並行**（大改訂の準備中の急ぎの訂正）: 文書の `owner` が明示の操作で 2 つ目を許す（監査に残る）。急ぎの方を先にマージし、
   大改訂の MR は合わせの画面に回る。フェーズのあるリポジトリでは、ADR-0028 §4 の「承認した blob ＝ マージの結果の blob」により、
   合わせた後に承認をもらい直す。
6. **ボット・AI** も同じ規則に従う（宣言のある文書・改訂中の文書は触らない。計画 13 §8.3）。`gstn doc status <ID>` で宣言と改訂中の MR を見せる。
7. **権限の表**に行を足す: 宣言の取得・延長・解除（本人 / owner / 管理者、許可と拒否）、例外の並行の許可、設定の変更。

## Alternatives Considered

### リアルタイムの共同編集（CRDT）
- **Pros**: 待たない
- **Cons**: 承認の単位が曖昧、「誰がどこを書いたか」がぼやける、Git との橋渡しが大きく保守が重い
- **Why not**: 規制の文書には承認の単位の明確さが要る

### 強いロック（貸出・返却）
- **Pros**: 分かりやすい
- **Cons**: 借りたまま忘れる、休みの人で止まる
- **Why not**: 期限・見える・解ける形（3）にして弱点を消し、強い規則は「開いた MR は 1 つ」（1）に置いた

### Git のふつうの流れだけ
- **Pros**: 作るものが無い
- **Cons**: 取り合いが最後に分かり、非エンジニアに衝突の解消をさせる
- **Why not**: 後ろの守り（4）としてだけ使う

## Consequences

### Positive
- 取り合いが「始める前に分かる」。承認の単位（1 つの MR）と編集の単位がそろう

### Negative
- 文書の索引（id ↔ パス）を MR の作成・マージの判定に使うため、索引の正しさに依存する
- 急ぎの訂正は例外の操作が要る

### Risks
- 索引が古く、2 つ目の改訂を見逃す → マージのときにも判定し直す（MR を開くときだけに頼らない）
- 宣言の期限切れで同時に書く → 4 の合わせで黙った上書きは起きない
