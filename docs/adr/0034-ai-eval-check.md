# ADR-0034: AI の評価のチェック `forge/ai-eval` — ベンチの報告の形、基準との比較、宣言したパイプラインだけ

**Date**: 2026-11-14
**Status**: proposed（accepted は P17-2 `feat/ci-ai-eval-check` の `rust-reviewer`・`silent-failure-hunter` のレビューで CRITICAL / HIGH が無いとき）
**Deciders**: Masaki Fujikawa（ユーザー、2026-11-13「この計画で進めて」: 計画 17 §1.6・§5.4・§9）、Claude

番号について: 計画 17 は P17-2 の ADR を「ADR-0033」と書いたが、0032 を 2 本の枝（A1 `feat/core-agent-part-format` と C13 `feat/git-ssh-transport`）が
同時に使っており、どちらかが 0033 に移る。重ならないよう 0034 にした。計画 17 の P17-3 が「ADR-0033 で決める」とした `forge-doc` の doctype の判断は、
P17-3 が自分の ADR（または本 ADR の Amendment）で決める。

## Context

計画 17 は PFS の中央 AI の資産（スキル・プレイブック・プロンプト・モデル）を GitStation の MR で直し、評価ベンチの結果で **直ったことを数字で示してから**
リリースする。ベンチは CI のジョブ（GPU の Runner `gpu-eval`、P17-1）で動くが、ジョブはチェックを書けない（ADR-0029 決定 8）。
GPU の出力は温度 0・シード固定でも完全には一致しないので、1 回の結果で合否を決めると MR が赤く揺れる。ベンチが動かない・基準が無いときに
「何も無いので成功」になると、ゲートが黙って外れる（契約 2）。そして計画 17 §9 は「宣言したリポジトリの外の動きを何も変えない」と決めた。

## Decision

1. **入口は「パイプラインが報告を宣言したか」**。`.forge-ci.yml` のジョブが成果物のパス **ちょうど `eval-report.json`**（作業ツリーのルート、
   `forge_ci::EVAL_REPORT_PATH`）を宣言したときだけ、計画の段で `ci_pipelines.ai_eval_job` にそのジョブを記録する（追記のマイグレーション
   `20261217100000`）。宣言の無いパイプラインには `forge/ai-eval` の行が現れない（必須にもならない）。選ばれたジョブの 2 つ以上が宣言したら
   計画は `invalid`（FG-CI-0001 `eval_report_declared_twice`）。
   - 計画 17 §0.4 はプロジェクトの設定 `ai_assets.enabled` を「`forge/ai-eval` の判定も呼ばない」印に挙げたが、同じ計画の P17-2 の行・§1.6・§9 は
     「`eval-report.json` を宣言したパイプラインだけで動く」「プロンプトやモデルを持つどのリポジトリでも、宣言すれば使える汎用の部品」と書く。
     **P17-2 は行と §9 に従い、宣言だけを入口にする**。理由: 宣言は `.forge-ci.yml` の明示の 1 行で、`evals/` のような名前のディレクトリに偶然
     当たることが無い（§0.4 が防ぎたかったこと）。`ai_assets.enabled` は P17-3 が足し、AI 資産の lint・`forge/risk` の 2 つの規則・リリースの作成を
     止める印として使う。`pfs-ai/assets` では `.forge-ci.yml` が保護パスなので、宣言を MR 1 本で外すことはできない（外せば必須の `forge/ai-eval` が
     現れず、マージは待つ）。
2. **報告の形は固定・版付き**（`gitstation.ai-eval-report/v1`、`forge_core::ai_eval`、`docs/ai-eval-report.md`）。ケースごとの `runs` / `passes`、
   `kind`（`regular` / `safety` / `reproduction`）、5 つの指標。知らないフィールドは拒み、1 MiB・5000 件・15 回まで。**基準も同じ形**
   （`evals/baselines/<models>.json`、夜間の結果から人が承認したもの）で、**ベースのブランチとの merge base から読む**（下の Amendment 1）。
3. **判定は純粋な関数**（`forge_core::ai_eval::evaluate`）。多数決（`passes * 2 > runs`）、安定（全部の回が同じ）と不安定。ゲートは計画 17 §1.6 の
   1〜4: 安全のケースは全部の回で合格かつ基準のものが全部ある、再現のケースは多数決で合格かつ基準で既に緑でない、基準で全部合格の `regular` が
   半分以下に落ちない、指標は許す差（−0.02 / +0.02 / +20 %）の内。**基準で不安定なケースはどちらにも数えず**、一覧と件数に出す。許す差は
   **基準の `allowed` だけ**から読む（報告の `allowed` は無視）。
4. **成功にしないもの**: 宣言したジョブが成功していない・報告が無い・保存したファイルが無い（FG-AIASSET-0002、warn、runbook `ai-eval-bench`）、
   報告が v1 でない・保存のときの sha256 と合わない（0007）、基準が無い・読めない・`models` が違う（0003）。どれも `error`。
   読みの一時の失敗（保存先・git・DB・リポジトリの準備中）は **何も書かない**（次の回にやり直し、監督が失敗の続きをログに出す。回数の上限は Amendment 4）。
5. **書くのは forge の worker**（タスク `ci_ai_eval`、10 秒ごと、保存先があるときだけ）。`ci/pipeline` と同じ形: system（ラベル `forge-ci`）、
   報告者なし、`checks::write_run`（コミットの advisory lock、`check.completed` は結論が変わったときだけ）。パイプラインの状態ごとに 1 回
   （`ci_pipelines.ai_eval_status`）。ファイルと git の読みはトランザクションの外で行い、書く時にパイプラインの状態と宣言したジョブの `attempt` が
   読んだときと同じことを確かめる（違えば何もしない）。同じコミットに宣言したパイプラインが複数あれば **一番新しいもの** だけが書く
   （宣言の無い新しいパイプラインはチェックを取り上げない）。
6. **予約**: `forge/ai-eval` は `forge/` の名前（`FORGE_REPORTED_CHECKS`）。HTTP の `CheckWrite` は `forge/` を全員に断る。CI のジョブ（ベンチを
   動かしたジョブ自身のトークン）は `authorize()` の CI の腕でチェックの書き込みを断られる。権限の表に Job・サービスアカウント・エージェントの
   deny の行を足した。
7. **MR に比較表**: チェックの要約（Markdown、64 KiB の内）に判定・指標の表・所見（コードと理由）・ケースの表（止めるもの → 不安定 → 直った →
   不合格 → 合格、最大 200 行）。製造の技術者向けの画面は P17-9。
8. **エラーコード**は領域 `AIASSET`。計画 17 §5.4 の仮の番号に合わせ 0002 / 0003 / 0004 / 0006 を使い、報告の形の誤りに 0007 を足した。
   0001 ManifestInvalid（P17-3）と 0005 ModelDigestMismatch（P17-1、alert）はその MR のために空けておく。

## Alternatives Considered

### `ai_assets.enabled` を入口にする（宣言と設定の両方を要る）
- **Pros**: §0.4 の文言に字面どおり合う。
- **Cons**: 設定は P17-3 で入るので P17-2 だけでは動かない。§9 の「どのリポジトリでも宣言すれば使える」と矛盾する。宣言のある `pfs-ai/assets` で
  設定が `false` に戻ると、必須の `forge/ai-eval` が現れずマージが待つだけで、何も守らない。
- **Why not**: 宣言は既に明示のオプトインで、偶然には当たらない。

### ジョブにチェックを書かせる（ジョブのトークンに `forge/ai-eval` だけ許す）
- **Why not**: ADR-0029 決定 8（ジョブはチェックを書けない）を崩す。ベンチのスクリプト（AI が直しうる資産を読む）が自分のゲートを緑にできる。

### 基準をパイプラインのコミット（MR の head・マージ結果）から読む（最初の案、レビューで取り下げ）
- **Pros**: モデルを変える MR が新しい基準を同じ MR で足せる（計画 17 §6）。
- **Cons**: MR が自分のゲート（ケース・`allowed`）を緩め、その緩めた基準で自分を緑にできる。保護パスの承認はマージの条件で、
  チェックの結果そのものは緩んだ基準のまま出る。
- **Why not**: ゲートを判定される側が決めてはいけない（レビュー HIGH 3）。

### 1 回の結果で決める（多数決なし）
- **Why not**: GPU の揺らぎで MR が赤く揺れ、ゲートが信用されなくなる（計画 17 §8）。

## Consequences

### Positive
- ベンチが動かない・基準が無い・報告が壊れたとき、必ず `error` とコードが残り、ログ（`forge.ai_eval.check_written` の `error_code`・`reason`・`detail`）と
  catalog から原因に辿れる。
- 宣言の無い普通のリポジトリでは何も変わらない（行も、必須のチェックも、worker の処理も無い）。
- 判定は純粋な関数で、DB や GPU なしに試せる。

### Negative
- v1 の指標は p95 が 1 つだけ（重大度ごとではない）。予算の指標も無い。足すときは `schema` を上げる。
- `forge/ai-eval` はマージ結果で「古い」の扱い（`reported_on_merge_results`）を持たない。head や今のマージ結果の行を使い、マージキューの列車は
  ベンチをやり直さない（MR の版の結果を使う）。ターゲットが進んだ後にベンチをやり直させたいときは、別に決める。
- 報告のファイルは成果物の 30 日の保持に従う。30 日より前のパイプラインの状態が変わる（再実行）と、新しい試行の報告を読む。

### Risks
- 合計の指標（的中率など）はベンチの数字をそのまま信じる。ケースごとのゲートは指標に頼らない。ベンチのイメージはダイジェスト固定で、変えるのは保護パスの MR。
- ベンチの採点が PFS の推論のコードと違う → 計画 17 §0.3 のとおり、ベンチのイメージは PFS の `iotpf-ai-service` のダイジェスト固定。
- 許す差が緩すぎ・きつすぎ → 計画 17 §1.6 のとおり、最初の 4 週の実測で基準の `allowed` を決め直す（保護パスの MR）。
- GPU の Runner が長く無い → `error` が続き MR が待つ。warn の FG-AIASSET-0002 と runbook `ai-eval-bench`（人が承知して通す抜け道は作らない）。

## Amendment 2026-11-14（P17-2 のレビュー: rust-reviewer・silent-failure-hunter、HIGH 4 件）

1. **基準はベースのブランチとの merge base から読む**（HIGH 3）。ベースのブランチは MR のパイプラインなら MR のターゲット、マージキューの列車なら
   その列車のブランチ、それ以外（push・手動・定期）はリポジトリの既定のブランチ。パイプラインのコミットとそのブランチの先端の `git merge-base`
   （browse API、argv・時間切れ）で決めたコミットの `evals/baselines/<models>.json` を読む。merge base が無い（ブランチが無い・履歴を共有しない）ときは
   `error`（FG-AIASSET-0003 `base_unresolved`）。MR の中の基準の変更（`allowed` を含む）は、その MR 自身の判定には効かない。
   新しいモデルの基準は **先に別の MR で入れる**（保護パス: 承認者の人の承認）。モデルを変える MR はその後で、入った基準と比べる（計画 17 §6 の「同じ MR で
   足す」をこう読み替える）。`main` への push のパイプラインは、自分のコミットが merge base なので、マージ済み（承認済み）の基準を読む。
2. **ケースの種類は基準のもの**（HIGH 1）。基準にあるケースは基準の `kind` で判定し、報告が別の種類を書いたら `case_kind_changed`（失敗）。
   報告が決めてよいのは、新しいケースの種類と、`regular` を `reproduction`（厳しい方）にすることだけ。
3. **空・欠けを成功にしない**（HIGH 2）。`cases` が空の報告・基準は形の誤り（FG-AIASSET-0007 `cases_empty`）。基準で全部の回に合格した `regular` の
   ケースが報告に無ければ `case_missing`（失敗）。安全のケースは基準の回数以上（`safety_runs_short`）。
   これで MR のベンチは「関わるケースだけ」ではなく、基準で安定に合格しているケースを全部動かす必要がある（計画 17 §1.6 の MR の範囲より広い。
   GPU の時間が足りなければ、基準を MR 用と夜間用に分ける案を P17-4 で決める）。
4. **読めない失敗も必ず結論にする**（HIGH 4）。報告・基準の読みの失敗（保存先・git・リポジトリの準備中）は数え（`ai_eval_failures`）、
   10 秒から倍々で最大 10 分あけて（`ai_eval_retry_at`、追記のマイグレーション `20261217100100`）やり直す。5 回目、または内部の誤り
   （待っても直らない）で `error`（FG-AIASSET-0002 `read_failed`、`detail` に元のコード）を書き、warn で 1 回ログに出す。待ちの一覧は
   やり直しの時刻の順なので、失敗を続けるパイプラインが新しいものを止めない。
5. **細部**: 24 時間を越えて `pending` / `running` のパイプラインは `error`（`pipeline_stale`）。報告のファイルは開いたファイルの大きさを確かめてから
   最大 1 MiB + 1 バイトだけ読む。`error` の結論はすべて warn でログに出す。`.forge-ci.yml` が壊れて計画が `invalid` になったパイプラインには
   宣言のジョブが無いので `forge/ai-eval` は書かない（`ci/pipeline` が `failure` で止める。必須の `forge/ai-eval` はその版で現れず、マージは待つ）。
