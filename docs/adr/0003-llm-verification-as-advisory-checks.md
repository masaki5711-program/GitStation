# ADR-0003: ローカル LLM による検証は Checks API の「助言」チェックとして出す

**Date**: 2026-10-26
**Status**: accepted
**Deciders**: Masaki Fujikawa（ユーザー）、Claude

## Context

マージとパイプラインの検証にローカル LLM（Ollama、qwen3.8 27B を基準）を使う。LLM の出力は
決定的ではなく、差分には攻撃者が書いた文も含まれうる（プロンプトインジェクション）。
一方で、LLM の結果をマージ条件に組み込めなければ活用されない。

## Decision

- LLM の結果は **Checks API のチェック**（`forge/ai-review`、`forge/acceptance` など）として出す。既定は **助言**（マージを止めない）で、プロジェクトの設定で必須にできる。
- LLM の判断だけでマージやデプロイを実行する経路は作らない。
- LLM が応答しない・出力が不正なときは、チェックを成功にせず `error` にし、エラーコード（領域 `LLM`）で記録する。
- 出力は JSON スキーマで検証する。LLM に変更系の道具は渡さない。
- 決定的に計算できることはコードで計算し、LLM には根拠として渡す。

## Alternatives Considered

### LLM の判定を常に必須にする
- **Pros**: 検証が確実に行われる
- **Cons**: 誤検知でマージが止まり、LLM の停止が開発の停止になる
- **Why not**: 評価セットで品質を測るまでは、必須にする根拠がない

### LLM を MR のコメントだけに使う（チェックにしない）
- **Pros**: 実装が単純
- **Cons**: マージ条件に組み込めない。結果の集計と評価がしにくい
- **Why not**: Checks API に統一すれば、CI・kanflow・LLM を同じ仕組みで扱える

## Consequences

### Positive
- 検証を足してもマージ条件のロジックは変わらない
- 採用率と誤検知率を測り、評価セットで比べてからプロンプトやモデルを変えられる

### Negative
- 助言のままだと読まれない可能性がある

### Risks
- GPU を kanflow と共用するため混雑する → ゲートウェイで同時実行数と優先度を制御し、待ち時間を監視する
