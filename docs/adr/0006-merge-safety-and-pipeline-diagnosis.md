# ADR-0006: main を壊さない仕組みと、機械が読めるパイプラインの診断

**Date**: 2026-10-26
**Status**: accepted
**Deciders**: Masaki Fujikawa（ユーザー）、Claude

## Context

AI で開発が速くなると、同時に開く MR とマージの頻度が増え、衝突と「単独では成功するが組み合わせると壊れる」
変更が増える。AI エージェントが push とパイプラインを繰り返すため、失敗の原因を人が読んで伝えていては遅い。

## Decision

- マージ可否は `git merge-tree --write-tree` で作業ツリーなしに判定する。開いている MR 同士の衝突も予測する。
- MR のパイプラインは **マージ結果** で実行し、対象ブランチが進んだらチェックを「古い」とする。
- **マージキュー** を M4 で提供する（当初の M8 から前倒し）。
- AI による衝突の解消案は別ブランチのコミットとして提案し、人間が承認して適用する。ロックファイルなどは再生成のコマンドで解消する。
- パイプラインの失敗は指紋でまとめ、既知の直し方（決定的）と LLM の推測を分けて、**機械が読める診断 API** で返す。
- パイプライン定義は push の前に `lint` / `plan` で自己確認できる。
- デプロイ後のヘルスチェックの失敗時は、stg は自動ロールバック、prod は人間の判断。

詳細: `../../../docs/plan/04-ci-cd-merge-safety.md`。

## Alternatives Considered

### ソースブランチだけでパイプラインを実行する
- **Pros**: Runner の負荷が小さい
- **Cons**: 意味的な衝突を見逃す
- **Why not**: main の破損は全員の作業を止める

### マージキューを後回しにする（M8）
- **Pros**: 初期の実装が軽い
- **Cons**: MR が増えたときに main の破損が頻発する
- **Why not**: 製品の目的（AI による加速）がまさに MR の増加をもたらす

## Consequences

### Positive
- AI エージェントが失敗を読んで自分で直すループが成立する
- main が常に緑に保たれる

### Negative
- Runner の負荷が増える（マージ結果のパイプライン、マージキュー）

### Risks
- Runner の台数不足 → M4 の開始前に Runner のホストを確認する（未定）
