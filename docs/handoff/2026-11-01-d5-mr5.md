## 3. 計画・指示からのずれ

1. **イベントのクラス**: `project.moved` は integration（計画の答え）。`group.moved` / `user.renamed` は呼び出し元の例の
   integration ではなく **admin**: プロジェクトを指さないインスタンス全体のイベントで、ADR-0016 §5 の表では admin。祖先の
   移動で動いたプロジェクトにはイベントを出さない（1 変更 100 件の上限。監査の行はプロジェクトごとにある）。
2. **`Retry-After` なし**（計画にない）。
3. **移動の対象が見えない・無い・プロジェクトの名前空間**はどれも FG-REPO-0005（MR1 の `target_not_visible`）。
4. **`moved` の墓標の行き先が「見える」のは役割のある人と管理者だけ**（internal のプロジェクトやグループでも、役割のない人には
   403 ではなく 404）。トランザクションの中の事実（`TombstoneAccess::Moved`）に可視性がないため、両方で同じ式にした。
5. **トップレベルのグループの名前の変更は管理者だけ**（ADR の「名前だけの変更は今の親 = `TopLevel`」をそのまま適用）。
6. 運用の CLI は `*_decided` を forge-hosting 経由で呼ぶ（ガード `decided_callers` のため）。呼び出し元のロールをロックする
   ユーザーとして id 0 を渡す。
7. 新しいマイグレーションなし。権限の表（純粋な `authorize()` の行）は MR1 のまま。

## 5. 残り・リスク

1. 独立レビュー → 指摘の修正 → `--no-ff` で統合。
2. 連携は、祖先のグループの移動・ユーザーの名前の変更で動いたプロジェクトのパスの変化をイベントで知らない（id で識別する前提）。
   必要になったら、プロジェクトごとのイベントを派生イベント（`DerivedTx`）で分けて出す案がある。
3. 移動の 302 は upload-pack の advertisement だけ（既存の dispatcher の規則）。画面の殻は公開なので墓標を見ない（M2 の SPA の
   `replaceState`）。
4. 名前の変更の判定（自分のロール）はローダーとトランザクションの両方で `target_of` と同じ式。片方だけ変えると
   `reconfirm` の判定が食い違う（テスト `a_rename_is_decided_on_the_projects_owner_not_the_parent` が固定）。
5. `gstn` の専用コマンド（`repo rename|transfer`、`group transfer`、`namespace release`）は `feat/client-gstn-hosting-more`。
