## 2a. レビューの指摘への対応（2 つ目のコミット）

- MEDIUM: 同じプロジェクトの完全削除の重なり。プロジェクトごとのセッションの advisory lock（forge-db `PurgeLock`、キー
  `(0x46475055, id mod 2^31-1)`）を `start` から `finish` まで持つ。取れなければ `deferred in_progress`。保存先の削除
  （新しい `StorageRoot::remove_blocking`）はロックを持つタスクで動き、120 秒を超えたら `deferred removal_running`、ロックは削除が
  終わるまで放さない。テスト: worker と `--now` の同時実行で削除は 1 回・他方は deferred、長い削除の最中の次の回は deferred。
- LOW: `storage_removed = existed || swept > 0`。LOW: 作成のジョブの状態の読み取りの失敗は `step=provision_check`（ロックは `step=lock`）。
  LOW: `--now` のまとめは新しい FG-REPO-0021 PurgeBatchIncomplete（warn）。終了コードは 0 以外、alert は二重にならない。

## 3. 計画・指示からのずれ

1. **`project.purged` は admin クラス**（呼び出し元の指示は integration）。承認済みの計画の答え「`project.purged` admin class, other
   project.* integration」に従った。理由: プロジェクトが無いので、integration の条件（そのプロジェクトの Reporter）を `authorize()` が
   判定できない。integration にするなら `event_type.rs` の 1 行と ADR-0016 の追記を変える。
2. **`forge serve` ではなく `forge worker` に配線**。背景の処理はすべて worker（ADR-0016 §7）で、保存先の削除も worker の権限で行う。
3. **墓標**: 「解放」は、古いパスの `moved` の墓標を消すのではなく、行き先を失わせる（`ON DELETE SET NULL`、ADR-0015 の既存の規則:
   行き先の無い `moved` は `deleted` と同じに扱う）。パスは塞いだまま、解放は墓標の解放の操作で。今のパスには `deleted` の墓標を書く。
4. git は使わない（ディレクトリの削除はファイル操作だけ）。「git の時間切れ」のテストは、保存先の締め切り（FG-REPO-0003 `reason=deadline`）で代えた。
5. マイグレーションなし（`purge_after` の部分索引は見送り。ADR-0015 の追記）。ルートなし（権限の表・gstn の表は変わらない）。

## 5. 残り・リスク

1. 独立レビュー → 指摘の修正 → `--no-ff` で統合。
2. `forge doctor` に「`purging` のまま古い」検査がない（毎回の FG-REPO-0020 のログで分かる）。
3. 作成のジョブが `running` のままリースが切れない限り、そのプロジェクトの完全削除は待ち続ける（`forge.repo.purge_deferred` が毎回出る）。
4. 裏で続く削除（`removal_running`）が失敗しても FG-REPO-0020 にはならず `forge.repo.purge_removal_ended`（warn）だけ。次の回が
   やり直し、そこで失敗すれば FG-REPO-0020 になる。
5. 段 3 が失敗して次の回に再開し、ディレクトリがもう無ければ、記録の `storage_removed` は `false`。
6. 毎回失敗する（例: シンボリックリンクのある）プロジェクトは `purge_after` が古い順の先頭に残り、1 回 20 件の枠を 1 つずつ使い続ける。
   20 件すべてがそうなると他は進まない（FG-REPO-0020 が毎回出るので気づける）。
