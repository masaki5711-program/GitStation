## 3. 始め方

1. **`main` への統合**（利用者の判断。PC で行うか、Claude に指示する）:
   GitStation の `claude/brave-cray-w62c35` を `main` に `--no-ff` で統合し、push（PC から社内 GitLab へもミラー）。以後の M3 のブランチは `main` から切る（`feat/<area>-<topic>`）。
2. **開発の環境**（テストサーバーで開発もするなら）: Rust（`rust-toolchain` / `rust-version` 1.88 以上）、Node 22 以上、git、PostgreSQL 16。
   開発用の DB は `docker compose -f ops/dev/compose.yml up -d --wait`（127.0.0.1:55432、合成の資格情報）。
   Docker が無ければ PostgreSQL 16 を直接立て、`forge_dev`（scram、パスワード `forge_dev`）で接続できるようにする。
   テストは `FORGE_TEST_DATABASE_URL=postgres://forge_dev@127.0.0.1:55432/forge_dev cargo nextest run --workspace -j 4`
   （**URL にパスワードを書かない**。設定が `password_in_url` で拒否する）。全体のテストは同時に 1 本だけ。
   - 注意: テスト用の DB のクラスタは**ロールがクラスタ全体で共有**される。全体のテストはロール（`forge_app` など）のパスワードを合成の値に戻すので、**テストサーバーで動かす GitStation 本体の PostgreSQL とは別のクラスタ**にする。
   - ディスク: `target/` は数十 GB に育つ。足りなくなったら古いテストの実行ファイル（`target/debug/deps`）を消す。
3. **M3 の計画を作る**: 計画 01 §8 の M3 の行を正とし、`planner` で **`docs/plan/11-m3-plan.md`** を書く（計画 10 と同じ形: 前提、設計、MR の分け方、各 MR のテストと評価役、利用者に決めてほしいこと）。**実装の前に利用者の承認を取る**（CLAUDE.md）。
4. 承認後は MR ごとに: tests first → 実装 → ゲート（fmt / clippy / nextest / gen-catalog / gen-authz、web は lint・typecheck・test・build・i18n・journey）→ 評価役（1 差分 1 言語レビュアー + 該当する専門の評価役、再レビューは指摘した評価役が修正差分だけ、最大 2 回）→ 統合 → 全体のテスト → push。
