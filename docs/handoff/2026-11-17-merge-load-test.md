# 引き継ぎ: 大量のマージの負荷試験（2026-11-17）

利用者の依頼:「工場でシステム開発だけではなく文章のマージも行う想定なので　相当数のマージが入る可能性があります」。
この PC の試験環境（compose `gs-m3-test`、forge serve / worker はホストのプロセス）で、文書とシステムのコードの大量のマージを測った。
**製品は調整していない**（設定・コードとも試験の前のまま）。データはすべて合成。スクリプトは `ops/loadtest/`（README あり）。

run1 では MR の作成の多くが 503 で失敗し（発見 F1）、b と c の規模が足りなかったため。

## 2. ボトルネック

1. **worker のジョブは 1 本ずつ**（`forge worker` の job runner は 1 件ずつ取る、`crates/forge-cli/src/worker/jobs.rs`）。MR 1 本ごとに
   `merge_request.refresh`・`mergeability`・`conflict_scan`・`check.risk`・`check.spec_index`・`check.spec_drift`・`ci.pipeline_create` が積まれ、
   `main` が進むたびに開いている MR すべての `mergeability` が積み直される（開いている MR × マージの回数）。
2. **`conflict_scan` が重い**: run1 の 12 分で 85 回、合計 573 秒（1 回 p50 5〜7 秒、最大 15 秒）。半分以上は `FG-REVIEW-0022 peers_capped`
   （相手 50 本で打ち切り、試した組 0）で、何も分からないまま worker の時間を使う。
3. **キューの列車がジョブの列に並ぶ**: `.forge-ci.yml` の無い文書のリポジトリでも、列車の `ci/pipeline` は `ci.pipeline_create` のジョブが
   「パイプラインなし」と決めるまで `Planning`（待ち）。このジョブが数百件の後ろに並ぶので、A の 1 バッチ（4 件）に 3〜4 分かかった。
   滞留が消えた後は 1 バッチ 15〜30 秒（8〜16 件/分）。
4. **古い `mergeability` のジョブが消えない**: dedup の鍵に `check_seq` が入るため、`main` が進むと古い seq のジョブも残る（10:34 に 56 本の MR に 256 件）。
5. **MR の作成が「閲覧」の上限に当たる**: 1 つのリポジトリの git の閲覧は同時に 8 まで（`BrowseLimits::max_per_repo`）で、超えると**待たずに** 503。
   MR の作成（source branch の確認）もこれを使うので、同じリポジトリに 10 本以上同時に作ると失敗する。
6. **C の CI は MR の数の 2 乗で増える**: `main` が進むたびに開いている MR のマージ結果のパイプラインが作り直される（40 本で 291 本）。
   今回はジョブが 1 秒なので目立たないが、ジョブが数分の本物の CI では Runner 1 台では回らない。

## 4. 推奨

1. **MR の作成（と他の書き込み）は閲覧の上限で即座に断らず、短く待つ**（global の pool と同じ `acquire_timeout` の待ち）か、作成の git の確認を
   ジョブへ回す（F1）。それまでは、クライアント（gstn・Kanflow 連携）が `FG-GIT-0004` を 1 秒あけて再試行する（run1r で 30/30・40/40 が成功）。
2. **worker のジョブを並列に**（kind ごとの上限つき、例 4〜8 本）し、キュー・マージに直結する種類（`ci.pipeline_create` の列車、`merge_request.refresh`）を優先する（F2）。
   `mergeability` は MR ごとに最新の seq だけを残す（古い seq を取り消す）。
3. **文書の近道**: `.forge-ci.yml` の無いリポジトリでは、列車の `ci/pipeline` をジョブを待たずにその場で「パイプラインなし（成功）」と決める（ボトルネック 3）。
   滞留が無ければ文書は 1 バッチ 15〜30 秒で、8〜16 件/分出ていた。
4. **`conflict_scan` は相手が上限を超えるときは走らせない**（または相手の数を減らして本当に試す）（F3）。
5. **バッチの大きさは 4 のままでよい**: 衝突の無い文書では 4 件のバッチがほぼすべて landed で、詰まりはバッチの外（ジョブの列）にあった。
   C のように壊れる MR が混ざると、赤いバッチ 1 つで 2〜3 本の列車が増える。8 に上げると二分の回数が増える。上げるのは F2 の後に測ってから。
6. **Runner**: C の CI は MR の数の 2 乗で増える（40 本で MR のパイプライン 291 本）。ジョブが数分の CI なら、`main` が進んだときの
   マージ結果のパイプラインを作り直さない（キューの列車で確かめるので）か、Runner を 3〜4 台にする。文書のリポジトリには Runner は要らない。
7. **文書のリポジトリの既定**: 新しいプロジェクトで文書（`doctype` の `.md`）が見つかったら `forge/doc-lint` を必須にする（または自動マージを止める）（F5）。
8. **push**: 共有のアカウントやボットを使うなら `max_per_principal` を上げるか、ボットごとにトークンを分ける（F4）。
