## 2. 入れたもの

- **新しいクレート `forge-oidc`**（機能クレート。`forge-web / forge-cli → forge-oidc → forge-auth / forge-db → forge-core`。forge-hosting には依存しない。`dependency_direction` の表に足した）
  - `http`: reqwest 0.12（`rustls-tls-manual-roots`、ring）。`no_proxy()`、リダイレクトに従わない（3xx は `reason=redirect`）、公開 CA なし（`auth.oidc.ca_file` だけ）、接続 2 秒、送信と本文を合わせた呼び出しごとの時間切れ、本文 1 MiB まで。失敗は FG-AUTH-0015 の `call` と `reason`。応答の本文はログにもエラーにも入れない。
  - `discovery`: `issuer` の完全一致、各エンドポイントは issuer と同じオリジンだけ。プロセスの中で 1 回取って持つ（同時の最初の要求は 1 つの取得を待つ。失敗はキャッシュしない）。`Oidc::prefetch` が起動時の 3 回（1 秒・2 秒の待ち）。
  - `keys`: `use` は `sig` かなし、RSA は 2048〜8192 bit・`e` は奇数で 3〜33 bit、EC は P-256・x/y 32 バイト・曲線の上（ring の一時の ECDH で相手の点を検証）。壊れた鍵は `kid` に理由を残す（`key_invalid` の `detail`）。
  - `jwks`: 10 分のキャッシュ、知らない `kid` の取り直しは 60 秒に 1 回まで。
  - `jwt`: jsonwebtoken `=11.1.0`（`default-features = false`）＋自前の ring の `CryptoProvider`（RS256 / ES256 の検証だけ、署名なし、`KeyUtils` も含めてすべて `Result`）。`JwtVerifier::new` だけが provider を入れる（別の provider があれば FG-SYS-0001 `jwt_provider_conflict`）。ヘッダーの `alg` を先に許可リストで見る、`kid` 必須、kty と alg の組、JWK の `alg` との一致。`iss`・`aud`・`exp`・`nbf` はライブラリ、`iat`（必須・未来は 60 秒まで）・`azp`・`nonce`（定数時間）・`sub` は自前。
  - `state`: `state`・`nonce`・PKCE の verifier（各 256 bit、OS の CSPRNG）・`next`・作成時刻を AES-256-GCM（`oidc-state`）で封じた `__Host-gstn_oidc`（10 分）。`next` は `/` か、`//`・`\`・`#`・制御文字なしで ADR-0015 のパーサーが読めるパスだけ。
  - `flow`（`Oidc::start` / `Oidc::complete`）: 認可コード + PKCE S256、`response_mode=query`、`scope=openid`。コールバック: state の Cookie → state の比較 → トークンのエンドポイント（`client_secret_basic`、5 秒。4xx は FG-AUTH-0011 `code_rejected`、5xx は 0015）→ ID トークンの検証 → `forge_db::identities::login_decided`（`authorize(anonymous, SessionCreate, Admission)` を変更の中で）→ 既存なら `last_login_at` → ブラウザの今のセッションを `revoke_presented`（`reason=logout`）→ 新しいトークンを先に作り、リフレッシュトークンと ID トークンをその `public_id` を AAD に封じる → `sessions::issue_with_token`。成功は `forge.auth.login_succeeded`。

## 3. ADR・計画との違い（決めたこと）

1. **入場の判定を結び付けの衝突より先に行う**（社員番号の利用者の状態で `SessionCreate`、新規は `New`）。ロールのない人が FG-AUTH-0014（warn）を出さないため。ボット・サービスアカウントは `NotHuman` の FG-AUTH-0013（ADR §4 の 4 は `privileged_account` に含めていた）。管理者は `privileged_account`。
2. `auto_link=false` で社員番号が既存の利用者 → FG-AUTH-0014 `auto_link_disabled`（MR1 の引き継ぎの LOW）。
3. FG-AUTH-0014 に `employee_number_taken`・`claim_invalid`、CLI の `subject_linked`・`already_linked`。FG-AUTH-0015 に `body`・`request`・`issuer_mismatch`。
4. 監査の actor: 結び付け・作成は `Anonymous`、前のセッションの失効と新しいセッションは `User(結んだ利用者)`。
5. `link_by_operator` は結び直しをしない（`forge_app` に DELETE がない）。
6. `SessionCreate` は `PLANNED` ではなく新しい `DECIDED_IN_ROUTE`。**エージェントモデルの `authz-coverage` のゲートが `decided_in` を知らなければ足すこと**。
7. ログインの開始の制限は固定の値（設定にしない）。
8. 模擬の OP のパスは定数（forge-web の「registry 以外のルート禁止」のテストのパターンに掛けない）。

## 4. `forge admin user link-identity` — ADR-0019 §8 の例外（CLAUDE.md 契約 4、`aab2ee2` で承認済み）

> ADR-0019 §8 への追記の文案: `forge admin user link-identity --user <username> --issuer <issuer> --subject <sub>`（M2 MR4、ADR-0021 §4 2a）は、
> トークンのコマンドや移動・名前の変更のコマンドと同じく `authorize()` を通らない運用のコマンドである。ホストの操作者が信頼の起点で、actor は
> `system`（`actor_label = forge-cli:<OS のアカウント>`）、本番では承認された Runbook（`oidc-identity-link`）の手順としてだけ実行する。
> 入口は `forge_oidc::operator_link_identity`（→ `forge_db::identities::link_by_operator`）だけで、どちらも actor が `system` でなければ
> FG-SYS-0001 `reason=operator_not_system`（HTTP から到達できない）。監査は `user.identity_linked`（`via=operator`、`issuer`。`sub` は入れない）。

入口とテストはこのコミットにある。**clap のコマンド自体は未実装**（§7）。
