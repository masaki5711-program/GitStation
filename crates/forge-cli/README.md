# forge-cli

**Responsibility**: the `forge` binary — operator commands now, the server
entry point from M1.

**Commands**

| Command | Purpose |
|---|---|
| `forge explain <CODE>` | cause / diagnosis / fix / runbook of an FG code |
| `forge errors list` | every registered code (id, HTTP, severity, cause) |
| `forge --version` | version |
| `forge admin repo-path <repo_id> [--storage-root]` | where a repository is stored (from its id, ADR-0009) and whether it exists |
| `forge admin token issue --user <name> --scopes <list> [--expires-in <n>d] [--name] [--agent]` | issue a personal access token (ADR-0019); printed **once** on stdout, never logged |
| `forge admin token revoke <token_id>` | revoke a token (`already revoked` writes nothing) |
| `forge admin token list --user <name>` | a user's tokens, newest first (never the secret) |
| `forge admin user disable <username> [--force]` | disable a user and revoke their active tokens; refused (FG-AUTH-0009) when it would leave no active human administrator or a top-level group without a direct active Owner, unless `--force` |
| `forge admin bootstrap-admin --user <name> [--create --email <e> [--display-name <n>]]` | make an active human the administrator (or create one) when forge has none: first install, recovery after `--force` |
| `forge admin events new-epoch` | M3 I1c (ADR-0016 Amendment I1c, runbook integration-feed-lag): after a database restore or rebuild in the same cluster, give the event feed a new epoch through `forge_maint` (`database.maint_url`; `forge.feed_new_epoch`, which writes `feed.epoch_rotated`); logs FG-DB-0014 and prints both epochs; every integration's cursor then answers 410 `epoch_mismatch` |
| `forge admin repo maintain <repo_id>` | M3 O3: enqueue one `repository.maintain` job for a ready repository (`forge_db::maintenance::enqueue_now`, key per request); the worker's maintenance lane runs it at once; an ops exception outside `authorize()` (ADR-0019 Amendment 2026-11-03); runbook `repo-maintenance` |
| `forge admin repo allow-import <repo_id> [--ttl-hours N]` | 2026-11-12: allow the one-time history import into an EMPTY repository (refs read with git first; FG-GIT-0025 when it has refs or is not ready); the first accepted push may carry secrets only in history (audited `repository.history_secret_imported`, a tip secret still refuses); `forge_db::history_imports::allow`; runbook `push-checks` "history import" |
| `forge backup` | M3 O1 (ADR-0019 Addendum O1, runbook `backup-restore`): one encrypted generation in `backup.dir` — the database first (pgBackRest behind `backup::db_tool::DbBackupTool`), then every ready repository (refs before objects, `git fsck --connectivity-only` of the copy, AES-256-GCM archive), `manifest.json` last, rotation to `backup.generations` (7), then a state copy; refuses a directory reachable by others (FG-SYS-0008 `insecure_permissions`) |
| `forge restore begin \| repositories --generation <g> [--replace] \| verify \| finish --generation <g> [--accept-db-behind] \| regrant-admin <username>` | M3 O1: the restore drill. `begin` makes `forge serve` / `forge worker` refuse to start (FG-SYS-0009 `restore_pending`) until `finish`; `verify` (read-only) compares `merge_request_versions` with `refs/merge-requests/*`, fscks every ready repository and reports database-behind refs / repositories; `finish` verifies again, revokes every token / session / webhook (`restore`), re-applies the narrowings of the newest state copy (or removes every administrator flag), rotates the feed epoch (`database.maint_url`) and writes `restore.finished`; `regrant-admin` gives a listed user the flag back |
| `forge admin runner register --name <n> --admin <user> [--tags a,b] [--description d]` | M4 C4 (runbook `ci-runner`): register a CI runner, recorded as registered by `--admin` (an active human administrator, else FG-AUTH-0003); its token `fgr_…` is printed **once** on stdout, never logged. Until the administration screen exists this is the way to register one (the API takes an administrator's web session only) |
| `forge admin runner list` | the runners (id, name, enabled, tags, last contact; never a token) |
| `forge admin runner disable <runner_id> --admin <user>` | disable a runner (the administrator is recorded as the audit actor): its token and its jobs' tokens are refused from the next request |
| `forge admin ssh-host-key generate` | M4 C13 (ADR-0032 §2, runbook `ssh-transport`): make the SSH transport's Ed25519 host key at `git.ssh.host_key_file` once (0600 on Unix; an existing file is never replaced: FG-SYS-0002 `target_exists`) and print its fingerprint and `known_hosts` line. `forge serve` never makes one |
| `forge admin ssh-host-key show` | the configured host key's fingerprint and `known_hosts` line (reads only) |
| `forge admin repo reprovision <repo_id>` | enqueue the provisioning job of a repository still `provisioning` again (after its job died; FG-REPO-0012); refused for a ready repository (FG-REPO-0014 `repository_ready`) |

`forge serve` (connects the database and checks the schema before binding; never migrates; injects the database into forge-web as the readiness probe and as the token authenticator — `forge_db::tokens::authenticate` behind `forge_core::Authenticator`, ADR-0019 §7, wrapped in `forge_web::BoundedAuthenticator` with `max(1, database.write_max_connections / 2)` concurrent lookups), `forge worker` (the background tasks until SIGINT / SIGTERM: the outbox sequencer every 200 ms via `forge_db::sequencer::run_once`, numbering events only — audit rows wait for the per-process sink comparison of C9; a failure is logged once per streak with `task` and backs off up to 5 s; the C6 job runner and reaper; the C8 audit seal `audit_seal`: looks every 10 s, seals via `forge_db::seal::seal_due` a minute after the last seal or when > 1000 rows wait, at once again while `more` — it needs `audit.seal_keys_file`, without it the worker does not start, `FG-SYS-0002 reason=missing`; the D4 MR3b job handler `repository.provision` (60 s): reads the repository's token on the write pool, `StorageRoot::init_bare_or_adopt_until` (git from `PATH`, HOME pinned to the storage root, at most 20 s per git call and never past the run's storage deadline — half the job's timeout —, file-system steps under the same deadline, no hooks path until M1 phase 10), then `forge_db::repositories::mark_ready_within` (the rest of the job's timeout minus 12 s for COMMIT; a hung step fails with its own retryable code, FG-GIT-0002 / FG-REPO-0003 `reason=deadline` / FG-DB-0002 `change_timeout`); logs `forge.repo.provisioned` (`repo_id`, `project_id`, `outcome` created / adopted / already_ready, `attempt`, `duration_ms`) once; storage failures retry or dead-letter by `provision_error_is_retryable` (FG-REPO-0004 `adopt_refused` is dead at once), database failures retry on FG-DB-0001 / 0002 — so the worker also needs `storage.root` and does not start without it; M3 R1b: the job handler `merge_request.refresh` (60 s, `worker/review.rs`: `forge_review::refresh` — the source tip, the version row, the hidden refs; git / storage / database failures and a repository not ready retry, anything else is dead at once) and the first production subscriber `merge-request-refresh` (`worker::registry(&ReviewConfig)`, registered at the head; it starts the `subscribers` task); M3 R2: the job handler `merge_request.mergeability` (90 s, `forge_review::check`, retried like the version job) and the subscriber's target-push checks capped by `review.mergeability_fanout_max`; the job's last failed attempt stores `job_failed`; the `mergeability_sweep` task every 30 s ends stale `checking` rows (`job_stale`) and re-requests `unchecked` ones with no live job, 50 per run, and verifies 50 decided rows per run against the live target tip with git (re-requesting the moved ones); doctor `review.mergeability`, FG-REVIEW-0003; M3 R6: the `codeowners_restore` task every 60 s records expired CODEOWNERS suspensions via `forge_db::review::restore_expired_codeowners` and logs `forge.worker.codeowners_enforcement_restored` — for the record only, the evaluation never waits for it; M3 I1c: the `events_retention` task every hour runs one batch of `forge.events_retention` (`forge_db::feed::run_retention`, at once again while a batch fills its window) and logs `forge.worker.events_retained`; the `check_run_retention` task every hour (after a full batch again after 0.5 s) runs `forge_db::checks::expire_old_runs` — check runs (with annotations) last updated more than `review.check_run_retention_days` (default 180, 30..=3650) days ago and not the current head of an open merge request, at most 1000 per short transaction, one `check_run.retention` audit row per project and batch — and logs `forge.worker.check_runs_expired`; doctor `checks.retention` warns while due runs are left), `forge db status [--check]` / `forge db migrate` (ADR-0014), `forge doctor [--json]` (read-only checks: config, database, schema, outbox backlog and sequencer lag (FG-DB-0005), audit seal backlog / verification (FG-DB-0015 / FG-DB-0011; `warn` when seals exist but this host has no seal keys, so HMACs were not checked), job queue, subscribers, who administers forge (`users.administration`: FG-AUTH-0010 warn when there is no active human administrator or a top-level group has no direct active Owner; `warn` without a code when there are no users yet), repository provisioning (`repositories.provisioning`: FG-REPO-0012 alert when a repository waits in `provisioning` > 10 min or its job is not queued / running), ready repositories without a directory (`repositories.storage`: FG-REPO-0002 with `missing` / `other` counts, at most 10 000 checked per run — beyond that `warn` / `truncated`; the stat calls run on the blocking pool, the whole walk within 60 s, else FG-REPO-0003 `check_timeout`; skipped when the storage root does not open; the only detector of a ready repository whose directory vanished), M3 I1c: `integrations.feed_lag` (FG-INT-0009 warn), `subscribers.work-item-sync` (the integration feed's bound), `events.retention`, `feed.sink_compare` (warns while `feed.require_sink_compare` is false, always in M3), storage, git; one line each — ok / warn / FAIL / skip — exits with the most severe failure). Logs go to stderr, command output to stdout. Planned: `forge diag bundle` (M1).

M3 N1 (ADR-0016 Amendment N1, `src/worker/notify_lane.rs`, runbook `notification-email`): with `notify.enabled` `forge worker` registers the recording `notify` subscriber (without it a paused one stays registered and records no mail, so enabling later never replays the disabled period) (merge request events → `forge.notifications`) and runs `notification.send` on its **own** `JobRunner` (task `notify_runner`, like the maintenance lane: a slow relay holds a send up to `notify.send_timeout_ms` and must not delay the main runner's one-at-a-time jobs); the relay's CA file and password are read at start (FG-SYS-0002). Doctor: `notify.queue` (FG-INT-0015: a notification waiting > 10 min, or failed in the last 24 h, unknown in the last 30 days, a warning for suppressed unusable addresses; read even while mail is off) and `notify.relay` (a TCP connect, nothing sent); both information while disabled. `forge serve` always mounts `GET|PUT /api/v1/user/notification-preferences`. M3 U4: the subscriber (also the paused one) records the in-app items (`forge.in_app_notifications`) for the same recipients, mail on or off; the task `in_app_notification_retention` (hourly) deletes read items after 30 days and every item after 180; `forge serve` mounts `GET /api/v1/user/notifications` (+ `/unread-count`) and `POST …/{id}/read`, `…/read-all`.

M3 O3 (ADR-0024 "実装で決めたこと（O3）", `src/worker/maintenance.rs`, runbook `repo-maintenance`): `forge worker` runs the repository maintenance on its **own** `JobRunner` (task `maintenance_runner`, only `repository.maintain` registered — the main runner never claims it, so a long gc never delays provisioning, version or mergeability jobs) and the task `maintenance_schedule` (every 60 s, only inside the `maintenance.window_*` window in `maintenance.window_time_zone`, read with the database's clock: the due repositories oldest first, at most `maintenance.batch_max` live jobs). One run: quarantine check → fsck (connectivity / full every `fsck_interval_days`; a finding stops it, FG-GIT-0019) → `gc --cruft --prune=<grace>` → pack-refs under the merge try-lock → commit-graph → counts, each step bounded by `maintenance.step_timeout_secs` and the run's deadline (job timeout 1 h − 60 s) and killed with its process tree; the ledger `forge.repository_maintenance` gets the outcome; a step's failure completes the job (warn, error from the second in a row). At start the worker checks the prune grace against the merge window and retry budget (`check_settings`) and the time zone (FG-SYS-0002). Doctor: `repositories.maintenance` (FG-GIT-0018 `failing` / `stale_running` / `no_recent_success` / `overdue`), `repositories.integrity` (FG-GIT-0019), `repositories.refs` (warn above `maintenance.refs_warn`), `repositories.stale_locks` (FG-GIT-0020: `packed-refs.lock` older than 10 min). O3 review: the quarantine is checked again right before gc; after a failed pack-refs the run removes its own `packed-refs.lock` (not older than the step) under the merge lock and alerts FG-GIT-0020 for an older one; the schedule records lost runs (`reap_stale_running`, FG-DB-0007) every pass; the outcome is logged after the ledger write (`forge.git.maintenance_ledger_failed` otherwise).

M3 R4 (ADR-0024 §4.2, `src/serve_merges.rs`): `forge serve` also runs the merge job `merge_request.merge` (one at a time, `forge_review::Merger` sharing the browse cache it invalidates; a failure that can pass later is retried, the last one ends a never-fenced attempt `superseded reason=job_failed`) and reconciles stuck attempts every 60 s (`Merger::reconcile`); `forge worker` does not register the kind. Shutdown gives a running merge 10 s. Review round 1: the runner and the reconciliation are separate tasks under supervisors (an unexpected exit or panic is FG-SYS-0005 `merge_task_exited`, restarted with a 1–30 s backoff); a reconciliation pass is bounded (50 s) and logs an info heartbeat `forge.serve.merge_reconcile_pass` once a minute (each attempt at most 20 s); `forge doctor` gains `review.merges` (FG-REVIEW-0009 `reconcile_overdue` / `ref_state_unknown` for `failed` attempts of the last 24 h). Runbook `merge-execution`.

M3 S0 (runbook `service-accounts`): `forge doctor` gains `service_accounts.tokens_expiring` (FG-AUTH-0019 warn: an active service account whose active tokens all expire within 14 days; `expiring_service_accounts`, `user_ids`, `soonest_expiry`, `within_days`) and `service_accounts.ownerless` (FG-AUTH-0010 warn `reason=ownerless_service_account`: no active human owner; `ownerless_service_accounts`, `user_ids`). Ids and counts only.

**`forge admin`** (step D3): `token issue` / `token revoke` are the first
mutating admin commands. The host operator is the trust root, so they run
outside `authorize()` (documented exception, ADR-0019 §8); `forge_db::tokens`
enforces the rules itself (the `admin` scope only for administrators, no bots,
no disabled owners, 1–365 days, 50 active tokens). In production running them
is an approved runbook step. The audit actor is the system actor labelled with
the OS account (`USERNAME` / `USER`). Log events `forge.admin.token.issued` /
`forge.admin.token.revoked` carry the token id and public id only. Scopes:
`read_repository`, `write_repository`, `read_api`, `api`, `admin`.
`user disable` and `bootstrap-admin` (D3 MR2, ADR-0019 §10–§11 and Amendment)
are mutating too: `forge_db::users` enforces the administration guard, and
`--force` (the first `--force` of the CLI) exists only here — HTTP never gets a
way past the guard. Log events `forge.admin.user.disabled` (`user_id`,
`forced`, `outcome`, `ownerless_groups`, `left_without_admin`) and
`forge.admin.user.admin_bootstrapped` (`user_id`, `created`) carry ids and
flags, never names. Runbook: `ops/runbooks/user-offboarding.md`.
`repo reprovision` (D4 MR3b) is mutating as well: `forge_db::repositories::reprovision`
locks the repository, refuses a ready one and writes the job with an audit-only
`repository.reprovision_requested` row; a queued / running job writes nothing (the
message names its state); after a succeeded job (a restore or a manual change) the new
job is keyed after it. Log event `forge.admin.repo.reprovisioned` (`repo_id`,
`project_id`, `job_id`, `after_job_id`, `outcome` queued / already_live, `job_state`). Runbook: `ops/runbooks/repository-provisioning.md`.

**Boundary rule**: `main.rs::report` is the CLI's error boundary — it logs the
`ForgeError` once via `telemetry::log_failure` and prints only the localized
user message, the code and the 問い合わせ番号. Exit codes: 2 = usage/unknown
input, 1 = failure.

**Error codes owned**: uses `FG-SYS-0005` (UnknownErrorCode). `forge admin token`
raises FG-AUTH-0008 `reason=scope_unknown` / `expires_malformed` itself (the name
is not echoed); the rest come from `forge_db::tokens` (see the forge-db README).
`forge admin user disable` / `bootstrap-admin` surface FG-AUTH-0009 from
`forge_db::users`; `forge doctor` reports FG-AUTH-0010, FG-REPO-0012 and FG-REPO-0002
(`repositories.*`). `forge admin repo reprovision` surfaces FG-REPO-0014 / 0005 from
`forge_db::repositories`.
